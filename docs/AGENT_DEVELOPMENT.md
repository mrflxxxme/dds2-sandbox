# Agent TDD — правила разработки DDS

**Методология:** Contract-First TDD с агентной оркестрацией (Agent TDD).

## Принцип

Один человек + ИИ-агенты. Человек описывает задачу своими словами.
Агент уточняет детали, формирует ТЗ, сам оркестрирует sub-агентов,
пишет тесты, код, миграции — параллельно где возможно.

---

## Фазы разработки

```
Фаза 0:   Понимание    → Lead (opus): уточняет → ТЗ
Фаза 1:   Фундамент    → Lead (opus): Model→Migration→Schema
           + Pre-warm   → Frontend explorer (opus, read-only) — параллельно
Фаза 2:   Реализация   → 2-3 агента (opus) параллельно
Фаза 2.5: Review       → code-reviewer + security-reviewer (opus) параллельно
Фаза 3:   Валидация    → pytest ‖ vitest ‖ conventions ‖ docs (opus) параллельно
           → Коммит
```

### Фаза 0 — Понимание задачи (человек + агент)

**Человек** описывает задачу своими словами. Любой формат — хоть одно предложение.

**Агент** читает DOMAIN_*.md затронутых доменов, анализирует существующий код,
затем задаёт уточняющие вопросы, чтобы заполнить пробелы:

```
Уточняющие вопросы агента (задаёт только то, что неясно из описания):

1. Модели     → Новая таблица или изменение существующей? Какие поля?
2. API        → Какие endpoint-ы? Что принимают/возвращают?
3. Frontend   → Нужен? Таблица/форма/модалка? Какие действия?
4. Кэш        → Нужен? Когда инвалидировать?
5. Крайние    → Что если пустые данные? Дубликаты?
6. Приоритет  → Что важнее: скорость или полнота?
```

**После ответов** агент формирует ТЗ и показывает на подтверждение:

```markdown
# ТЗ: [Название]

## Что и зачем
1-2 предложения (из слов человека).

## Домены
[x] Reports  [x] Frontend  ...

## Модели / Таблицы
- Новая: `ModelName` (поля, SoftDeleteMixin: да/нет)
- Изменение: `ModelName` (что меняется)
- Alembic миграция: да/нет

## API-контракт
| Метод | Путь | Request | Response |
|-------|------|---------|----------|
| GET   | /api/v1/... | query params | `TypeName[]` |
| POST  | /api/v1/... | `CreateSchema` | `TypeName` |

## Бизнес-правила
1. При X → Y
2. Кэш: prefix=`...`, TTL=..., инвалидация: ...

## Frontend
- Страница: /p/[slug]/...
- Компоненты: DataTable / FormModal / кастом
- Состояния: loading, error, empty

## Тест-кейсы
### Backend
1. Позитивный: ...
2. Негативный: ...
3. Граничный: ...

### Frontend
1. Рендер данных
2. Loading/empty/error
3. Действия пользователя
```

**Человек** подтверждает ТЗ или корректирует. После подтверждения — Фаза 1.

#### Когда нужно ТЗ, а когда нет

| Тип задачи | Пример | ТЗ + подтверждение |
|------------|--------|--------------------|
| Новый модуль / фича | Отчёт по марже, новый CRUD | Да — полное ТЗ, ждать подтверждения |
| Кросс-доменное изменение | Новое поле WB → влияет на отчёт | Да — ТЗ нужно, связи неочевидны |
| Баг / мелкий фикс | Сломался фильтр, опечатка, 500 на endpoint | Нет — сразу чинить |
| Одно поле / мелкое изменение | Добавить `phone` в User | Нет — сразу делать |
| Рефакторинг без изменения API | Разбить сервис на два файла | Нет — сразу делать |

**Правило:** Новая фича или кросс-доменное изменение → ТЗ + подтверждение. Баг или мелочь → сразу делать.
**Правило:** ТЗ должно содержать API-контракт. Без контракта параллельная разработка невозможна.

### Фаза 1 — Фундамент + Pre-warm (lead последовательно + 1 read-only агент)

**Lead agent (opus) — строго последовательно:**

```
1. Model (models/*.py)
2. Alembic migration (alembic/versions/*.py)
3. Schema (schemas/*.py)
```

**Почему последовательно:**
- Migration зависит от Model
- Schema зависит от Model
- Два Alembic revision одновременно → сломанная цепочка

**Frontend Pre-warm (opus, read-only) — параллельно с lead:**

Пока lead создаёт модели/миграции, read-only агент изучает frontend:
1. Читает `src/types/api.ts` — существующие интерфейсы
2. Читает `src/lib/api/{domain}.ts` — существующие API методы
3. Читает целевую страницу или ближайший аналог
4. Читает `src/components/` которые будут использоваться
5. Читает `.claude/templates/new_page.tsx.tmpl`

**CONSTRAINT:** Pre-warm агент НЕ пишет файлы. Только чтение.
**Зачем:** Frontend agent в Фазе 2 стартует с полным контекстом, без разгона.

**Результат фазы:** модель в БД, схемы готовы, frontend контекст загружен.

---

### Фаза 2 — Реализация (2-3 агента параллельно, opus)

Главный агент сам запускает sub-агентов через Agent tool и контролирует результат.
Человек не участвует — ждёт результат Фазы 3.

#### Стандартный режим (2 агента — backend + frontend):

```
┌─────────────────────────┐    ┌─────────────────────────┐
│  Агент 1: Backend       │    │  Агент 2: Frontend      │
│  (opus)               │    │  (opus)               │
│                         │    │                         │
│  1. Тесты (красные)     │    │  1. Типы в api.ts       │
│  2. Service             │    │  2. API метод в api.ts   │
│  3. Router              │    │  3. Страница/компонент   │
│  4. Тесты (зелёные)     │    │  4. Vitest тесты        │
│                         │    │                         │
│  Файлы:                 │    │  Файлы:                 │
│  - tests/test_*.py      │    │  - src/types/api.ts     │
│  - services/*_service.py│    │  - src/lib/api.ts       │
│  - routers/*.py         │    │  - src/app/p/[slug]/*   │
│  - cache.py (prefix)    │    │  - src/components/*     │
│                         │    │  - src/__tests__/*      │
└─────────────────────────┘    └─────────────────────────┘
         ↓ 0 пересечений файлов ↓
```

#### Расширенный режим (3 агента — 2 backend домена + frontend):

Когда задача затрагивает 2+ **изолированных** backend домена:

```
┌───────────────────┐  ┌───────────────────┐  ┌───────────────────┐
│  Backend-A        │  │  Backend-B        │  │  Frontend         │
│  (opus)         │  │  (opus)         │  │  (opus)         │
│                   │  │                   │  │                   │
│  domain A:        │  │  domain B:        │  │  types + api +    │
│  service+router   │  │  service+router   │  │  page + tests     │
│  +tests           │  │  +tests           │  │                   │
└───────────────────┘  └───────────────────┘  └───────────────────┘
```

**Условия для 3 агентов:**
1. Домены в матрице изоляции (см. ниже) — НЕ импортируют друг друга
2. `cache.py` — изменения очереди для lead agent ПОСЛЕ обоих backend
3. Каждый backend агент владеет ТОЛЬКО файлами своего домена

**Frontend работает по API-контракту из ТЗ**, не дожидаясь backend.
API-методы в `api.ts` пишутся по контракту — когда backend готов, всё подключается без изменений.

### Фаза 2.5 — Параллельный Review (2 read-only агента, opus)

Запускается сразу после завершения Фазы 2, ДО тестов:

```
┌──────────────────────────┐    ┌──────────────────────────┐
│  code-reviewer (opus)  │    │  security-reviewer       │
│  read-only               │    │  (opus) read-only      │
│                          │    │                          │
│  - Iron rules            │    │  - SQL injection         │
│  - Качество кода         │    │  - Multi-tenancy         │
│  - Конвенции DDS         │    │  - Crypto / secrets      │
│  → APPROVE/WARNING/BLOCK │    │  → APPROVE/WARNING/BLOCK │
└──────────────────────────┘    └──────────────────────────┘
```

**CRITICAL issues** → исправить ДО Фазы 3
**WARNING/LOW** → заметить, продолжить к Фазе 3

### Фаза 3 — Параллельная валидация + Docs (3-4 агента, opus)

Все проверки НЕЗАВИСИМЫ — запускать параллельно:

```
┌──────────────────┐  ┌──────────────────┐  ┌──────────────────┐  ┌──────────────────┐
│  pytest          │  │  vitest          │  │  conventions     │  │  docs (optional) │
│  (opus)         │  │  (opus)         │  │  (opus)         │  │  (opus)         │
│                  │  │                  │  │                  │  │                  │
│  docker compose  │  │  cd frontend-    │  │  bash scripts/   │  │  git diff →      │
│  exec backend    │  │  react && npx    │  │  check_          │  │  update          │
│  pytest tests/   │  │  vitest run      │  │  conventions.sh  │  │  DOMAIN_*.md     │
│  -x --tb=short   │  │                  │  │                  │  │  CLAUDE.md       │
└──────────────────┘  └──────────────────┘  └──────────────────┘  └──────────────────┘
```

После всех проверок → один коммит или логическая серия коммитов

## Правила параллелизации

### Можно параллелить (0 конфликтов)

| Агент 1 | Агент 2 | Почему безопасно |
|---------|---------|------------------|
| Backend service + tests | Frontend страница | Разные языки, разные директории |
| Сервис домена A | Сервис домена B | Разные файлы, разные таблицы |
| Backend pytest | Frontend vitest | Независимые фреймворки |

### НЕЛЬЗЯ параллелить

| Ситуация | Риск | Решение |
|----------|------|---------|
| 2 Alembic миграции | Сломанная цепочка revision | Строго последовательно |
| 2 агента → один файл | Git конфликт | Только один агент на файл |
| Сервис A вызывает сервис B | Агент не видит изменений другого | Последовательно |
| `opiu_service` + `wb_bdr_service` | Связанная логика удержаний | Один агент на оба |
| Модель + тесты к ней | Тесты зависят от реализации | Фаза 1 → Фаза 2 |

### Файлы-синглтоны (только один агент одновременно)

Эти файлы трогает максимум один агент за задачу:

- `CLAUDE.md`
- `cache.py` (invalidate_project_reports)
- `alembic/versions/*`
- `scripts/check_conventions.sh`
- `src/types/api.ts` (frontend singleton)
- `src/app/globals.css` (стили singleton)

---

### Матрица изоляции доменов (для multi-domain backend)

Перед запуском 2+ backend агентов — проверь что домены НЕ импортируют друг друга.

#### Безопасные пары (0 зависимостей):
| Домен A | Домен B | Можно параллелить |
|---------|---------|-------------------|
| reports/ | planning/ | ✅ |
| funnel/ | assembly/ | ✅ |
| transactions_service | warehouse_* | ✅ |
| telegram_service | cost/ | ✅ |
| ai/ | reports/ | ✅ |

#### НЕЛЬЗЯ параллелить (есть import-зависимости):
| Домен A | Домен B | Причина |
|---------|---------|---------|
| warehouse_stock | warehouse_need | need импортирует stock |
| supply_chain/ | cost/ | vehicle_delivery → cost/items |
| opiu_service | wb_bdr_service | оба используют bdr_loaders |
| health_check | warehouse_*/funnel/ | health_check импортирует оба |
| stock_analytics | stock_forecast | analytics → forecast |

**Правило:** Если сомневаешься — проверь через `grep -r "from backend.services.{domain}" backend/services/`.

| Задача | Модель | Обоснование |

## TDD-цикл внутри фазы 2

Каждый агент в фазе 2 следует циклу:

```
1. Написать тесты по тест-кейсам из ТЗ
2. Запустить → убедиться что КРАСНЫЕ (падают)
3. Написать минимальный код → тесты ЗЕЛЁНЫЕ
4. Рефакторинг (не ломая тесты)
```

### Backend тесты

```python
# tests/test_{module}.py
# Обязательные сценарии:
# 1. Позитивный — CRUD с валидными данными
# 2. project_id — чужой project → пустой результат (НЕ 403)
# 3. is_deleted — удалённые не возвращаются
# 4. Пустые данные → пустой массив
# 5. Невалидный input → 422
```

### Frontend тесты

```typescript
// src/__tests__/{component}.test.tsx
// Обязательные сценарии:
// 1. Рендер — данные отображаются
// 2. Loading — спиннер
// 3. Empty — пустое состояние
// 4. Error — сообщение об ошибке
// 5. Action — клик вызывает API метод
```

## Чеклист готовности (перед коммитом)

```
Железные правила DDS:
  [ ] project_id фильтрация в каждом запросе
  [ ] is_deleted фильтрация (если SoftDeleteMixin)
  [ ] soft_delete() вместо db.delete()
  [ ] Numeric(18,2) для денег
  [ ] Параметризованный SQL (не f-string)
  [ ] invalidate_cache() после мутаций
  [ ] Бизнес-логика в services/ (не в routers/)
  [ ] utcnow() из backend.utils.time

Тесты:
  [ ] pytest tests/ -x — зелёные
  [ ] npm run test — зелёные (если frontend)

Конвенции:
  [ ] bash scripts/check_conventions.sh — проходит

Автоматические проверки (не нужно запускать вручную):
  - Bandit + Gitleaks — запускаются автоматически через pre-commit hooks
  - CodeRabbit — автоматически ревьюит PR после push

Документация:
  [ ] CLAUDE.md обновлён (новый домен/модель/кэш)
  [ ] DOMAIN_*.md обновлён (если затронут домен)
```

## Примеры

### Пример 1: Новая фича (полный цикл)

**Вы:** "Хочу видеть маржу по каждому товару — выручка минус себестоимость минус комиссия WB"

```
Фаза 0 — Понимание:
  Агент читает DOMAIN_REPORTS.md, DOMAIN_COST.md, DOMAIN_WB.md
  Агент спрашивает:
    — За какой период? Фильтр по бренду нужен?
    — Таблица на отдельной странице или таб в reports?
    — Что если у товара нет себестоимости?
  Вы отвечаете.
  Агент формирует ТЗ:
    GET /api/v1/reports/product-margin → ProductMarginRow[]
    Frontend: таблица с Excel export, страница /reports/product-margin
  Вы: "ок"

Фаза 1 — Фундамент:
  → Schema: ProductMarginRow в schemas/reports.py
  → Новых моделей нет (JOIN существующих)

Фаза 2 — Реализация (агент запускает параллельно):
  Sub-агент 1 (backend):
    → tests/test_product_margin.py (5 тестов, красные)
    → services/reports/product_margin_service.py
    → routers/reports.py (добавить endpoint)
    → cache.py (добавить prefix)
    → тесты зелёные

  Sub-агент 2 (frontend):
    → types/api.ts (ProductMarginRow)
    → api.ts (getProductMargin)
    → src/app/p/[slug]/reports/product-margin/page.tsx
    → src/__tests__/product-margin.test.tsx
    → vitest зелёные

Фаза 3 — Интеграция:
  → pytest + vitest + check_conventions
  → коммит: feat: отчёт по марже по товарам
```

### Пример 2: Баг (быстрый цикл)

**Вы:** "На странице транзакций 500 ошибка при пустом фильтре"

```
Без ТЗ. Агент сразу:
  → Читает лог ошибки
  → Находит причину в services/transactions_service.py
  → Фиксит
  → Прогоняет pytest
  → Коммит: fix: 500 при пустом фильтре транзакций
```
