# Agent TDD — правила разработки DDS

**Методология:** Contract-First TDD с агентной оркестрацией (Agent TDD).

## Принцип

Один человек + ИИ-агенты. Человек описывает задачу своими словами.
Lead-агент уточняет детали, формирует ТЗ, **по умолчанию делает работу сам последовательно**.
Параллельные sub-агенты включаются ТОЛЬКО когда задача реально делится на изолированные слои (backend + frontend).

**Главный урок (2026-04-22):** избыточный параллелизм давал оверхед больше выигрыша. Простые задачи занимали 20-30 мин из-за спавна/синка/мержа teammates. Текущая политика — параллелить только то, где выигрыш очевиден.

---

## Когда параллелить

| Тип задачи | Как делать |
|---|---|
| Только backend | Lead сам, последовательно |
| Только frontend | Lead сам, последовательно |
| **Backend + Frontend** (обе части реально нужны) | **2 параллельных агента или Team** |
| Рефакторинг / баг / поиск кода | Lead сам |
| Очень крупная фича `/spec`-уровня | По обсуждению с пользователем |

**Принцип:** оверхед оркестрации должен быть **меньше** выигрыша от параллелизма. Для < 1 часа работы — почти всегда меньше.

---

## Фазы разработки (фича backend+frontend)

```
Фаза 0:   Понимание    → Lead (opus): уточняет → ТЗ → подтверждение пользователя
Фаза 1:   Фундамент    → Lead (opus): Model → Migration → Schema (последовательно)
Фаза 2:   Реализация   → Backend ‖ Frontend (2 агента, opus, isolation: worktree)
Фаза 2.5: Review       → code-reviewer / security-reviewer ПО ТРИГГЕРУ (последовательно)
Фаза 3:   Валидация    → Bash: pytest && vitest && check_conventions.sh → коммит
```

**Если задача только backend или только frontend** — Фаза 2 делается lead'ом без спавна агентов.

### Фаза 0 — Понимание задачи

**Человек** описывает задачу своими словами. Любой формат — хоть одно предложение.

**Lead-агент** читает DOMAIN_*.md затронутых доменов, анализирует существующий код, затем задаёт уточняющие вопросы:

```
1. Модели     → Новая таблица или изменение существующей? Какие поля?
2. API        → Какие endpoint-ы? Что принимают/возвращают?
3. Frontend   → Нужен? Таблица/форма/модалка? Какие действия?
4. Кэш        → Нужен? Когда инвалидировать?
5. Крайние    → Что если пустые данные? Дубликаты?
6. Приоритет  → Что важнее: скорость или полнота?
```

**После ответов** агент формирует ТЗ:

```markdown
# ТЗ: [Название]

## Что и зачем
1-2 предложения.

## Домены
[x] Reports  [x] Frontend  ...

## Модели
- Новая: `ModelName` (поля, SoftDeleteMixin: да/нет)
- Изменение: `ModelName` (что меняется)
- Alembic миграция: да/нет

## API-контракт
| Метод | Путь | Request | Response |
|-------|------|---------|----------|
| GET   | /api/v1/... | query params | `TypeName[]` |

## Бизнес-правила
1. При X → Y
2. Кэш: prefix=`...`, TTL=..., инвалидация: ...

## Frontend
- Страница: /p/[slug]/...
- Состояния: loading, error, empty

## Тест-кейсы
### Backend
1. Позитивный, негативный, граничный

### Frontend
1. Рендер, loading/empty/error, действия
```

#### Когда нужно ТЗ, а когда нет

| Тип задачи | Пример | ТЗ + подтверждение |
|------------|--------|--------------------|
| Новый модуль / фича | Отчёт по марже, новый CRUD | Да |
| Кросс-доменное изменение | Новое поле WB → влияет на отчёт | Да |
| Баг / мелкий фикс | Сломался фильтр, опечатка, 500 на endpoint | Нет — сразу чинить |
| Одно поле / мелкое изменение | Добавить `phone` в User | Нет — сразу делать |
| Рефакторинг без изменения API | Разбить сервис на два файла | Нет — сразу делать |

**Правило:** ТЗ должно содержать API-контракт. Без контракта параллельная разработка backend+frontend невозможна.

---

### Фаза 1 — Фундамент (lead последовательно)

```
1. Model (models/*.py)
2. Alembic migration (alembic/versions/*.py)
3. Schema (schemas/*.py)
```

**Почему последовательно:**
- Migration зависит от Model
- Schema зависит от Model
- Два Alembic revision одновременно → сломанная цепочка

**Pre-warm убрали** — lead сам прочитает frontend-контекст через Grep/Read, когда дойдёт до Phase 2 frontend-агента. Спавн read-only агента давал оверхеда больше, чем экономии.

---

### Фаза 2 — Реализация

#### Backend + Frontend (2 параллельных агента)

```
┌─────────────────────────┐    ┌─────────────────────────┐
│  Backend agent          │    │  Frontend agent         │
│  (opus, worktree)       │    │  (opus, worktree)       │
│                         │    │                         │
│  1. Тесты (красные)     │    │  1. Типы в api.ts       │
│  2. Service             │    │  2. API метод           │
│  3. Router              │    │  3. Страница/компонент  │
│  4. Тесты (зелёные)     │    │  4. Vitest тесты        │
│                         │    │                         │
│  Файлы:                 │    │  Файлы:                 │
│  - tests/test_*.py      │    │  - src/types/api.ts     │
│  - services/*_service.py│    │  - src/lib/api/*.ts     │
│  - routers/*.py         │    │  - src/app/p/[slug]/*   │
│  - cache.py (prefix)    │    │  - src/components/*     │
└─────────────────────────┘    └─────────────────────────┘
         ↓ 0 пересечений файлов ↓
```

Frontend работает по API-контракту из ТЗ, не дожидаясь backend. Когда backend готов — всё подключается без изменений.

#### Только backend или только frontend

Lead делает сам, последовательно, в основной директории. Без спавна агентов и worktree.

#### Multi-domain backend (3 агента) — УБРАН из default

Раньше был «расширенный режим: 2 backend домена + frontend». Убран — слишком редкий кейс, сложная матрица зависимостей, прецедент `7a8c70c` (агент писал в main dir вместо worktree).

Если задача реально требует — пользователь явно говорит «параллельно по доменам», тогда возвращаем multi-agent для конкретной задачи.

---

### Фаза 2.5 — Review (по триггеру, последовательно)

После завершения Фазы 2 (или Фазы 1 для backend-only) lead запускает sub-агентов **последовательно**, по триггерам:

| Агент | Триггер |
|-------|---------|
| `code-reviewer` | Дифф ≥ 3 файла или новый домен |
| `security-reviewer` | Задеты `auth/SQL/crypto/user-input/secrets` |
| `performance-optimizer` | Новые endpoints с массовыми выборками |
| `database-reviewer` | Миграции, сложные SQL |
| `api-designer` | Новые/изменённые routers/schemas |

**НЕ параллелить с Phase 2.** Параллельный review раньше иногда применял блокирующие фиксы без чтения memory (прецедент 2026-04-21: `RuntimeError("REGISTER_ENABLED=true forbidden")` крашнул прод). Последовательный review безопаснее: lead передаёт агенту контекст из memory.

**CRITICAL issues** → исправить ДО Фазы 3
**WARNING/LOW** → заметить, продолжить

---

### Фаза 3 — Валидация (Bash напрямую)

```bash
docker compose exec backend pytest tests/ -x --tb=short
cd frontend-react && npx vitest run
bash scripts/check_conventions.sh
```

**Раньше было:** 4 параллельных агента (pytest ‖ vitest ‖ conventions ‖ docs).
**Сейчас:** Bash напрямую — быстрее, меньше токенов, меньше ошибок. Спавн валидаторов давал оверхед без выигрыша.

После всех проверок → один коммит или логическая серия коммитов.

## Правила параллелизации (когда задача backend+frontend)

### Можно параллелить (0 конфликтов)

| Агент 1 | Агент 2 | Почему безопасно |
|---------|---------|------------------|
| Backend service + tests | Frontend страница | Разные языки, разные директории |
| Backend pytest | Frontend vitest | Независимые фреймворки |

### НЕЛЬЗЯ параллелить

| Ситуация | Риск | Решение |
|----------|------|---------|
| 2 Alembic миграции | Сломанная цепочка revision | Строго последовательно |
| 2 агента → один файл | Git конфликт | Только один агент на файл |
| Сервис A вызывает сервис B | Агент не видит изменений другого | Последовательно |
| Модель + тесты к ней | Тесты зависят от реализации | Фаза 1 → Фаза 2 |

### Файлы-синглтоны (только один агент одновременно)

- `CLAUDE.md`
- `cache.py` (`invalidate_project_reports`)
- `alembic/versions/*`
- `scripts/check_conventions.sh`
- `src/types/api.ts` (frontend singleton)
- `src/app/globals.css`

---

## Изоляция параллельных агентов (`isolation: worktree`)

При запуске 2 агентов одновременно (Backend + Frontend) — обязателен `isolation: worktree`:

- Создаёт временный git worktree автоматически
- Убирается сам если агент не сделал изменений
- Если изменения есть — путь и ветка возвращаются для merge
- 0 конфликтов файлов между параллельными агентами

Lead agent (Phase 1, Phase 3 коммит) → НЕ изолируется.

### Constraints для каждого teammate (обязательно в промпте)

1. **Relative paths only** — никаких `/Users/a1/Desktop/dds_app/...` в Read/Write/Edit/Bash
2. **Types-first** — сначала `types/api.ts` + `lib/api/<domain>.ts`, потом тесты
3. **Git-status-check в конце** — отчёт с `git status`, `git diff --stat`, `git log -1 --oneline`
4. **Long-running → `run_in_background: true`** если >5 мин

## Model Routing
**Политика: opus 4.7 везде** (Max подписка, требование владельца 2026-04-21 — см. `memory/feedback_model_always_opus.md`).

| Задача | Модель |
|--------|--------|
| Lead (Фаза 0 + оркестрация) | opus |
| Фаза 1 (Model+Migration+Schema) | opus |
| Фаза 2 Backend / Frontend | opus |
| Фаза 2.5 reviewers | opus |

## TDD-цикл внутри фазы 2

```
1. Написать тесты по тест-кейсам из ТЗ
2. Запустить → убедиться что КРАСНЫЕ (падают)
3. Написать минимальный код → тесты ЗЕЛЁНЫЕ
4. Рефакторинг (не ломая тесты)
```

### Backend тесты

```python
# tests/test_{module}.py
# Обязательные сценарии:
# 1. Позитивный — CRUD с валидными данными
# 2. project_id — чужой project → пустой результат (НЕ 403)
# 3. is_deleted — удалённые не возвращаются
# 4. Пустые данные → пустой массив
# 5. Невалидный input → 422
```

### Frontend тесты

```typescript
// src/__tests__/{component}.test.tsx
// Обязательные сценарии:
// 1. Рендер — данные отображаются
// 2. Loading — спиннер
// 3. Empty — пустое состояние
// 4. Error — сообщение об ошибке
// 5. Action — клик вызывает API метод
```

## Чеклист готовности (перед коммитом)

```
Железные правила DDS:
  [ ] project_id фильтрация в каждом запросе
  [ ] is_deleted фильтрация (если SoftDeleteMixin)
  [ ] soft_delete() вместо db.delete()
  [ ] Numeric(18,2) для денег
  [ ] Параметризованный SQL (не f-string)
  [ ] invalidate_cache() после мутаций
  [ ] Бизнес-логика в services/ (не в routers/)
  [ ] utcnow() из backend.utils.time

Тесты:
  [ ] pytest tests/ -x — зелёные
  [ ] npx vitest run — зелёные (если frontend)

Конвенции:
  [ ] bash scripts/check_conventions.sh — проходит

Документация:
  [ ] CLAUDE.md обновлён (новый домен/модель/кэш)
  [ ] DOMAIN_*.md обновлён (если затронут домен)
```

## Примеры

### Пример 1: Новая фича backend+frontend (полный цикл с параллелизмом)

**Вы:** "Хочу видеть маржу по каждому товару — выручка минус себестоимость минус комиссия WB"

```
Фаза 0 — Понимание:
  Lead читает DOMAIN_REPORTS.md, DOMAIN_COST.md, DOMAIN_WB.md
  Спрашивает: период? фильтр по бренду? таб или страница?
  Формирует ТЗ → подтверждение

Фаза 1 — Фундамент (lead, последовательно):
  → Schema: ProductMarginRow в schemas/reports.py
  → Новых моделей нет (JOIN существующих)

Фаза 2 — Реализация (2 агента ПАРАЛЛЕЛЬНО):
  Backend agent (worktree):
    → tests/test_product_margin.py
    → services/reports/product_margin_service.py
    → routers/reports.py (endpoint)
    → cache.py (prefix)

  Frontend agent (worktree):
    → types/api.ts (ProductMarginRow)
    → lib/api/reports.ts (getProductMargin)
    → src/app/p/[slug]/reports/product-margin/page.tsx
    → src/__tests__/product-margin.test.tsx

Фаза 2.5 — Review (последовательно):
  → code-reviewer (дифф ≥ 3 файла)
  → security-reviewer пропускаем (нет auth/SQL/crypto)

Фаза 3 — Валидация (Bash):
  → docker compose exec backend pytest tests/ -x
  → cd frontend-react && npx vitest run
  → bash scripts/check_conventions.sh
  → коммит: feat: отчёт по марже по товарам
```

### Пример 2: Только backend (lead сам, без агентов)

**Вы:** "Добавь endpoint GET /api/v1/categories для списка категорий"

```
Без параллельных агентов:
Фаза 1: Lead сам — schema + service + router + test
Фаза 2.5: code-reviewer (если дифф ≥ 3 файла)
Фаза 3: pytest + check_conventions
Коммит: feat: GET /api/v1/categories
```

### Пример 3: Баг (быстрый цикл, без агентов)

**Вы:** "На странице транзакций 500 ошибка при пустом фильтре"

```
Без ТЗ. Lead сразу:
  → Читает лог ошибки
  → Находит причину в services/transactions_service.py
  → Фиксит
  → pytest
  → Коммит: fix: 500 при пустом фильтре транзакций
```
