## Шаг 1. Получить сборку

```bash
git clone -b sandbox/full-build https://github.com/mrflxxxme/dds2-sandbox.git dds2-full && cd dds2-full
```

Если репозиторий уже склонирован:

```bash
git fetch && git checkout sandbox/full-build && git pull
```

## Шаг 2. Создать `.env`

```bash
cp docs/specs/design/sandbox.env.example .env
```

Файл содержит рабочие значения для локального запуска: пароли для контейнеров, выключенные внешние интеграции (Wildberries, Telegram, AI), разрешённую регистрацию. Менять ничего не нужно.

## Шаг 3. Поднять стек

```bash
docker compose -p dds2-full -f docker-compose.yml -f docker-compose.sandbox.yml up -d --build
```

Два `-f` обязательны — без второго подхватится dev-override с портами 8000/3000/5432 и столкнётся с вашим основным стеком. Имя проекта `-p dds2-full` даёт отдельные контейнеры и тома.

Первая сборка — 5–15 минут. Миграции (236 ревизий) накатываются автоматически при старте backend.

```bash
docker compose -p dds2-full ps
```

Ожидаемо 7 контейнеров healthy. Адреса:

| Что | Адрес |
|---|---|
| Интерфейс | http://127.0.0.1:13000 |
| API, Swagger `/docs` | http://127.0.0.1:18000 |
| PostgreSQL | 127.0.0.1:15434, база `dds_db`, пользователь `dds` |

## Шаг 4. Завести пользователя и проект

```bash
curl -X POST http://127.0.0.1:18000/api/v1/auth/register -H "Content-Type: application/json" -d "{\"username\":\"lead\",\"password\":\"sandbox12345\",\"email\":\"lead@example.com\"}"
```

Ответ содержит `access_token`. Создайте проект:

```bash
curl -X POST http://127.0.0.1:18000/api/v1/projects -H "Content-Type: application/json" -H "Authorization: Bearer ТОКЕН" -d "{\"name\":\"Проверка\"}"
```

Владелец проекта получает доступ ко всем разделам автоматически. Войдите на http://127.0.0.1:13000 тем же логином.

## Что проверять

### А. Модуль «Дизайн карточек»

Раздел в меню, группа «Продажи». Полный цикл: создать заявку с подсказкой товара → у ведущего красная отметка → назначить исполнителя → перетащить карточку в «В работе» → сдать версию с файлами → вернуть с причиной (пустую причину форма не примет) → пересдать → принять. Журнал на деталке покажет все переходы с авторами и временем.

Остальные экраны: список с фильтрами, календарь с переключателем раскраски, загрузка команды, сквозной экран по брендам. Подробности — `docs/DESIGN-TASKS-GUIDE.md`.

Проверить отказы прав удобно вторым пользователем: зарегистрируйте его, пригласите в проект с ролью viewer без ключа `design-tasks` — раздел не появится в меню, а прямой запрос вернёт 403.

### Б. Права доступа на бэкенде

Главное, что изменилось: теперь недостаточно скрыть раздел на фронте — сервер сам проверяет ключ доступа.

```bash
curl -i http://127.0.0.1:18000/api/v1/ab-tests -H "Authorization: Bearer ТОКЕН_БЕЗ_ДОСТУПА" -H "X-Project-Id: ID"
```

Ожидается 403. До фикса такой запрос проходил, и участник с правом только просмотра мог запустить А/Б-тест, подменив живое фото карточки.

Учтите два эффекта, которые заметны сразу:

- **Роль viewer теряет запись везде.** Гейт выбирает роль по методу: чтение — viewer, любая мутация — editor. Если человек с ролью viewer раньше что-то создавал через интерфейс, теперь получит 403. Галочки доступа это не лечат — нужна роль editor.
- **Ключ `funnel` не даёт управления рекламой.** Воронка откроется, но ставки, пополнение бюджета и старт кампаний сидят на ключе `ads-manager` — без него именно эти кнопки отвалятся внутри открытого экрана.

Чтобы узнать заранее, кто именно упрётся в отказ, есть готовый запрос `scripts/rbac_impact_report.sql` — только чтение. Он воспроизводит логику эффективных прав вместе с наследованием и выдаёт по каждому участнику: проект, имя, роль, получит ли «Дизайн карточек» и список разделов, которые потеряет. На пустой локальной базе он бесполезен — нужна копия боевых данных:

```bash
docker compose -p dds2-full exec -T db psql -U dds -d dds_db -X -A -F "|" < scripts/rbac_impact_report.sql
```

Первым делом стоит посмотреть, нет ли участников с пустой датой настройки доступов — у них наследование выключено целиком, и они потеряют всё новое, включая новый раздел.

### В. Загрузки

Попробуйте приложить к задаче `.svg` или `.html` — файл отклонится с внятной ошибкой. Это закрывает возможность подсунуть активное содержимое, которое исполнилось бы при просмотре. Обычные картинки, PDF и архивы принимаются как раньше.

Скачивание отдаёт файл вложением с запретом угадывания типа — проверить можно заголовками:

```bash
curl -sI "http://127.0.0.1:18000/api/v1/design-tasks/1/materials/1/file" -H "Authorization: Bearer ТОКЕН" -H "X-Project-Id: ID"
```

В ответе `Content-Disposition: attachment` и `X-Content-Type-Options: nosniff`.

### Г. Внешний вид

Приглушённый текст (подписи, вторичные значения, плейсхолдеры) теперь действительно серый. Раньше около 390 мест по всему интерфейсу молча рендерились основным цветом из-за несуществующих переменных стилей. Заметнее всего на складских экранах, распределении остатков и в замерах.

## Прогнать тесты самому

Полная сюита (около 14 минут):

```bash
docker compose -p dds2-full exec backend pytest tests/ -q
```

Только модуль дизайна:

```bash
docker compose -p dds2-full exec backend pytest tests/test_design_models.py tests/test_design_state.py tests/test_design_service.py tests/test_design_permissions.py tests/test_design_notify.py tests/test_design_ab_bridge.py tests/test_api_design_tasks.py -q
```

Сторожевой тест прав — он падает, если у домена появится незакрытая ручка:

```bash
docker compose -p dds2-full exec backend pytest tests/test_rbac_page_gates.py -q
```

Типы и юнит-тесты фронтенда — **с хоста**, из каталога `frontend-react` (нужен Node 20+ и один раз `npm ci`). В контейнере они не запускаются: образ фронта — production-сборка без dev-зависимостей.

```bash
cd frontend-react && npx tsc --noEmit && npx vitest run
```

> Важно: полный прогон pytest чистит данные — тестовая инфраструктура удаляет всё, кроме зарезервированных проектов. Демонстрационные данные заводите после прогона, а не до.

## Управление стеком

Пересобрать после правок (исходники запечены в образ, bind-mount нет):

```bash
docker compose -p dds2-full -f docker-compose.yml -f docker-compose.sandbox.yml up -d --build backend worker
```

Остановить, сохранив данные:

```bash
docker compose -p dds2-full stop
```

Удалить целиком вместе с базой:

```bash
docker compose -p dds2-full -f docker-compose.yml -f docker-compose.sandbox.yml down -v
```

## Если что-то не так

**`POSTGRES_PASSWORD must be set in .env`** — пропущен шаг 2 или команда запущена не из корня репозитория.

**Порт занят** — сдвиньте порты в `docker-compose.sandbox.yml` (три строки) и перезапустите.

**Данные не грузятся** — `docker compose -p dds2-full logs backend --tail 50`; чаще всего backend ещё накатывает миграции, это до минуты после старта.

**Регистрация отвечает 403** — в `.env` стоит `REGISTER_ENABLED=false`; верните `true` и пересоздайте backend.

**Разлогинило после пересборки** — пересборка фронта перезапускает backend, выданные токены становятся недействительными. Войдите заново.
