## §1. Что строим

Раздел «Дизайн карточек» в DDS2: доска из 6 столбцов с перетаскиванием (основной вид), список (второй вид), календарь на месяц, экран загрузки команды, сквозной экран по брендам. Задача = заявка на инфографику: название товара текстом (+опциональная привязка к артикулу через автоподсказку), обязательная ссылка на ТЗ-гугл-таблицу, 2–3 строки сути, исходные материалы (файлы/ссылки/артикул-пример). Распределяет задачи только ведущий дизайнер. Сдача — версиями с вердиктом; из «Принято» и «Отменена» возврата нет. Уведомления: личные в TG + утренняя сводка в чаты. По принятой задаче с опознанным товаром — кнопка в АБ-тест фото.

Масштаб: 3 дизайнера, 60+ задач/мес. Роли PRD ↔ RBAC DDS2 (решение архитектора, без новых сущностей):

| Роль PRD | В DDS2 |
|---|---|
| Ведущий дизайнер | `member_role in ("owner","admin")` = **is_lead** |
| Менеджер | `editor`, различается как **автор** задачи (`author_user_id`) |
| Дизайнер | `editor`, различается как **исполнитель** (`assignee_user_id`) |
| Руководитель | любой с page-ключом `design-tasks` (обычно `viewer`) + TG-сводка |

## §4. Цикл фазы (5 шагов; сжатие 9-шагового WIZOR)

1. **Scope** — lead читает phase-spec + доноры, снимает открытые вопросы (эскалация, если продуктовые).
2. **Implement** — TDD: падающий тест первым; порядок Model → Migration → Schema → Service → Router → Test; исполнитель по `executors` спека.
3. **Verify** — `test-runner`: целевые гейты спека зелёные + `check_conventions.sh`; «зелёное по утверждению» запрещено — только транскрипт прогона.
4. **Review** — `/review`-фан-аут по tier (§ниже); ≤2 цикла правок, дальше — эскалация архитектору.
5. **Close** — строка в STATUS.md (дата, commit-sha, evidence), DECISIONS-LOG пополнен owned-решениями; подпись архитектора там, где требуется (§8).

**Tier = глубина ревью** (не размер фазы):

| Tier | Линзы |
|---|---|
| T1 | один профильный ревьюер (обычно `frontend-reviewer` или `code-reviewer`) |
| T3 | 3 линзы: `code-reviewer` + `security-reviewer` + (`database-reviewer` \| `api-designer` — по содержанию фазы) |
| T5 | полный `/review`-фан-аут + `performance-optimizer` (только Ф7) |

## §6. Стоячие инварианты модуля (проверяются КАЖДЫМ ревью, любой tier)

1. Каждый запрос фильтрует `project_id`; `GET /all-projects` — только проекты членства `ProjectMember` (отдельный тест обязателен).
2. SoftDelete-модели → `.where(is_deleted == False)`; удаление только `soft_delete()`.
3. `ACCEPTED` и `CANCELLED` — терминальны; переходы только по словарю; журнал `design_task_events` append-only, не подтирается.
4. Статусы/перечисления — `String`, не pg-enum.
5. Все write-ручки: `Depends(rate_limit_write)` + `require_role(..., page="design-tasks")`.
6. Время — `backend.utils.time.utcnow`; SQL — только `:param`-binding.
7. Файлы — через `validate_file_content` + MinIO (`storage.py`); пути `design/{project_id}/{task_id}/...`; отдача с проверкой `project_id`.
8. Уведомления — best-effort: сбой TG не роняет операцию; scheduler-джобы пробрасывают `asyncio.CancelledError`.
9. Права считает бэк (`permissions` в ответе деталки); фронт логику прав не дублирует.
10. `.scalars().all()` без `.limit()` запрещён; выборки доски/списка ограничены.

## §7. Передняя растяжка — эскалация

Агент **владеет** (решает сам + пишет в [DECISIONS-LOG.md](DECISIONS-LOG.md)): нейминг и индексы в рамках утверждённой модели; тексты ошибок; декомпозиция компонентов и структура файлов; тест-дизайн и фикстуры; вёрстка в рамках `.claude/rules/design.md`; retry/порядок работ внутри фазы.

Агент **эскалирует** (стоп только этой ветки, остальное продолжается): изменение словаря переходов или матрицы прав; состав/семантика колонок доски; изменение схемы БД после фриза Ф0; любая новая зависимость (npm/pip); внешне видимое поведение, расходящееся с PRD/этим чартером; всё из tripwire-списка §8.

**Литмус:** *«Изменится ли то, что видит менеджер/дизайнер, или то, что зафиксировано в PRD/чартере?»* Да → эскалация.

**Механика:** строка `ESCALATION` в STATUS.md («Блокеры / действия архитектора»): Fork · Варианты · Рекомендация агента · Что блокирует. Архитектор отвечает — агент продолжает.

## §8. Задняя растяжка — tripwire + подпись архитектора

**Не мёржится в dev без явного ok архитектора** (изменения в): `migrations/**` · `backend/models/**` · `backend/schemas/**` (после Ф0) · `backend/rbac.py` · `backend/cache.py` · `backend/main.py` · любые файлы вне зоны модуля. Worktree-teammates эти пути **не трогают вообще** — находки передают эскалацией.

`git push` и деплой — только человек (правило CLAUDE.md, здесь лишь ссылка).

**Подпись архитектора** (аналог founder_signature, колонка в STATUS.md):
- **Ф0 и Ф2** — подпись ДО мержа (схема БД и API-контракт — самое дорогое в откате);
- **Ф7** — финальная подпись перед ship;
- остальные фазы — автозакрытие по зелёным гейтам, подпись постфактум.

## §9. Evidence-протокол

Фаза закрыта только при наличии (фиксируется в STATUS.md: дата + commit-sha + чем подтверждено):

1. Транскрипт `test-runner` с зелёным прогоном целевых гейтов спека (точные команды — в Exit-gate каждого спека).
2. Для фаз с миграциями: `alembic upgrade head && alembic downgrade -1 && alembic upgrade head` чисто.
3. Для фронт-фаз: `npx tsc --noEmit` + vitest + прохождение сценария в браузере (skill `webapp-testing`).
4. `bash scripts/check_conventions.sh` без нарушений.

Невозможность прогнать гейт (нет окружения/ключей) — НЕ тихий скип: явная запись `evidence_gap: <что> / <почему> / <что нужно>` в STATUS.md, фаза остаётся открытой до решения архитектора.

## §10. Оркестрация и параллелизм

- **Хребет (Ф0→Ф1→Ф2)** — последовательно, lead-сессия, коммиты в ветку модуля.
- **После фриза контракта (Ф2)** — фан-аут worktree-teammates: `tm-frontend` (Ф3→Ф5, зона `frontend-react/`) ‖ `tm-backend` (Ф4→Ф6, зона `backend/services/`, `backend/routers/`, `backend/scheduler/`, `tests/`). Зоны не пересекаются; teammate'ам в промпт: относительные пути, types-first при касании API, `git status` в финальном отчёте, долгое — `run_in_background`.
- Read-only фан-аут (`/review`, Explore) — всегда параллельно, без запроса.
- Мержи веток teammates — только через lead, по одному, с прогоном гейтов между.
- Один активный phase-spec на исполнителя; ре-скоуп фазы — только через эскалацию.

## §11. Форматы артефактов

**Phase-spec** (`phases/F<N>-<slug>.md`):

```markdown
---
phase: F2 · title · status: planned|active|done
tier: 3
depends_on: [F1]
executors: [lead]              # lead | tm-backend | tm-frontend
reviewers: [api-designer, security-reviewer, code-reviewer]
donors: [точные пути файлов-образцов]
prd_refs: [PRD v4 §4, §7]
---
<!-- HEAD-SUMMARY: 1–2 строки -->
## Goal
## In scope / Out of scope   (out — со стрелками «→ Fn» / «→ потом»)
## Работы                    (файл → что именно, с точными именами)
## AC                        (AC-1..AC-7, машинно-проверяемые)
## Exit-gate                 (таблица порогов + evidence-команды)
## Hints                     (порядок, ловушки, доноры)
```

**Запись DECISIONS-LOG** (append-only):

```markdown
### <ISO-ts> | F<N> | arch|impl
- Fork: <одна строка>
- Decision: <что решили>
- Rationale: <почему>
- Reversibility: reversible | hard-to-reverse
```

**Строка STATUS** (таблица «Прогресс»): `| Ф<N> | статус | дата | commit | evidence | подпись |`, статусы: ⏳ planned · 🔨 active · 🟢 done-unsigned · ✅ signed.

## §12. Что модуль сознательно НЕ делает (PRD §8 + технические)

Публикация комплекта в WB-витрину (`X-Photo-Number="1"` — техблок) → отдельный проект · портал подрядчиков (аутсорс — только флаг) → потом · автоподсказки «какие карточки переделать» → потом · деньги/счета — остаются в заявках на оплату (стык `PaymentRequestCategory.DESIGN` готов) → потом · оценка в часах — никогда · items-список артикулов → потом (Р2) · touch-доска/@dnd-kit → потом (Р8) · кэширование списков → потом (Р10).
