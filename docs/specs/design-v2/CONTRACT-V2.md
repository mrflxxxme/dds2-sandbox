# CONTRACT-V2 — HTTP-контракт правок модуля «Дизайн карточек»

<!-- HEAD-SUMMARY: точный контракт всех новых и изменённых ручек волн A–D. Аддитивен к FROZEN ../design/CONTRACT.md: существующие тела, коды и тексты не меняются. Источник правды для types-first: фронт пишется по этому файлу. -->

**Версия:** 1.0 · **Дата:** 2026-08-19 · **Статус:** заморожен на старте волны A

Префикс всех путей — `/api/v1/design-tasks`. Скоуп проекта — заголовок `X-Project-Id`
(кроме унаследованного `GET /all-projects`). Тонкая проверка lead/автор/исполнитель — в сервисе.

### Минимальная роль по каждой ручке v2

Двухуровневая схема v1 сохраняется: грубый HTTP-гейт `require_role(...)` + тонкая проверка в сервисе.
Ниже — гейт для **каждой** новой и изменённой ручки, догадываться не нужно.

| Ручка | `require_role` | `rate_limit_write` | Тонкая проверка в сервисе |
|---|---|---|---|
| `GET /calendar` (изменена) | `viewer` | нет | — |
| `PUT /{task_id}` (изменена) | `editor` | да | lead для поля `number` |
| `GET /refs/*` | `viewer` | нет | — |
| `POST/PUT/DELETE /refs/*` | `editor` | да | **lead** (иначе 403) |
| `PUT /{task_id}/labels` | `editor` | да | lead \| автор \| исполнитель |
| `PUT /{task_id}/attributes` | `editor` | да | lead \| автор \| исполнитель + не терминал |
| `POST /bulk/*` | `editor` | да | по каждой задаче отдельно |
| `GET /stats`, `/stats/by-assignee`, `/stats/funnel`, `/stats/by-attribute` | `viewer` | нет | — |
| `GET /stats/export.xlsx` | `viewer` | нет | — |
| `GET /dashboard/layout` | `viewer` | нет | — |
| `PUT /dashboard/layout` | **`viewer`** | да | только своя раскладка (`user_id` из сессии) |

**`PUT /dashboard/layout` — единственная write-ручка модуля с гейтом `viewer`.** Это осознанно:
Р32 даёт `viewer`-руководителю дашборд, а дашборд без права сохранить свою раскладку бесполезен.
Ручка не пишет данных проекта — только персональную настройку интерфейса, скоупленную
`user_id` из сессии, поэтому `editor` для неё избыточен. `rate_limit_write` при этом остаётся.
`user_id` **никогда** не берётся из тела запроса — только из сессии (иначе один пользователь
перезапишет раскладку другому).

**Порядок объявления в роутере:** все статические пути (`refs/*`, `bulk/*`, `stats/*`,
`dashboard/*`) объявляются **ДО** `/{task_id}` — FastAPI матчит по порядку.

⚠️ Существующий тест это **не поймает**: в репо есть только `test_board_not_captured_by_task_id`,
и он проверяет единственный путь `/board`. Поэтому каждая волна, добавляющая статический путь,
**обязана** добавить свой аналогичный тест (`refs`, `bulk`, `stats`, `dashboard` — по одному
на префикс); без него ошибка порядка проявится как 422 «task_id должен быть int» в рантайме.

## §1. Волна A — календарь с произвольным диапазоном

### `GET /calendar` (изменена, аддитивно)

| Параметр | Тип | Было | Стало |
|---|---|---|---|
| `month` | `str` `YYYY-MM` | обязательный | опциональный, поведение прежнее |
| `date_from` | `date` | — | опциональный |
| `date_to` | `date` | — | опциональный |

Правила:
- ни один параметр не передан → `month` = текущий месяц (сегодня по МСК);
- `month` вместе с `date_from`/`date_to` → **400** `«Укажите либо month, либо диапазон дат»`;
- `date_from` без `date_to` или наоборот → **400** `«Укажите обе границы диапазона»`;
- `date_from > date_to` → **400** `«Начало диапазона позже конца»`;
- диапазон длиннее **400 дней** → **400** `«Диапазон не больше 400 дней»`.

**Окно выборки и cap:**
- фактическое окно выборки шире запрошенного на **±6 дней** с каждой стороны — календарь
  дорисовывает недели соседних месяцев (унаследовано из v1, где окно было
  `[1-е число − 6 дн; последний день + 6 дн]`);
- cap: **500** задач в режиме `month` (как в v1, не меняется), **2000** в режиме диапазона;
- при усечении ответ несёт `truncated: true` — тихое усечение запрещено.

Тело ответа `DesignCalendarOut` сейчас — `{month, date_from, date_to, tasks}`, где `date_from`/`date_to`
это **границы фактического окна выборки** (с уже применённым расширением ±6 дней).
Волна A добавляет **одно аддитивное поле** `truncated: bool = false`; остальные поля сохраняют
и имена, и смысл. При диапазоне `month` содержит месяц `date_from` запроса.
Фронт раскладывает задачи по `tasks[].due_date`, а не по `month`.

Совместимость: старый вызов `GET /calendar?month=2026-08` работает байт-в-байт как раньше —
это закрепляется регресс-тестом.

## §2. Волна B — редактируемый номер

### `PUT /{task_id}` (изменена, аддитивно)

Тело `DesignTaskUpdate` получает поле:

```
number: str | None = None      # None = не менять
```

Валидация (Р18, порядок проверок ровно такой):

| Проверка | Ошибка |
|---|---|
| не lead | **403** `«Номер заявки меняет только ведущий дизайнер»` |
| статус ACCEPTED или CANCELLED (даже у lead) | **403** `«Номер закрытой задачи не меняется»` |
| после `strip()` пусто | **400** `«Номер не может быть пустым»` |
| длина > 40 | **400** `«Номер длиннее 40 символов»` |
| не совпал с `^[A-Za-zА-Яа-яЁё0-9._-]+$` | **400** `«Номер: только буквы, цифры, дефис, точка и подчёркивание»` |
| номер занят живой задачей проекта | **400** `«Номер уже занят»` |

Нормализация перед проверками: `strip()`. Внутренних пробелов формат не допускает.
Успех → **200**, полный `DesignTaskDetail` (как у остальных write-ручек задачи).

### Флаг прав

`DesignTaskPermissions` получает `can_edit_number: bool` (после `can_edit`).
Правило: `is_lead and status not in (ACCEPTED, CANCELLED)`.

## §3. Волна C — справочники, метки, реквизиты

### Справочник меток

```
GET    /refs/labels                       → DesignLabelOut[]
POST   /refs/labels                       → DesignLabelOut            201
PUT    /refs/labels/{label_id}            → DesignLabelOut            200
DELETE /refs/labels/{label_id}            → 204   (архивирование, Р30)
```

`DesignLabelOut`: `{id, name, color, sort_order, is_archived, usage_count}`
(`usage_count` — число задач с этой меткой сейчас; считается одним GROUP BY на список, не per-row).

`DesignLabelIn`: `{name: str 1..60, color: LabelColor, sort_order: int = 0}`
`LabelColor` — строковый enum ровно из 10 значений:
`red | orange | amber | green | teal | blue | violet | pink | brown | slate`.

`GET` отдаёт по умолчанию только активные; `?include_archived=true` — все.

### Справочник реквизитов

```
GET    /refs/attributes                          → DesignAttributeOut[]   (со вложенными values)
POST   /refs/attributes                          → DesignAttributeOut     201
PUT    /refs/attributes/{attribute_id}           → DesignAttributeOut     200
DELETE /refs/attributes/{attribute_id}           → 204  (архивирование вместе со значениями)
POST   /refs/attributes/{attribute_id}/values    → DesignAttributeValueOut 201
PUT    /refs/values/{value_id}                   → DesignAttributeValueOut 200
DELETE /refs/values/{value_id}                   → 204  (архивирование)
```

`DesignAttributeOut`: `{id, name, is_multi, sort_order, is_archived, usage_count, values: DesignAttributeValueOut[]}`
(`usage_count` поля = число задач, у которых выбрано **любое** его значение; нужен UI для
предупреждения «Используется в N задачах» при архивировании поля целиком)
`DesignAttributeValueOut`: `{id, attribute_id, value, sort_order, is_archived, usage_count}`
`DesignAttributeIn`: `{name: str 1..60, is_multi: bool = false, sort_order: int = 0}`
`DesignAttributeValueIn`: `{value: str 1..120, sort_order: int = 0}`

Общие правила справочников:
- запись — **только lead** → иначе **403** `«Справочник ведёт ведущий дизайнер»`;
- чтение — любой с page-ключом;
- **`?include_archived`** (bool, default `false`) действует одинаково на `GET /refs/labels` и
  `GET /refs/attributes`; у второй он фильтрует **и вложенные `values`**: при `false` не
  возвращаются ни архивные поля, ни архивные значения внутри активных полей;
- **повторный `DELETE` уже архивной записи → 204**, состояние не меняется (идемпотентность);
- архивирование поля архивирует **все его значения** каскадом; разархивирования в v2 нет
  (понадобится — заводится заново);
- дубль имени/значения среди активных → **400** `«Такое название уже есть»` / `«Такое значение уже есть»`;
- не найдено → **404** `«Метка не найдена»` / `«Поле не найдено»` / `«Значение не найдено»`
  (эти три текста добавляются в `_NOT_FOUND_TEXTS` роутера);
- cap: 200 полей, 500 значений на поле, 100 меток на проект → **400** `«Достигнут предел справочника»`.

### Назначение на задачу

```
PUT /{task_id}/labels        { label_ids: int[] }   → DesignTaskDetail
PUT /{task_id}/attributes    { value_ids: int[] }   → DesignTaskDetail
```

Семантика — **replace набора** (не add/remove): что передали, то и стало.
Пустой массив = снять всё. Идемпотентно: повторный вызов с тем же набором не пишет событий.

| Проверка | Ошибка |
|---|---|
| не lead / не автор / не исполнитель (Р29) | **403** `«Метки ставит ведущий, автор или исполнитель»` (для реквизитов — `«Реквизиты ставит ведущий, автор или исполнитель»`) |
| реквизиты у задачи в ACCEPTED/CANCELLED (Р31) | **400** `«Реквизиты закрытой задачи не меняются»` |
| id чужого проекта или несуществующий | **404** `«Метка не найдена»` / `«Значение не найдено»` |
| архивная метка/значение в наборе, которой не было на задаче | **400** `«Метка в архиве»` / `«Значение в архиве»` |
| два значения одного поля при `is_multi = false` | **400** `«Поле «{name}» допускает одно значение»` |

Метки в терминальных статусах менять **можно** (Р31) — гварда нет.

### Массовое проставление (Р33)

```
POST /bulk/labels       { task_ids: int[], label_ids: int[], mode: "add" | "remove" }  → BulkResultOut
POST /bulk/attributes   { task_ids: int[], value_ids: int[], mode: "add" | "remove" }  → BulkResultOut
```

Успех → **200** (даже если часть задач не обработана — это не ошибка вызова).
`BulkResultOut`: `{updated: int, skipped: int, errors: [{task_id, message}]}`

Отличие от `PUT /{id}/labels`: здесь `add`/`remove`, а не replace — пачкой проставляют
недостающее, не затирая чужую разметку. Cap: 500 задач за вызов → **400** `«Не больше 500 задач за раз»`
(единственная ошибка, роняющая весь вызов; проверяется до обработки).

Поведение по каждой задаче — ровно так:

| Ситуация | Куда попадает | Что в `message` |
|---|---|---|
| применено | `updated` | — |
| набор уже такой (`add` того, что есть; `remove` того, чего нет) | `updated` | — (идемпотентно, событий не пишем) |
| нет прав на эту задачу (Р29) | `skipped` | — |
| реквизиты у задачи в ACCEPTED/CANCELLED (Р31) | `errors` | «Реквизиты закрытой задачи не меняются» |
| `mode:"add"` даёт второе значение поля с `is_multi = false` | `errors` | «Поле «{name}» допускает одно значение» |
| задача не найдена или чужого проекта | `errors` | «Задача не найдена» |

`skipped` — **только** «нет прав»; всё остальное, что не применилось, идёт в `errors` с текстом
гварда. Метки в терминальных статусах ошибкой не являются (Р31).

### Расширение существующих ответов

`DesignTaskListItem` и `DesignTaskDetail` получают:

```
labels:     [{id, name, color}]                                    # текущие, порядок по sort_order
attributes: [{attribute_id, attribute_name, value_id, value}]      # порядок по sort_order поля
```

`DesignTaskDetail` дополнительно:

```
label_history: [{label_id, name, color, times: int}]               # Р20: «была с меткой N раз»
```

`DesignTaskPermissions` получает три флага:

```
can_set_labels:     is_lead or is_author or is_assignee                        # терминалы разрешены (Р31)
can_set_attributes: (is_lead or is_author or is_assignee) and not terminal     # терминалы запрещены (Р31)
can_manage_refs:    is_lead                                                    # показывает вкладку «Настройки»
```

`can_manage_refs` дополнительно отдаётся в `DesignBoardPermissions` (ответ `GET /board`) —
вкладка «Настройки» рисуется до открытия любой задачи.

Паритет схем и сервиса ловят **два** существующих теста, оба обязаны остаться зелёными:
`test_permissions_schema_matches_service` (флаги задачи) и
`test_board_permissions_schema_matches_service` (флаги доски). Забыл зеркалить флаг — упадёт тест.

Загрузка меток/реквизитов для списков — **батчем** (один `IN`-запрос на страницу), не per-task:
N+1 запрещён инвариантом v1 §6.10 и проверяется в AC волны C.

**`GET /board` и `GET ""` новых фильтрующих параметров НЕ получают** (Р21 — фильтрация клиентская).

## §4. Волна D — аналитика

### Окно периода — общее правило для всех ручек статистики

`date_from` и `date_to` (тип `date`) действуют одинаково у `GET /stats` (унаследована),
всех трёх разрезов и выгрузки:

- оба опциональны; **не передан ни один → последние 30 дней включительно**
  (`date_from = сегодня − 29 дней`, `date_to = сегодня`, по МСК — то же окно, что показывала `StatsPanel`);
- передан только `date_from` → `date_to = сегодня` (**поведение v1 сохраняется дословно**);
- передан только `date_to` → **400** `«Укажите обе границы диапазона»`;
- `date_from > date_to` → **400** `«Начало диапазона позже конца»`;
- окно длиннее **400 дней** → **400** `«Диапазон не больше 400 дней»`.

Тексты намеренно те же, что у `GET /calendar` (§1) — один набор на модуль, синонимы не плодим.

**Почему правило мягче календарного.** У `GET /calendar` пара `date_from`/`date_to` новая, там
допустима строгость «обе или ни одной». У `GET /stats` одиночный `date_from` — существующий
рабочий вызов (`StatsPanel` шлёт именно его), и запрет сломал бы FROZEN-контракт v1.
Все изменения v2 остаются **аддитивными**: ни один существующий вызов модуля не меняет ответ.
Закрепляется регресс-тестом «`GET /stats?date_from=X` до и после волны D даёт идентичный ответ».

### Разрезы

```
GET /stats/by-assignee?date_from&date_to   → DesignStatsByAssigneeOut
GET /stats/funnel?date_from&date_to        → DesignStatsFunnelOut
GET /stats/by-attribute?date_from&date_to  → DesignStatsByAttributeOut
```

```
DesignStatsByAssigneeOut  {rows: [{user_id: int, name: str, active: int, accepted: int,
                                   on_time_share: float|null, avg_cycle_days: float|null,
                                   avg_versions: float|null}], truncated: bool}
DesignStatsFunnelOut      {rows: [{status: str, count: int, avg_days_in_status: float|null}]}
DesignStatsByAttributeOut {attributes: [{attribute_id, attribute_name,
                                         rows: [{value_id: int|null, value: str, count: int}]}],
                           labels: [{label_id, name, color, count}], truncated: bool}
```

- `user_id` — тот же `users.id`, что в `assignee_user_id` задачи; `name` — display-имя,
  зеркальное бэковому `_user_names` (донор v1, календарь красится по нему же).
- `active` — число задач исполнителя в `DESIGN_ACTIVE_STATUSES` **на момент запроса** (снимок,
  окно на него не влияет — как `unassigned_over_2d` в v1). Именно по нему сверяются с `GET /workload`.
- `rows` воронки — ровно шесть статусов доски в этом порядке:
  `NEW · ASSIGNED · IN_PROGRESS · REVIEW · REVISION · ACCEPTED`
  (= константа `DESIGN_BOARD_STATUSES` v1). `ON_HOLD` и `CANCELLED` в воронку **не входят** —
  они вне доски. `count` — снимок текущего состояния, `avg_days_in_status` — за окно периода.
- «Активные статусы» для просрочки и `active` — константа `DESIGN_ACTIVE_STATUSES` v1
  (пять штук, без `ON_HOLD` и терминалов); своего списка не заводить.
- `value_id: null` + `value: "Без значения"` — задачи, где поле не заполнено (Р33).

**Cap'ы и усечение:** `by-assignee` — 200 строк, `by-attribute` — 50 полей × 200 значений и
100 меток; при усечении соответствующий ответ несёт `truncated: true`, и фронт показывает
строку «показаны не все». Воронка cap не имеет (всегда 6 строк).

Общее с существующим `GET /stats` (семантика не меняется):
- `None` = «нет данных» (пустой знаменатель), не `0`;
- окно режет по `accepted_at` для метрик приёмки, по `created_at` для входных;
- задачи без значения реквизита попадают в строку `{value_id: null, value: "Без значения"}` (Р33);
- архивные метки/значения из выдачи **не исключаются** (Р30 — история не должна ломаться).

### Раскладка дашборда (Р23)

```
GET /dashboard/layout   → DesignDashboardLayoutOut
PUT /dashboard/layout   { widgets: [{id: str, visible: bool, order: int}] }  → DesignDashboardLayoutOut
```

`DesignDashboardLayoutOut`: `{widgets: [{id: str, visible: bool, order: int}], is_default: bool}`

Персонально на пользователя × проект (`user_id` — из сессии, не из тела).
`GET` без сохранённой раскладки отдаёт дефолт — все виджеты видимы, порядок = порядок
объявления ниже — с `is_default: true`; после первого `PUT` — `is_default: false`.

Известные `id` и их порядок по умолчанию: `metrics` · `by_assignee` · `funnel` · `by_attribute`.

Валидация тела `PUT` (набор **полный и точный**, частичные апдейты не поддерживаются):

| Ситуация | Ответ |
|---|---|
| неизвестный `id` | **400** `«Неизвестный виджет: {id}»` |
| `id` повторяется | **400** `«Виджет повторяется: {id}»` |
| известный `id` отсутствует в наборе | **400** `«Не хватает виджета: {id}»` |

Полный набор требуется намеренно: иначе появление нового виджета в следующей версии
молча оставляло бы его скрытым у всех, кто хоть раз сохранял раскладку.
`order` — любые целые, важен только их относительный порядок; сервер нормализует к `0..N-1`.

### Выгрузка

```
GET /stats/export.xlsx?date_from&date_to   → 200 application/vnd.openxmlformats-officedocument.spreadsheetml.sheet
```

Read-ручка: без `rate_limit_write`, доступ — всем с page-ключом (Р32).
Отдаётся обычным `Response` через существующий хелпер `_attachment()` модуля — **не**
`StreamingResponse` (файл собирается openpyxl целиком в память, как у донора `problem_digest_xlsx`).
Заголовки — как у остальных файловых ручек модуля:
`Content-Disposition: attachment; filename*=UTF-8''<имя>` и `X-Content-Type-Options: nosniff`.
Имя файла: `design-tasks_<date_from>_<date_to>.xlsx`, где границы — **разрешённые** значения окна
(то есть при отсутствии параметров подставляются дефолтные последние 30 дней, а не пустые строки).

Листы:
1. **«Сводка»** — 6 метрик PRD §10, разрез по исполнителям, воронка, разрезы по реквизитам и меткам;
2. **«Задачи»** — по строке на задачу: номер · название · тип · сложность · срочно · исполнитель ·
   автор · срок · статус · версий · метки · далее по колонке на каждое **активное** поле-реквизит
   (в порядке `sort_order`) · создано · принято.

Формат ячеек-множеств: метки и значения `is_multi`-полей — **через запятую с пробелом**
(`«Срочно, Переделка»`), пустое множество — пустая ячейка (не «—», чтобы не мешать фильтрам Excel).
Колонок реквизитов — не более **50** (первые по `sort_order`); если полей больше, в «Сводке»
появляется строка `«Показаны первые 50 полей-реквизитов из N»`. Архивные поля в колонки не выносятся,
но их значения на старых задачах попадают в выгрузку, если поле активно.

Cap листа «Задачи» — 5000 строк. При усечении в «Сводке» появляется явная строка
`«Показано 5000 из N задач — сузьте период»` (тихое усечение запрещено).

## §5. Сводная таблица кодов

| Код | Когда |
|---|---|
| 200 | успешное чтение, все `PUT` и `POST /bulk/*` (в т.ч. с непустыми `skipped`/`errors`) |
| 201 | создание записи справочника |
| 204 | архивирование записи справочника (включая повторный `DELETE` уже архивной) |
| 400 | нарушение любого гварда из таблиц выше (`ValueError` сервиса) |
| 403 | нет права (`PermissionError` сервиса) |
| 404 | тексты из `_NOT_FOUND_TEXTS`: «Задача не найдена», «Версия сдачи не найдена», «Метка не найдена», «Поле не найдено», «Значение не найдено» |
| 413 | превышение размеров файлов (унаследовано, в v2 не изменяется) |
| 502 | `WbContentError` (унаследовано, в v2 не изменяется) |
