## §3. Роадмап волн

```
A (UI + календарь) ──► B (номер) ──► C (метки + реквизиты) ──► D (Аналитика)
  T3, фронт + 1 ручка    T3, узкий      T3, полный слой         T3, полный слой
```

| Волна | Название | Зависит | Tier | Исполнитель | Exit одной строкой |
|---|---|---|---|---|---|
| A | Иконка · «Все бренды» · фильтры доски · `PeriodPicker` · двухмесячный календарь · тултипы | — | T3 | lead (ручка `/calendar`) + tm-frontend | tsc+vitest зелёные, чек-лист A в браузере, PR-A замержен |
| B | Редактируемый номер заявки | — | T3 | lead | миграция up/down/up; тесты прав, уникальности и гонки; PR-B |
| C | Метки + справочник реквизитов + массовое проставление | B | T3 | lead (хребет) → tm-frontend | миграции чисты; сценарий «завести бренд → проставить → отфильтровать» E2E; PR-C |
| D | Вкладка «Аналитика» + XLSX + персистенс раскладки | C | T3 | lead (бэк) → tm-frontend | виджеты сходятся с фактом; XLSX открывается; PR-D |

Все волны T3 — каждая трогает бэк. Состав ревьюеров — в шапке phase-spec.

**Волны исполняются строго последовательно**, параллельного старта нет ни у одной пары.
A и B выглядят независимыми по смыслу, но обе правят `EditTaskModal.tsx` (A — поле срока
через `PeriodPicker`, B — поле номера), поэтому B начинается **после мержа PR-A**. C и D
зависят содержательно (D считает разрезы по сущностям C). Порядок мержа: A→B→C→D.

## §4. Наследование v1 и общие правила для всех волн

- **Цикл фазы** — v1 §4 (Scope → Implement → Verify → Review → Close), TDD: падающий тест первым.
- **Порядок работ** — Model → Migration → Schema → Service → Router → Test → UI. Фан-аут на
  `tm-frontend` — только ПОСЛЕ мержа бэк-хребта волны (types-first).
- **Инварианты** — v1 §6 все 10. Новые таблицы обязаны повторить паттерн изоляции:
  `UniqueConstraint(id, project_id)` на родителе + составной FK `(child_id, project_id)` с `ON DELETE CASCADE`.
- **Кэш** — Р10 v1 действует: `@cached` не добавляется нигде, включая справочники и статистику.
- **Контракт** — `../design/CONTRACT.md` остаётся FROZEN; все изменения волн описаны в
  [CONTRACT-V2.md](CONTRACT-V2.md) и **только аддитивны**: существующие тела, коды и тексты не меняются.
- **Тексты ошибок — часть контракта.** Все новые тексты перечислены в CONTRACT-V2 §6; менять их = менять API.
- **Маппинг ошибок** — существующий хелпер `_svc`: `PermissionError → 403`, `ValueError → 400`,
  кроме текстов из `_NOT_FOUND_TEXTS` → 404. Новые «не найдено»-тексты добавляются в этот frozenset явно.
- **Write-ручки** — `Depends(rate_limit_write)` + `require_role(..., page="design-tasks")`.
- **Права считает бэк** (§6.9 v1): каждый новый флаг живёт в `compute_permissions` и зеркалится
  в `DesignTaskPermissions` — паритет ловит существующий `test_permissions_schema_matches_service`.
- **Растяжки** — v1 §7–§8. Tripwire (`migrations/**`, `models/**`, `schemas/**`, `rbac.py`,
  `cache.py`, `main.py`) правит только lead; сюда же в v2 добавляется `frontend-react/src/app/globals.css`
  (Р26 — общий файл, задевает весь фронт).
- **Evidence** — v1 §9: транскрипт `test-runner`; для волн с миграциями цикл
  `alembic upgrade head && downgrade -1 && upgrade head`; для фронт-частей `tsc --noEmit` + vitest + браузер.
- **Новые зависимости** — нет ни одной. `date-fns`, `react-day-picker`, `openpyxl` уже в deps;
  drag — нативный HTML5 (Р8 v1). Любая новая зависимость = эскалация.

## §5. Что v2 сознательно НЕ делает

Полный конструктор виджетов (metabase-like) → потом · PDF-отчёты → потом ·
виджет «динамика по неделям» → потом (владелец отложил 2026-08-19) ·
удаление ручки `GET /all-projects` → потом (Р19) · глобальный кросс-проектный справочник → потом ·
серверная фильтрация доски → потом (Р21: клиентской хватает при 60+ задачах/мес) ·
общая на проект раскладка дашборда → потом (Р23: раскладка персональная) ·
произвольный hex-цвет метки → никогда (Р26 ломает тёмную тему) ·
жёсткое удаление из справочников → никогда (Р30 архивирование).
