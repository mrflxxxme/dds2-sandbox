# DOMAIN_ASSEMBLY — Заявки на сборку + Лист логиста

Промежуточный слой между складом фулфилмента и отгрузкой FBO-поставок WB.
`WbFboSupply` (1:1) → `AssemblyRequest` → при SHIPPED создаёт `OutboundShipment`.

## Таблицы
| Модель | Назначение | Ключ / constraint |
|--------|------------|-------------------|
| `AssemblyRequest` | Заявка на сборку (статус, FBO-привязка, vehicle/pallet поля) | `models/assembly.py` |
| `AssemblyRequestItem` | Позиция заявки (barcode, qty) | FK на request |
| `AssemblyStatusHistory` | История смен статуса | FK на request |
| `AssemblyDraft` | Черновик распределения N×M (`distribution` JSONB), SoftDelete | `models/assembly.py` |
| `OutboundShipment` / `OutboundShipmentItem` | Отгрузка, создаётся при SHIPPED | `models/warehouse.py` |

`PackageType` = `BOX | MONOPALLET | SUPERSAFE`. Один `AssemblyRequest` = одна транспортная единица WB = один `package_type`; тип определяется через `POST /warehouse/acceptance-check` (см. `DOMAIN_WAREHOUSE.md`).

## Бизнес-правила
- **Статусная модель:** `IN_PROGRESS → READY → VEHICLE_ASSIGNED → SHIPPED → DELIVERED`. Строго последовательная, пропуск запрещён. Допустимые откаты: `READY → IN_PROGRESS` (`start_assembly`, сбрасывает `actual_ready_date`), `VEHICLE_ASSIGNED → READY` (`unassign_vehicle`), `SHIPPED → READY` (cancel). `CANCELLED` — из любого статуса. **`CLOSED` («Закрыт»)** — терминальный статус возврата: `SHIPPED/DELIVERED → CLOSED` (`return_to_warehouse`), когда WB не принял поставку и товар вернулся; в отличие от `CANCELLED`, логистика заявки сохраняется.
- **PENDING — legacy:** остаётся в enum для совместимости со `status_history`, но активных заявок в нём быть не должно. Новые заявки создаются сразу в `IN_PROGRESS`. `start_assembly` идемпотентен (повторный клик в IN_PROGRESS = no-op).
- **Валидация остатков** при create/update (PENDING/IN_PROGRESS) и `start_assembly`: `available = warehouse_stock.quantity − reserved_by_other_active_requests`, где reserved — сумма позиций по этому товару в других активных заявках (PENDING/IN_PROGRESS/READY/VEHICLE_ASSIGNED). Нехватка → `ValueError` с детализацией по баркодам. См. `_validate_available_for_assembly()` в `services/assembly/crud.py`.
- **При Ship (VEHICLE_ASSIGNED → SHIPPED):** валидация stock ≥ need; списание stock (`OUTBOUND`, `reference_type="ASSEMBLY"`); создаётся `OutboundShipment(SHIPPED)` + items; проставляются взаимные `outbound_shipment_id` на request и `WbFboSupply`; `shipped_at = utcnow()`.
- **При Cancel SHIPPED:** возврат stock (`reference_type="ASSEMBLY_CANCEL"`); `WbFboSupply.outbound_shipment_id = NULL`; `OutboundShipment.soft_delete()`; статус → READY.
- **При Return (`return_to_warehouse`, `POST /{id}/return`, SHIPPED/DELIVERED → CLOSED):** WB не принял поставку, товар вернулся на склад-источник. Создаётся `InboundReceipt(ACCEPTED)` «Возврат по заявке ASM-…» → товар возвращается ГОДНЫМ стоком (`MovementType.INBOUND`, `reference_type="RECEIPT"`). В отличие от Cancel: заявка НЕ отменяется (статус `CLOSED`), `OutboundShipment` НЕ удаляется, `pickup_cost` сохраняется → логистика остаётся в аналитике. Связанная `WbFboSupply` помечается `return_processed_at`/`return_type=GOODS`/`return_qty` (если ещё не обработана) — уходит из «недоприёмки», двойного возврата не будет. Партиальная недоприёмка (WB принял часть) — отдельный flow `process_fbo_return` (см. `DOMAIN_WAREHOUSE`/`fbo_supply`), кнопка возврата заявки рассчитана на полный возврат.
- **Редактирование:** items — только до READY (заблокировано в SHIPPED/DELIVERED/CLOSED/CANCELLED). FBO-поставка — менять можно только до отгрузки и только при реальной смене (передача той же поставки в payload — no-op, не падает). Мета-поля (`pallets_count`, `pallet_weight_kg`, `comment`, `estimated_ready_date`, `wb_warehouse_name_manual`, `package_type`) и логистика (`pickup_cost`, `vehicle_*`, `driver_phone`) — в любом статусе кроме CANCELLED, включая SHIPPED/DELIVERED/CLOSED (inline edit + страница редактирования; остатки не двигаются). **Склад-источник (`warehouse_id`)** — меняется в любом статусе до отгрузки (не SHIPPED/DELIVERED/CANCELLED); новый склад проверяется на существование и тип FULFILLMENT, сток ре-валидируется на нём только в PENDING/IN_PROGRESS (в READY/VEHICLE_ASSIGNED — без сверки, как и items, подгон под факт WB). UI: `<select>` на странице редактирования заявки.
- **AssemblyDraft (N×M):** черновик с экрана «Потребность по складам». Матрица `ФФ-источники × WB-целевые`, юзер балансирует Σ src ↔ Σ tgt по каждой строке. `commit_draft`: per-row валидация `Σ src == Σ tgt > 0` (иначе 400); pro-rata распределение в пары (largest-remainder для целочисленности); создаёт N `AssemblyRequest(IN_PROGRESS)` — по одной на уникальную пару `(source_ff, target_wb, package_type)` с qty>0 (новинки и обычные на один склад — В ОДНОЙ заявке; если в ней есть товар-новинка, `comment` получает префикс `NEWCOMER_COMMENT_PREFIX`). Atomic: исключение → rollback всех созданных, draft остаётся; успех → soft-delete draft.
- **Объединение черновиков (`merge_drafts`, `POST /merge`):** когда несколько черновиков отправляют товар по одному маршруту `(ff → wb)`, они создадут раздельные отправки на ФФ. `merge_drafts` сливает список черновиков в один. Survivor = черновик с наибольшим числом строк (tie-break: наименьший id); остальные soft-delete. Строки объединяются по ключу `(nm_id, package_type)` — src/tgt суммируются поэлементно. `handed_units` переносятся в survivor (ключ `(source_ff, target_wb, package_type)`; позиции суммируются по баркоду, статус `handed` побеждает `draft`). `cold_start_shares` сбрасывается (юзер запускает авто-баланс заново). После merge → редирект на `distribute/preview?draft=<id>&pkg=BOX`.
- **Партиальный commit_draft по упаковке:** `package_type` (BOX/MONOPALLET — короб/моно). **Срез упаковки = вкладка UI, а не точный тип:** `package_type=BOX` («Короб») коммитит ВСЁ, кроме MONOPALLET — т.е. BOX И SUPERSAFE (каждая заявка сохраняет свой реальный тип); `MONOPALLET` — только моно (`_pkg_selected`). Иначе SUPERSAFE-строки молча оставались бы в черновике. Всё не выбранное остаётся в `rows` черновика для следующих сборок; если осталось что-то ИЛИ есть `handed_units` — draft не удаляется. **Новинки НЕ разделяются** на отдельные заявки: новинка — производный признак товара (`fetch_newcomer_nm_ids`), а не ось группировки; если в заявку `(ff, wb, pkg)` попал хоть один товар-новинка, её `comment` получает префикс `NEWCOMER_COMMENT_PREFIX`.
- **Жизненный цикл заявки-юнита** (`distribute` → «передан на ФФ» → «в сборке»). «Заявка-юнит» = ключ `(source_ff × target_wb × package_type)` — новинки и обычные товары на один склад в ОДНОМ юните. Состояния: **auto** (живёт в `rows`) → **draft** (ручная правка, `set_unit_items`, status=`draft`, ещё в `handed_units`) → **handed** (`hand_off_unit`, status=`handed`, заморожен) → **committed** (`AssemblyRequest`). Все lifecycle-функции нормализуют `handed_units` через `_normalize_handed_units` (схлопывают снимки одного ключа — для старых черновиков, где новинки/обычные были разнесены). Эндпоинты `units/*` (`assembly_draft_service`):
  - `hand_off_unit` — «передать на ФФ»: `_carve_unit_from_rows` вырезает поток ff→wb из `rows` (новинки + обычные вместе) и сливает с существующим снимком склада, если он есть (status=`handed`). Снимок не трогается правками распределения (его уже нет в `rows`).
  - `revert_unit` — «вернуть в черновик»: вливает позиции `handed`-юнита обратно в `rows`.
  - `commit_unit` — «в сборку»: создаёт один `AssemblyRequest` из снимка (требует status=`handed`, иначе 400 «сначала передайте на ФФ»), удаляет юнит; пустой draft → soft-delete.
  - `set_unit_items` — редактор наполнения: заменяет позиции (фиксирует auto-юнит как `draft`); на `handed` — 400 «правка запрещена». Проверку свободного остатка ФФ делает фронт.
  - `delete_unit` — удалить юнит целиком (товар остаётся на ФФ); на `handed` — 400 «сначала верните в черновик».
  - `move_unit` — «сменить склад WB» (UI: кнопка на `distribute/request`): перенести юнит на другой WB-целевой склад черновика. Двигается ТОЛЬКО поток этого ФФ (`ff→wb`), баланс матрицы сохраняется. Источник — авто (вырезаем из rows) или ручной черновик; на складе-получателе сливается с существующим ручным черновиком по баркоду, иначе поток возвращается в rows как `ff→new_wb`. `handed` переносить нельзя (400); перенос на тот же склад — 400.
- **Связь заявка ↔ черновик (`source_draft_id`):** `commit_unit` и `commit_draft` проставляют `AssemblyRequest.source_draft_id = draft.id`. Страница склада-источника (`distribute/ff`) показывает блок «История — в сборке» — заявки этого черновика (`GET /warehouse/assembly?draft_id=&warehouse_id=`). NULL для заявок из других путей (FBO/ручные). Заявки, созданные до миграции `asm_source_draft_id`, в инлайне не появятся (только в полном списке `/warehouse/assembly`).
- **Предпросмотр созданных (`get_created_groups`, `GET /warehouse/assembly/created-groups`):** после полного коммита черновик soft-удаляется, но созданные заявки группируются по `source_draft_id` в read-only «Созданные партии» на странице `warehouse/assembly`. Только **IN_PROGRESS**-заявки (ещё в сборке, не ушли в работу/отгрузку), кап 50 групп, свежие сверху. Имя черновика резолвится даже после его soft-delete. Это якорь для будущего мёрджа созданных заявок (заявка↔заявка / черновик→заявка по дублирующимся маршрутам).

`distribution` JSONB: `source_warehouse_ids[]`, `target_warehouse_names[]`, `rows[]` (`nm_id`, `barcode`, `vendor_code`, `src{warehouse_id:qty}`, `tgt{wb_name:qty}`, `package_type`), `cold_start_shares{wb_name:доля}|null` (cold-start авто-баланс), `handed_units[]` (замороженные снимки: `source_ff_id`, `target_wb_name`, `package_type`, `status`, `items[]`), `pallets_count`, `pallet_weight_kg`, `estimated_ready_date`.

## Зависимости
- `DOMAIN_WAREHOUSE` — `acceptance-check` определяет `package_type`; `_update_stock` / `_resolve_barcode` для движения остатков.
- `DOMAIN_REPORTS` — on-assembly заявки участвуют в Stock Forecast.
- WB API — данные FBO-поставок (`WbFboSupply`).

## Грабли
- При `commit_draft` строки группируются по `(source_ff, target_wb, package_type)` — если для одного склада нужны и короб, и моно, это разные заявки. Новинки и обычные на один склад/упаковку — ОДНА заявка (новинка лишь добавляет префикс 🆕 в `comment`).
- **Старые черновики «в полёте»:** до объединения юнитов новинки и обычные на один склад жили в РАЗНЫХ снимках `handed_units` (и могли быть переданы на ФФ раздельно). `_normalize_handed_units` (вызывается во всех lifecycle-функциях) и фронтовый `buildFfUnits` схлопывают их по ключу `(ff, wb, pkg)`. Смешанный статус (часть в снимке + часть ещё в `rows`) → карточка показывается как `черновик`; `hand_off_unit` дослаивает `rows` в снимок.
- **Carve сохраняет баланс строки:** `_carve_unit_from_rows` вычитает выделенный qty из `src` И из `tgt` на одну величину → остаток строки остаётся сбалансированным (`Σsrc == Σtgt`). При правке снимка не пересчитывать через `src/tgt` — `HandedUnit.items` уже плоский список qty.
- **SUPERSAFE и срез «Короб»:** `commit_draft?package_type=BOX` трактует «Короб» как не-MONOPALLET (`_pkg_selected`), поэтому SUPERSAFE-строки коммитятся вместе с BOX (исправлено — раньше они молча оставались в черновике). Каждая заявка сохраняет реальный `package_type`. ⚠️ Если WB заворачивает SUPERSAFE на приёмке иначе — это уже про acceptance, не про отбор.
- **Cross-type drag (distribute, фронт):** перетаскивание WB-колонки между вкладками Моно/Короб меняет `package_type` перенесённых строк — с подтверждением. Срабатывает ТОЛЬКО если цель однотипна (`onlyMono`/`onlyBox`); смешанная цель → обычный merge без смены типа. Колонки с нулём в текущем типе показывают вторичный счётчик (📦/📐) — подсказка куда тащить. Типы определяются по `allRows` (все строки, не только видимые во вкладке).
- Аналитика логистики (`GET /warehouse/assembly/shipments/analytics`) кэшируется 300s; `date_to` фильтрует как `shipped_at < date_to + 1 day` (включает весь день). Считает заявки в статусах **SHIPPED / DELIVERED / CLOSED** — `CLOSED` (возврат: WB не принял) включён намеренно, перевозка оплачена. `CANCELLED` исключён.
- **Аналитика потока сборки (`GET /warehouse/assembly/flow-analytics`,** `services/assembly/analytics.py::get_assembly_flow_analytics`): summary / stages / transitions / by_warehouse / anomalies / thresholds (Pydantic-схемы зеркалят TS-блок «Анализ потока сборки» в `types/api.ts`). Период — по `created_at` (query `date_from`/`date_to`, дефолт 90 дней) применяется к stages/transitions/summary; **аномалии — всегда по текущему состоянию активных заявок** (IN_PROGRESS..SHIPPED, период не применяется). Длительности этапов — из `AssemblyStatusHistory` (время в статусе = вход → следующий переход); заявки из черновика исторически могли не иметь стартовой записи → fallback: вход в IN_PROGRESS = `created_at` (теперь `_create_one_request` пишет стартовую запись `None → IN_PROGRESS`, `changed_by="system"`). Категории аномалий (одна на заявку, по приоритету): `wb_accepted_not_shipped` (READY/VEHICLE_ASSIGNED при `WbFboSupply.wb_status == ACCEPTED` — «забыли отгрузить», без порога) → `stuck_shipment` (от `actual_ready_date`, порог `ship_threshold_days=2`) → `stuck_assembly` (от входа в IN_PROGRESS, порог `assembly_threshold_days=3`) → `shipped_not_accepted` (от `shipped_at`, порог `delivery_threshold_days=7`). Кэш `reports:assembly_flow` (300s) инвалидируется во всех переходах статусов (`services/assembly/status.py`) и при создании заявки (`crud.py`).
