# DOMAIN_ASSEMBLY — Заявки на сборку + Лист логиста

Промежуточный слой между складом фулфилмента и отгрузкой FBO-поставок WB.
`WbFboSupply` (1:1) → `AssemblyRequest` → при SHIPPED создаёт `OutboundShipment`.

## Таблицы
| Модель | Назначение | Ключ / constraint |
|--------|------------|-------------------|
| `AssemblyRequest` | Заявка на сборку (статус, FBO-привязка, vehicle/pallet поля) | `models/assembly.py` |
| `AssemblyRequestItem` | Позиция заявки (barcode, qty) | FK на request |
| `AssemblyStatusHistory` | История смен статуса | FK на request |
| `AssemblyPickupCostHistory` | История правок стоимости перевозки (`old_cost`→`new_cost`, `changed_by`) | FK на request |
| `AssemblyDraft` | Черновик распределения N×M (`distribution` JSONB), SoftDelete | `models/assembly.py` |
| `OutboundShipment` / `OutboundShipmentItem` | Отгрузка, создаётся при SHIPPED | `models/warehouse.py` |

`PackageType` = `BOX | MONOPALLET | SUPERSAFE`. Один `AssemblyRequest` = одна транспортная единица WB = один `package_type`; тип определяется через `POST /warehouse/acceptance-check` (см. `DOMAIN_WAREHOUSE.md`). **`package_type` — это ТИП ПРИЁМКИ WB (canBox/canMonopallet/canSupersafe), НЕ единица поставки** (дефолт `BOX` почти у всех — привязывать к нему подписи «короб/паллета» нельзя, регресс #736→хотфикс #744).
**Единица поставки — отдельное булево поле `shipped_as_boxes`** (миграция `asm791`, дефолт `False` = паллеты): при `True` `pallets_count`/`pallet_weight_kg` считаются коробами, фронт переключает подписи («Короба»/«Вес 1 короба» vs «Палеты») в формах создания/редактирования (селектор «Единица поставки») и на деталке. Отдельного `box_count` нет — единица одна пара числовых полей. Мета-поле: редактируется в любом не-CANCELLED статусе (вкл. SHIPPED/DELIVERED). **Автоподстановка:** при переключении на «Короба» в форме редактирования число единиц авто-заполняется `boxes_count` (Σ⌈кол-во/кратность⌉ по позициям), обратно — исходным числом паллет. **Сквозная единица:** `OutboundShipment.shipped_as_boxes` — снимок с заявки при `ship_request` (миграция `asm792`); отдаётся в `LogisticsShipmentRow` (История отправок), `ShippableShipmentRow` (Оплаты), `AssemblyAttempt` (попытки на деталке) → все эти списки/карточки показывают единицу забора («N кор» vs «N пал»), а не всегда «палет».

## Бизнес-правила
- **Статусная модель:** `IN_PROGRESS → READY → VEHICLE_ASSIGNED → SHIPPED → DELIVERED`. Строго последовательная, пропуск запрещён. Допустимые откаты: `READY → IN_PROGRESS` (`start_assembly`, сбрасывает `actual_ready_date`), `VEHICLE_ASSIGNED → READY` (`unassign_vehicle`), `SHIPPED → READY` (cancel). `CANCELLED` — из любого статуса. **`RETURNED` («Возврат на склад»)** — НЕтерминальный: `SHIPPED/DELIVERED → RETURNED` (`return_to_warehouse`), когда WB не принял поставку. Из `RETURNED` — `reopen_for_reship` (→ `READY`: переотгрузка новым водителем по новой FBW-поставке) либо `close_request` (→ `CLOSED`). **`CLOSED` («Закрыт»)** — терминал после возврата(ов); логистика всех попыток сохранена. См. «Цепочка попыток отгрузки» ниже.
- **Цепочка попыток отгрузки (одна заявка = N попыток):** заявку можно отгрузить → не приняли → вернуть → переотгрузить новым водителем/FBW несколько раз. На `AssemblyRequest` хранится лишь ЗЕРКАЛО последней попытки (затирается). Долговечная история — на документах: каждая `ship_request` создаёт `OutboundShipment` со СНИМКОМ логистики попытки (`assembly_request_id`, `wb_fbo_supply_id`, `attempt_no = max+1` под row-lock, `pickup_cost`/`vehicle_*`/`driver_phone`/`counterparty_id`/`pickup_date`/`delivery_date`/`pallets_count`/`pallet_weight_kg`); каждый возврат создаёт `InboundReceipt` с `assembly_request_id`/`assembly_attempt_no` (его `warehouse_id` = склад возврата, **может отличаться** от склада-источника — параметр `return_warehouse_id`). `return_to_warehouse` чистит зеркало заявки (`outbound_shipment_id`/`shipped_at`/`wb_fbo_supply_id` → NULL), чтобы её можно было пере-связать с новой FBW (partial-unique индекс перестаёт держать). FK на заявку — `ON DELETE SET NULL` (история не удаляется). Цепочка для деталки: `get_assembly_attempts` (`GET /{id}/attempts`, схема `AssemblyAttempt`) — join `OutboundShipment` + `WbFboSupply` + `InboundReceipt` по `(assembly_request_id, attempt_no)`, исход: `rejected` (есть возврат) / `accepted` (FBW ACCEPTED либо заявка DELIVERED) / `in_transit`.
- **PENDING — legacy:** остаётся в enum для совместимости со `status_history`, но активных заявок в нём быть не должно. Новые заявки создаются сразу в `IN_PROGRESS`. `start_assembly` идемпотентен (повторный клик в IN_PROGRESS = no-op).
- **Валидация остатков** при create/update (PENDING/IN_PROGRESS) и `start_assembly`: `available = warehouse_stock.quantity − reserved_by_other_active_requests`, где reserved — сумма позиций по этому товару в других активных заявках (PENDING/IN_PROGRESS/READY/VEHICLE_ASSIGNED). Нехватка → `ValueError` с детализацией по баркодам. См. `_validate_available_for_assembly()` в `services/assembly/crud.py`.
- **При Mark Ready (IN_PROGRESS → READY):** авто-вес паллеты (если не задан вручную). Валидация переходов проверяется ДО применения авто-веса (apply_goods_weight КОММИТИТ, а stale-страница может отправить отказанный переход, молча мутируя терминальную заявку); `preserve_set_pallets=True` не перетирает уже заданное число паллет (от фронта per-классам совместимости категорий либо оператора), только геометрия фронта знает полностью. `mark_ready` также коммитит обновлённый вес/паллеты, поэтому гейт — рано.
- **При Ship (VEHICLE_ASSIGNED → SHIPPED):** валидация stock ≥ need; списание stock (`OUTBOUND`, `reference_type="ASSEMBLY"`); создаётся `OutboundShipment(SHIPPED)` + items; проставляются взаимные `outbound_shipment_id` на request и `WbFboSupply`; `shipped_at = utcnow()`.
- **При Cancel SHIPPED:** возврат stock (`reference_type="ASSEMBLY_CANCEL"`); `WbFboSupply.outbound_shipment_id = NULL`; `OutboundShipment.soft_delete()`; статус → READY. **Row-lock:** переход валидируется и действует под FOR UPDATE (ре-чтение из-за параллельной синхронизации WB: без лока `_auto_deliver_assembly` гонится с cancel, двойной возврат стока и конфликт статусов).
- **При Return (`return_to_warehouse`, `POST /{id}/return`, SHIPPED/DELIVERED → CLOSED):** WB не принял поставку, товар вернулся на склад-источник. Создаётся `InboundReceipt(ACCEPTED)` «Возврат по заявке ASM-…» → товар возвращается ГОДНЫМ стоком (`MovementType.INBOUND`, `reference_type="RECEIPT"`). В отличие от Cancel: заявка НЕ отменяется (статус `CLOSED`), `OutboundShipment` НЕ удаляется, `pickup_cost` сохраняется → логистика остаётся в аналитике. Связанная `WbFboSupply` помечается `return_processed_at`/`return_type=GOODS`/`return_qty` (если ещё не обработана) — уходит из «недоприёмки», двойного возврата не будет. Партиальная недоприёмка (WB принял часть) — отдельный flow `process_fbo_return` (см. `DOMAIN_WAREHOUSE`/`fbo_supply`), кнопка возврата заявки рассчитана на полный возврат.
- **Редактирование:** items — только до READY (заблокировано в SHIPPED/DELIVERED/CLOSED/CANCELLED). FBO-поставка — менять можно только до отгрузки и только при реальной смене (передача той же поставки в payload — no-op, не падает). Мета-поля (`pallets_count`, `pallet_weight_kg`, `comment`, `estimated_ready_date`, `wb_warehouse_name_manual`, `package_type`) и логистика (`pickup_cost`, `vehicle_*`, `driver_phone`) — в любом статусе кроме CANCELLED, включая SHIPPED/DELIVERED/CLOSED (inline edit + страница редактирования; остатки не двигаются). **Стоимость перевозки (`pickup_cost`, ASM-785):** каждая фактическая правка (new ≠ текущей) пишет строку в `AssemblyPickupCostHistory` (старая→новая цена + автор из `get_current_user`: «Имя Фамилия» ?? username, ≤50 симв); `changed_by` прокидывается через `update_assembly_request(..., changed_by=)`. Читается `GET /{id}/pickup-cost-history` (`get_pickup_cost_history`, схема `PickupCostHistoryResponse`) → карточка «История стоимости перевозки» на деталке. Повторный PUT с той же ценой / правка другого поля истории не плодят. **Склад-источник (`warehouse_id`)** — меняется в любом статусе до отгрузки (не SHIPPED/DELIVERED/CANCELLED); новый склад проверяется на существование и тип FULFILLMENT, сток ре-валидируется на нём только в PENDING/IN_PROGRESS (в READY/VEHICLE_ASSIGNED — без сверки, как и items, подгон под факт WB). UI: `<select>` на странице редактирования заявки.
- **«Из FBO» (`refresh_from_fbo`, `POST /{id}/refresh-from-fbo`, до SHIPPED):** ре-синк позиций заявки из привязанной `WbFboSupply`. Перед дифом форс-перетягивает из WB **detail + построчный goods** (`_try_force_enrich_supply(force=True, with_goods=True)` → обновляет зеркало `WbFboSupplyItem`), иначе диф шёл по застрявшему локальному снимку и не видел SKU, добавленных в кабинете WB после создания поставки (баг FBW-40012237: наш итог 398 vs WB/ФФ 550). `use_accepted = (wb_status==ACCEPTED)` → берём `accepted_qty` принятой поставки либо `quantity` заявленной. ШК из goods, которых нет в номенклатуре, не валят рефреш (был бы 400) — копятся в `RefreshFromFboResponse.skipped` (UI-варнинг). Best-effort: нет WB-ключа/ошибка → диф по тому, что уже в БД. **Для совместной поставки авто-синк состава отключён** (см. ниже).
- **Совместная поставка («Совместный номер» — 1 WB-поставка → N сборок):** одна `WbFboSupply` может нести несколько сборок — по одной на ФФ-источник (напр. wms + wms2 → одна совместная FBO-поставка WB). Уникальность держит partial-индекс `ix_assembly_requests_fbo_wh_unique` на `(project_id, wb_fbo_supply_id, warehouse_id)` (WHERE не удалена, не CANCELLED, поставка задана): двух активных сборок С ОДНОГО склада на одну поставку нельзя, разные склады — можно. Привязка второй сборки: дропдаун доступных поставок (`list_fbo_supplies(exclude_with_assembly=True, exclude_assembly_warehouse_id=<склад>)`) прячет поставку только если она занята сборкой ТОГО ЖЕ склада. **Признак «совместная» — вычисляемый** (≥2 сборок на поставке под тем же предикатом), не хранится: роутер считает батчем (`_enrich_joint` → `joint_supply`/`joint_siblings`), фронт показывает бейдж «Совместная» + фильтр «Только совместные» (`joint_only`). При ACCEPTED поставке `_auto_deliver_assembly` переводит в DELIVERED ВСЕ отгруженные сборки (не одну). **Авто-синк состава из FBO отключён** (combined-состав поставки нельзя атрибутировать одному источнику): ручной `refresh_from_fbo` → `ValueError`, фоновая пачка тихо пропускает (`raise_on_joint`). При cancel/return указатель `WbFboSupply.outbound_shipment_id` чистится только если он принадлежит ЭТОЙ сборке (не затираем отгрузку сестринской). **Ограничение MVP:** возврат одной из совместных сборок помечает `return_processed_at` на общей поставке (per-supply поле) — крайне редкий кейс частичного возврата совместной поставки ведётся вручную. **Передача логисту:** на листе логиста совместная схлопывается в одну строку (фронт коллапсит по `wb_fbo_supply_id`, якорь = min id) с разбивкой забора по складам — склад-источник / паллеты / вес / внутренний № заявки ФФ (`ff_request_number` сборки этого склада) / статус — и итогами (`joint_total_pallets`, `joint_total_weight_kg = Σ паллеты×вес`). Готовность к назначению машины — `joint_ready` (ВСЕ сборки поставки в READY и дальше; ни одной PENDING/IN_PROGRESS); пока не готовы все, строка видна, но «Назначить машину» заблокирована с пометкой «ждёт готовности: <склады>». Машина — ОДНА на всю поставку: `assign_vehicle` на совместной требует все-READY (иначе `ValueError` с перечнем неготовых) и **зеркалит** реквизиты машины/перевозчика во все сборки в одной транзакции (READY→VEHICLE_ASSIGNED у каждой, один `_resolve_carrier`). Отгрузка — `ship_joint_supply` (`POST /{id}/ship-joint`): отгружает ВСЕ назначенные сборки поставки разом (каждая своим складом/стоком/`OutboundShipment` через `ship_request`); sync-путь авто-отгрузки не трогаем.
- **WB-поставка (реплей кабинета):** каждый `AssemblyRequest` может быть занесён в FBW-поставку Wildberries через реплей внутреннего API кабинета seller-supply.wildberries.ru (публичного API нет). Модель `AssemblyWbSupply` (1:1, CASCADE) зеркалит жизненный цикл: `WbSupplySyncStatus` = NONE → DRAFT (черновик) → PREORDER (наполнение + валидация) → (ручная бронь даты в кабинете — антибот-гейт) → BOOKED (supply_id получен) → BOXED (раскладка коробов) → PASSED (пропуск водителя/авто/паллет), либо ERROR. Сервис `wb_supply_service`: `create_preorder` (выбор типа упаковки BOX/MONOPALLET/SUPERSAFE), `sync_supply_id` (подхват supply_id после ручной брони), `push_boxes` (раскладка + barcode), `push_pass` (TRN детали). Авторизация — БАНДЛ (authorizev3 + HttpOnly-cookie `.wildberries.ru`), сессия в зашифрованной ячейке интеграции; истечение → EXPIRED + просьба обновить доступ. Роутер: `/warehouse/assembly/{id}/wb/*` + `/wb-session`. **Резолв склада направления** (`_resolve_warehouse_id`): направление заявки — КАНОН-имя (`ACCEPTANCE_TO_STOCK_NAME`: «Краснодар», «Самара (Новосемейкино)»), а `getWarehouseFilterItems` кабинета отдаёт СЫРЫЕ имена («Краснодар (Тихорецкая)», «Новосемейкино») — матч: точный → casefold → канонизация обеих сторон (спец-двойники СГТ/Питание/СЦ исключаются; >1 реального кандидата под каноном, как Астана/Астана 2, — понятная ошибка выбора вручную). Без канон-шага «Краснодар»/«Самара» не резолвились вовсе (ASM-689/693, 2026-07-15). **Пер-товарные ошибки валидации** (`_extract_goods_errors`): `validateWarehouseGoodsV2` отдаёт `items[].hasError + errors[{field,error}]` (живой пример — «Запрет завоза предмета на склад»: категория запрещена на складе); с такими товарами `supply/create` падает `-32003` с ПУСТЫМ `innerMsg`, поэтому `create_preorder` поднимает список проблемных товаров понятной ошибкой ДО создания преордера (ASM-700/701).
- **Bulk-синк АВТОРИТЕТНОГО статуса WB (`sync_all_states`, `POST /warehouse/assembly/wb/sync-states`):** для каждой поставки с известным `supply_id` (реплей-связь ИЛИ адопция из FBO) дёргает `supply/supplyDetails {supplyID}` → пишет кабинетный `statusName`/`statusId` в `wb_supply_state(_id)` (для адоптированных без строки — создаёт строку BOOKED). Именно этот статус видит пользователь в кабинете («Запланировано»/«Отгрузка разрешена»/«Идёт приёмка»/«Принято»/«Отгружено на воротах»). Джоба `sync_all_projects_wb_supply_states` (scheduler 4ч) + ручная кнопка «Синхронизировать WB» в списке. Список обогащается батчем без N+1 (`AssemblyRequestResponse.wb_supply`) из сохранённого `wb_supply_state`. Кабинетный `statusId` и `statusID` из Suppliers API — **одна шкала** (сверено на 40732469: обе отдают `3`); показываем кабинетный, при его отсутствии — FBO-метку через `fbo_state_label`. Расхождение «кабинет Запланировано vs у нас В пути» было не двумя системами, а сдвигом `FBW_STATUS_MAP` на единицу (починено 2026-07-10). NB: `supply/listSupplies` отдаёт список под ключом **`data`** (не `supplies`), `statusIDs=[]` = «ничего» → `[-2]`, страница ≤20 — потому статус тянем per-supply через `supplyDetails`, а не пагинацией списка. Панель (`get_state`) тянет `supplyDetails` вживую (best-effort, при недоступности WB — FBO-фолбэк).
- **Адопция поставки из FBO (авто, без ручного заведения):** если реплей-связь не заводили, но у заявки есть привязанная **FBO-поставка** (`wb_fbo_supply_id`, синкается Marketplace API ~30 мин) — панель «Поставка WB» показывает её как **BOOKED** с `supply_id = WbFboSupply.wb_supply_id` (портальный supply_id == FBO wb_supply_id, подтверждено: `trn_details` принимает этот id) и статусом из кабинета (`supplyDetails`, best-effort; FBO `wb_status` — фолбэк). Деривится на чтение (`get_state`, `_enrich_wb_supply` в списке) — строку на GET не пишем; реальная строка появляется при заносе коробов/пропуска (`_get_or_create_link(adopt_supply_id=…)` бэкфиллит supply_id). Так короба/пропуск работают для поставок, забронированных прямо в кабинете. Хелперы `wb_supply_service.fbo_adopted_supply_id`/`fbo_state_label`.
- **Короба из кабинета (`get_cabinet_boxes`, `GET /warehouse/assembly/{id}/wb/cabinet-boxes`):** список коробов поставки с содержимым, как во вкладке «Упаковка» кабинета WB — batch-метод `ListBarcodesBoxes {incomeID: supply_id}` на `/ns/sm-box/.../box` (`client.list_boxes`). Каждый короб: `boxcode` + `barcodes[]{barcode, quantity, imtName (название), imgSrc (фото), brand, saNm (артикул), colorName, volume}`. supply_id — из реплей-связи ИЛИ адопции из FBO. Фронт (вкладка «Упаковка») рендерит раскрывающийся список + сводку «N коробов · X баркодов · Z шт».
- **Пропуск из кабинета (`get_cabinet_pass`, `GET /warehouse/assembly/{id}/wb/cabinet-pass`):** существующий пропуск поставки из `trn_details` (водитель/авто/паллеты + `barcode.barcodeId`/`barcodePrefix` + даты `dateFrom/dateTo`). Нужен, когда пропуск завели ПРЯМО в кабинете — авто-синк тянет только статус, не пропуск; DDS его не хранил → поля пусты. Фронт (вкладка «Пропуск») тянет при открытии, показывает баннер «пропуск уже заведён» и подставляет пустые поля формы из кабинета. supply_id — из связи/адопции.
- **«Назначить машину» = состав WB-пропуска.** Поля модалки (лист логиста и деталка) 1:1 с пропуском: Имя, Фамилия, Телефон, Марка, **Госномер**. Все обязательны. Хранение: `assembly_requests.driver_first_name` / `driver_last_name` (миграция `wbp04_assembly_driver_name`), `vehicle_brand` = марка, **`vehicle_info` = госномер**. ⚠ Исторически `vehicle_info` была свободной строкой «Номер, водитель, ТК» — у СТАРЫХ заявок там текст, поэтому читатели госномера обязаны терпеть оба формата, а ФИО у них NULL. Данные не мигрировались.
- **Машина ↔ пропуск (двусторонний префилл):** `assign_vehicle` (и ручная правка полей машины в шапке заявки через `update_assembly_request`) зеркалит реквизиты в WB-пропуск (`wb_supply_service.sync_pass_from_vehicle`, best-effort — сбой не роняет назначение): госномер (`_extract_plate` c фолбэком на сырое значение — иностранные номера не матчатся regex'ом) + марка + телефон **перезаписываются** (машина — источник истины); ФИО берётся из явных колонок заявки, а если их нет (старая заявка) — `_parse_driver_name` (эвристика «Фамилия Имя» после вырезания номера и телефона) и только в ПУСТОЙ пропуск; паллеты — если пусто. Строка `AssemblyWbSupply` создаётся при необходимости БЕЗ адопции (siblings совместной поставки могут не иметь загруженного `wb_fbo_supply` → lazy-load в async упал бы); `supply_id` добирается позже в `get_state`/`push_*`. **Авто-занос пропуска в WB (F3+, `try_autopush_pass`):** после зеркалирования пропуск сам уезжает в кабинет, как только это возможно — занести можно ТОЛЬКО при забронированной дате (`supply_id`; сама бронь — ручной антибот-шаг), поэтому попытка делается на КАЖДОМ событии, когда занос становится доступен: (1) назначение машины / правка реквизитов (`try_autopush_pass_by_assembly` после commit, best-effort), (2) подхват брони (`sync_supply_id`), (3) фоновый добор в `sync_all_states` (шедулер каждые 30 мин — переиспользует уже разобранный `cab`, без лишнего `trn_details`). Условия заноса идемпотентны: есть `supply_id`, `sync_status != PASSED`, заполнены ВСЕ поля WB (`_pass_is_complete`: ФИО+телефон+госномер+марка+паллеты; иначе ждём дозаполнения), в кабинете пропуска ещё нет (`cab.has_pass=False` — не перетираем ручной кабинетный ввод). Сбой заноса не флипает связь в ERROR и не роняет назначение/синк; ручной `push_pass` («Занести пропуск в WB») остаётся как override. Обратное направление: модалка префиллится из уже заведённого пропуска — `WbSupplyStateBrief` несёт `pass_driver_*`/`pass_car_*`, а `_enrich_wb_supply` отдаёт бриф и для «голого» локального пропуска (`_link_has_pass`, sync_status=NONE без supply/preorder — в колонке «WB» такой показывается как «—»).
- **Bulk-назначение машины** (`assign-vehicle-bulk`) прокидывает в per-request `AssignVehicle` подрядчика (`carrier_inn`/`carrier_name`) — раньше он приходил в payload, но терялся при сборке (фикс вместе с `wbp04`).
- **Логистику оказывает склад забора** (`AssignVehicle.logistics_by_warehouse`, флаг на заявке — миграция `asm790`): вместо ввода ИНН подрядчика перевозчиком становится контрагент склада-источника (`Warehouse.counterparty_id`). `assign_vehicle` резолвит контрагента ПО КАЖДОЙ сборке отдельно (`_warehouse_counterparty_id`) — у совместной поставки склады-источники разные; если у склада контрагент не задан → `ValueError` («У склада забора не указан контрагент…»). `carrier_inn`/`carrier_name` игнорируются. Лист оплаты не меняется — он уже завязан на `OutboundShipment.counterparty_id` (снимок при `ship_request`), забор приходит с реквизитами склада-контрагента. `unassign_vehicle` сбрасывает флаг. `AssemblyRequestResponse` несёт `logistics_by_warehouse` (состояние чекбокса) + `warehouse_counterparty_id` (гейт: без контрагента чекбокс задизейблен). UI — чекбокс в модалке «Назначить машину», прячет поля подрядчика.
- **Карточка поставки кабинета (`supplyDetails`) → 2 персистентных поля** (миграция `wbp03_supply_date_reject`): `supply_date` (забронированный слот сдачи, `supplyDate`) и `reject_reason` (текст кабинетных ошибок, `rejectReason` — «Не заполнены ШК коробов…», «Не заполнен пропуск…»). Пишутся в `get_state` (если строка связи реальна) и в bulk-синке; отдаются в `WbSupplyState` и `WbSupplyStateBrief` (`supply_date`). UI: колонка «Дата брони WB» в списке + поле в шапке заявки; баннер «Исправьте ошибки» в панели «Поставка WB» (как в кабинете). `supplyDate` парсится с ОТБРАСЫВАНИЕМ tz без конверсии в UTC (`_parse_wb_dt`) — иначе слот «23 июля +03:00» уехал бы на 22-е.
- **Пропуск: все поля обязательны.** WB (`setTRNDetails`) не примет пропуск без имени/фамилии/телефона/марки/госномера/паллет — фронт гейтит кнопку «Занести пропуск в WB» и перечисляет незаполненное. **ШК:** у поставки WB НЕТ собственного штрихкода — сканируются ШК ПРОПУСКА (`WB-GI-<barcode_id>`, из `trn_details`) и ШК КОРОБОВ (`WB_<boxcode>`). Оба печатаются клиентом (`lib/wbBoxStickers.ts`) в формате кабинета: A4, один ярлык на страницу, QR ≈63 мм + Code128 + код текстом 18pt.
- **Расхождение паллет заявки и пропуска:** заявка (`pallets_count`) и WB-пропуск (`pass_pallets`) — независимые числа; расхождение подсвечивается в статусах `READY / VEHICLE_ASSIGNED / SHIPPED` (до READY паллеты ещё правят). Список сборок: баннер сверху + бейдж «≠ WB» в колонке «Палеты»; панель «Поставка WB» → вкладка «Пропуск»: ⚠ у поля «Кол-во паллет» (сравнение с `assembly_pallets_count` из `get_state`).
- **AssemblyDraft (N×M):** черновик с экрана «Потребность по складам». Матрица `ФФ-источники × WB-целевые`, юзер балансирует Σ src ↔ Σ tgt по каждой строке. `commit_draft`: per-row валидация `Σ src == Σ tgt > 0` (иначе 400); pro-rata распределение в пары (largest-remainder для целочисленности); создаёт N `AssemblyRequest(IN_PROGRESS)` — по одной на уникальную пару `(source_ff, target_wb, package_type)` с qty>0 (новинки и обычные на один склад — В ОДНОЙ заявке; если в ней есть товар-новинка, `comment` получает префикс `NEWCOMER_COMMENT_PREFIX`). Atomic: исключение → rollback всех созданных, draft остаётся; успех → soft-delete draft.
- **Reconcile «один мир» (2026-07-10):** черновик — персистентный план, а заявки создаются и другими путями (предраспределение машины, ручные) — `dropCommittedRows` ловит только заявки СВОЕГО черновика. При загрузке `distribute/page` строки (rows + prebook) сверяются с `GET /warehouse/assembly/in-transit` (batch `fetch_in_transit_by_nm`: активные статусы + PRE_DISTRIBUTED, канон-имена складов) и урезаются per (nm, WB-склад) — «уже едет» повторно не предлагается (прод-кейс «швабры апл»: 54 шт ехали заявками pre-dist, черновик дублировал). PRE_DISTRIBUTED (резерв машины в пути) входит в per-склад вычет целей cold-start (`include_pre_distributed=True` в table-пути), но НЕ в вычет свободного ФФ (`_ACTIVE_ASM_STATUSES` vs `_ACTIVE_ASM_STATUSES_WITH_PD`) — товара машины ещё нет на ФФ. Server-side зеркало — ДЕЛЬТА-гейт `update_draft` (`_subtract_in_transit`): на каждом PUT транзит вычитается из плана, но только в пределах ПРИРОСТА относительно уже сохранённого черновика (идемпотентность автосейва) — защита от stale-вкладки, PUT'ящей старый план поверх очищенного. ✋ SKU из `distribution.manual_nms` гейт НЕ трогает: степперная правка матрицы делается при видимой колонке «В сборке», прирост поверх транзита — осознанный добор (прод-кейс 2026-07-15: +4 короба в Электросталь молча резались до нуля → «правка не сохраняется»). Кнопка «✓ Готово с правкой» дожимает незаписанный дебаунс сразу (`finishManual`), не полагаясь на fire-and-forget анмаунта. **Демоция урезанных направлений (2026-07-17):** гейт режет транзит per (nm, склад) ПОСЛЕ фронтовой паллет-нормализации — из целой смешанной паллеты выпадают покрытые транзитом SKU, и остаток направления в rows переставал быть целой паллетой (прод-кейс draft 62: ЕКБ ехал «1 пал · ⚠ ~50%»). Теперь остатки направлений (package_type × склад), урезанных гейтом в rows, уезжают в prebook (`_demote_directions_to_prebook`, пары `_allocate_pairs`, слияние `_merge_rows`); `as_is`-строки и ✋ ручные SKU не трогаются; фронт-консолидация поднимает собравшиеся целые паллеты обратно.
- **Гейт ёмкости ФФ (2026-07-22, `_clamp_to_ff_capacity`):** второй server-side гейт `update_draft`, сразу после дельта-гейта. План (rows[].src + prebook[].src) per (barcode, ФФ) клампится к `cap = max(0, сток warehouse_stock − в_сборке активными заявками PENDING/IN_PROGRESS/READY/VEHICLE_ASSIGNED − резерв других черновиков get_drafts_reserved)`. Сознательно БЕЗ baseline: применяется и к уже сохранённому плану — иначе «храповик»: SKU с available=0 выпадает из articles фронтового расчёта, calc не владеет nm, его строки консервируются навечно, а дельта-гейт режет только прирост (прод: divan_darkblue — сток 8 целиком в ASM-858, черновик держал ещё 8; швабра EP-800 — 402 обещанных из 282 физических). Порядок среза: prebook → rows (авто), `as_is`/✋ `manual_nms` последними — но физика важнее ручных решений, фантом с ✋ тоже срезается (в отличие от дельта-гейта, где ✋ освобождает). Fail-open (сбой выборки → лог + план нетронут), батч-запросы, пустые строки после среза удаляются. Фактический срез аудируется событием истории `CAPACITY_TRIM` (снапшот ДО среза + разбивка по артикулам, откатываемо как снапшот-событие), а остаток урезанного rows-направления демотируется в предбронь `_demote_directions_to_prebook` — канон «rows = целые паллеты» (as_is/✋ manual демоция не трогает). **Слепое пятно транзита закрыто там же:** `fetch_in_transit_by_nm` берёт склад как `COALESCE(wb_warehouse_name_manual, wb_fbo_supplies.warehouse_name)` — заявки, привязанные к WB-поставке без ручного имени, раньше выпадали в `'?'` и были невидимы всем вычетам.
- **Объединение черновиков (`merge_drafts`, `POST /merge`):** когда несколько черновиков отправляют товар по одному маршруту `(ff → wb)`, они создадут раздельные отправки на ФФ. `merge_drafts` сливает список черновиков в один. Survivor = черновик с наибольшим числом строк (tie-break: наименьший id); остальные soft-delete. Строки объединяются по ключу `(nm_id, package_type)` — src/tgt суммируются поэлементно. `handed_units` переносятся в survivor (ключ `(source_ff, target_wb, package_type)`; позиции суммируются по баркоду, статус `handed` побеждает `draft`). **Флаги выживают:** `manual_nms` (защита ручного плана SKU от авто-синка) и `prebook_origin` (провенанс паллет для бейджа) Union'ятся с сохранением порядка — раньше при слиянии терялась ручная разметка и генезис паллет. `cold_start_shares` сбрасывается (юзер запускает авто-баланс заново). После merge → редирект на `distribute/preview?draft=<id>&pkg=BOX`.
- **Партиальный commit_draft по упаковке:** `package_type` (BOX/MONOPALLET — короб/моно). **Срез упаковки = вкладка UI, а не точный тип:** `package_type=BOX` («Короб») коммитит ВСЁ, кроме MONOPALLET — т.е. BOX И SUPERSAFE (каждая заявка сохраняет свой реальный тип); `MONOPALLET` — только моно (`_pkg_selected`). Иначе SUPERSAFE-строки молча оставались бы в черновике. Всё не выбранное остаётся в `rows` черновика для следующих сборок; если осталось что-то ИЛИ есть `handed_units` — draft не удаляется. **Новинки НЕ разделяются** на отдельные заявки: новинка — производный признак товара (`fetch_newcomer_nm_ids`), а не ось группировки; если в заявку `(ff, wb, pkg)` попал хоть один товар-новинка, её `comment` получает префикс `NEWCOMER_COMMENT_PREFIX`. После коммита инвалидируется кэш `reports:warehouse_need` (заявки попадают в IN_ASSEMBLY вычета потребности, иначе без инвалидации до 5 минут показывается свободным сток, уже уехавший в заявки).
- **Жизненный цикл заявки-юнита** (`distribute` → «передан на ФФ» → «в сборке»). «Заявка-юнит» = ключ `(source_ff × target_wb × package_type)` — новинки и обычные товары на один склад в ОДНОМ юните. Состояния: **auto** (живёт в `rows`) → **draft** (ручная правка, `set_unit_items`, status=`draft`, ещё в `handed_units`) → **handed** (`hand_off_unit`, status=`handed`, заморожен) → **committed** (`AssemblyRequest`). Все lifecycle-функции нормализуют `handed_units` через `_normalize_handed_units` (схлопывают снимки одного ключа — для старых черновиков, где новинки/обычные были разнесены). **Предзаявка (is_prebooking):** заявка-бронь для ⌛-направлений (приём открыт, лимита нет): ФФ собирает сразу, слот WB бронируется при появлении лимита. Бэк (`create_prebooking`) всегда был package-agnostic; фронт раньше давал кнопку только MONOPALLET — теперь и BOX. Дозабор ⌛-направления кладёт результат В ПРЕДБРОНЬ (не в черновик — «черновик = готовое к сдаче»), целые паллеты затем уходят предзаявкой. Эндпоинты `units/*` (`assembly_draft_service`):
  - `hand_off_unit` — «передать на ФФ»: `_carve_unit_from_rows` вырезает поток ff→wb из `rows` (новинки + обычные вместе) и сливает с существующим снимком склада, если он есть (status=`handed`). Снимок не трогается правками распределения (его уже нет в `rows`).
  - `revert_unit` — «вернуть в черновик»: вливает позиции `handed`-юнита обратно в `rows`. Ключ инвариантности: `(nm_id, package_type, barcode)` — один nm_id несёт несколько баркодов (размерные варианты), влив по частичному ключу приписал бы qty чужому баркоду.
  - `commit_unit` — «в сборку»: создаёт один `AssemblyRequest` из юнита (замораживает его неявно — отдельный hand-off не нужен; берёт черновик FOR UPDATE), удаляет юнит; пустой draft → soft-delete. Пишет событие COMMIT_REQUEST (иначе заявка была невидима в истории и неоткатываема). **Гвард:** предбронь (`distribution.prebook`) держит черновик живым (даже без `rows`/`handed_units`) — она резервирует сток в `/drafts/reserved`, soft-delete молча терял бы резерв → другие черновики запланировали бы его повторно.
  - `set_unit_items` — редактор наполнения: заменяет позиции (фиксирует auto-юнит как `draft`); на `handed` — 400 «правка запрещена». Проверку свободного остатка ФФ делает фронт.
  - `delete_unit` — удалить юнит целиком (товар остаётся на ФФ); на `handed` — 400 «сначала верните в черновик». **Гвард:** не удаляем, если это `handed`-юнит с живыми товарами — факт передачи оператору ФФ.
  - `remove_rows_by_nm` (хелпер): убирает из `rows` все строки и предбронь указанных SKU. **Гвард:** `handed`-юниты с товарами НЕ трогаются — это физический факт передачи товара оператору; чистка неликвида не должна молча «забывать» переданное, иначе `/drafts/reserved` отпускал бы его резерв.
  - `move_unit` — «сменить склад WB» (UI: кнопка на `distribute/request`): перенести юнит на другой WB-целевой склад черновика. Двигается ТОЛЬКО поток этого ФФ (`ff→wb`), баланс матрицы сохраняется. Источник — авто (вырезаем из rows) или ручной черновик; на складе-получателе сливается с существующим ручным черновиком по баркоду, иначе поток возвращается в rows как `ff→new_wb`. `handed` переносить нельзя (400); перенос на тот же склад — 400.
- **Связь заявка ↔ черновик (`source_draft_id`):** `commit_unit` и `commit_draft` проставляют `AssemblyRequest.source_draft_id = draft.id`. Страница склада-источника (`distribute/ff`) показывает блок «История — в сборке» — заявки этого черновика (`GET /warehouse/assembly?draft_id=&warehouse_id=`). NULL для заявок из других путей (FBO/ручные). Заявки, созданные до миграции `asm_source_draft_id`, в инлайне не появятся (только в полном списке `/warehouse/assembly`).
- **Предпросмотр созданных (`get_created_groups`, `GET /warehouse/assembly/created-groups`):** после полного коммита черновик soft-удаляется, но созданные заявки группируются по `source_draft_id` в read-only «Созданные партии» на странице `warehouse/assembly`. Только **IN_PROGRESS**-заявки (ещё в сборке, не ушли в работу/отгрузку), кап 50 групп, свежие сверху. Имя черновика резолвится даже после его soft-delete. Это якорь для будущего мёрджа созданных заявок (заявка↔заявка / черновик→заявка по дублирующимся маршрутам).
- **Дедуп повторного commit черновика (фикс дубля «дозабор из предброни»):** черновик переживает commit, пока в нём осталась предбронь (`distribution.prebook`) — см. `commit_draft` (ветка «не soft-delete»). Если после первого коммита юзер добирает паллеты из предброни и коммитит **тот же черновик** ещё раз, `commit_draft` для каждой группы `(pair_src_id, target_wb_name, package_type)` ищет уже созданную **не-отгруженную** сборку **из этого же `source_draft_id`** (`wb_fbo_supply_id IS NULL`, статус PENDING/IN_PROGRESS) и **доливает** в неё позиции (`_fold_barcodes_into_request`: суммирует по `(nomenclature_id, barcode)`, паллеты Σ, вес — **взвешенное среднее только из известных весов** — нулевой добавляемый не разбавляет уже проставленный вес заявки, иначе экспорт/аналитика занижаются и авто-пересчёт mark_ready срабатывает ошибочно), а не плодит дубль. Скоуп по `source_draft_id` не трогает намеренно раздельные сборки других черновиков. READY-сборку не трогаем (доливка «расготовила» бы собранный груз) — редкий такой дубль лечится ручным «Объединить».
- **Дедуп повторного распределения машины (тот же фикс для экрана «Распределить машину»):** `create_pre_distribution` инкрементален (over-commit-гард `_reserved_by_barcode(vehicle_id)` пускает дозабор машины частями), поэтому второй заход на то же направление плодил бы дубль. **Advisory-lock** (`pg_advisory_xact_lock` per-project) сериализует конкурентные сабмиты с одной вкладки/двух юзеров: SELECT гарда и дедупа читают свежий резерв после commit'а победителя; повторный ре-захват на каждой группе (commit per-группу). Для каждой группы `(wb_name, package_type)` ищем не-терминальную сборку **той же машины** (`source_vehicle_id`) с тем же `(target_wh, wb_name, package_type, wb_fbo_supply_id)` (статус PRE_DISTRIBUTED/IN_PROGRESS) и доливаем позиции (`_fold_into_pre_dist_request`), а не создаём новую. Пре-дистрибуции разных машин не сливаются (скоуп `source_vehicle_id`).
- **Принятая машина в распределении (окно 3 дня, 2026-07-15):** DELIVERED-машина с ACCEPTED-приёмкой не старше `PRE_DIST_DELIVERED_WINDOW_DAYS` (=3, дата — `InboundReceipt.actual_date`, связь `cost_order_id`/`inbound_receipt_id` в обе стороны) остаётся в списке/пуле предраспределения (`accepted_date` в `PreDistVehicle`). Её груз уже оприходован в `WarehouseStock` ФФ, поэтому `create_pre_distribution` создаёт из неё **ОБЫЧНЫЕ** заявки: `IN_PROGRESS`, `skip_stock_validation=False`, `is_pre_distribution=False`, но `source_vehicle_id` остаётся меткой (бейдж «🚚 Из машины V-…» в списке сборок). Перед мутациями — единый предчек реального остатка по Σ всех групп (`_validate_available_for_assembly`): fold-путь сам сток не проверяет, а create-путь коммитит по-групно — предчек даёт fail-fast без частично созданных групп. Fold-дедуп работает и тут (статусы PRE_DISTRIBUTED/IN_PROGRESS в выборке дедупа покрывают оба режима). ## Грабли
- При `commit_draft` строки группируются по `(source_ff, target_wb, package_type)` — если для одного склада нужны и короб, и моно, это разные заявки. Новинки и обычные на один склад/упаковку — ОДНА заявка (новинка лишь добавляет префикс 🆕 в `comment`).
- **Старые черновики «в полёте»:** до объединения юнитов новинки и обычные на один склад жили в РАЗНЫХ снимках `handed_units` (и могли быть переданы на ФФ раздельно). `_normalize_handed_units` (вызывается во всех lifecycle-функциях) и фронтовый `buildFfUnits` схлопывают их по ключу `(ff, wb, pkg)`. Смешанный статус (часть в снимке + часть ещё в `rows`) → карточка показывается как `черновик`; `hand_off_unit` дослаивает `rows` в снимок.
- **Carve сохраняет баланс строки:** `_carve_unit_from_rows` вычитает выделенный qty из `src` И из `tgt` на одну величину → остаток строки остаётся сбалансированным (`Σsrc == Σtgt`). При правке снимка не пересчитывать через `src/tgt` — `HandedUnit.items` уже плоский список qty.
- **SUPERSAFE и срез «Короб»:** `commit_draft?package_type=BOX` трактует «Короб» как не-MONOPALLET (`_pkg_selected`), поэтому SUPERSAFE-строки коммитятся вместе с BOX (исправлено — раньше они молча оставались в черновике). Каждая заявка сохраняет реальный `package_type`. ⚠️ Если WB заворачивает SUPERSAFE на приёмке иначе — это уже про acceptance, не про отбор.
- **Cross-type drag (distribute, фронт):** перетаскивание WB-колонки между вкладками Моно/Короб меняет `package_type` перенесённых строк — с подтверждением. Срабатывает ТОЛЬКО если цель однотипна (`onlyMono`/`onlyBox`); смешанная цель → обычный merge без смены типа. Колонки с нулём в текущем типе показывают вторичный счётчик (📦/📐) — подсказка куда тащить. Типы определяются по `allRows` (все строки, не только видимые во вкладке).
- Аналитика логистики (`GET /warehouse/assembly/shipments/analytics`) кэшируется 300s; считает **по ПОПЫТКАМ отгрузки** — агрегат по `OutboundShipment` (не по `AssemblyRequest`), поэтому переотгрузка после возврата суммирует ОБЕ перевозки (а не затирает). Фильтр: непустые отгрузки заявок (`assembly_request_id IS NOT NULL`, `status != CANCELLED`, заявка не удалена) — возвраты (RETURNED/CLOSED) включены (перевозка оплачена), отменённые (soft-deleted на cancel) исключены. `date_to` фильтрует `shipped_date < date_to + 1 day`; dest = снимок `OutboundShipment.destination` (fallback `wb_warehouse_name_manual`). Постфактум-правки `pickup_cost`/`vehicle_*` на SHIPPED/DELIVERED зеркалятся `update_assembly_request` на отгрузку текущей попытки.
- **Стоимость логистики ₽/шт и ₽/короб** (`GET /warehouse/assembly/shipments/cost-per-unit`, `get_logistics_cost_per_unit`, кэш `reports:logistics_cost_per_unit` 300s) — раздел «Стоимость ₽/шт» на «Листе логиста» (сегмент внутри «Истории отправок»). `pickup_cost` — стоимость на ВСЮ отгрузку; разносим по позициям (`OutboundShipmentItem`): ₽/шт забора = pickup_cost/Σштук, ₽/короб = pickup_cost/Σкоробов (короб = ⌈кол-во/кратность⌉ per (склад отгрузки, ШК) через `resolve_box_qty_by_warehouse`; позиции без кратности в короба не идут). Разрез по **категории** (эффективная: `CategoryOverride ?? Nomenclature.subject`, резолв через `_category_by_nm`) и **бренду** (`Nomenclature.brand`), плюс динамика за период (день/неделя/месяц по `shipped_date`, бакет в Python). `total_cost` среза — unit-alloc (покрывает все штуки). Фильтры `brands`/`categories` — НА УРОВНЕ ПОЗИЦИИ (знаменатель ₽/шт забора не зависит от фильтра). Агрегация Python-side (короба — ceil по кратности), ≈6 запросов без N+1, кап `_COST_PER_UNIT_SHIPMENTS_LIMIT=8000` (флаг `truncated`). Отдельно от `_COST_PER_PALLET`-аналитики (та — ₽/паллета).
- **Список сборок (`GET /warehouse/assembly`) обогащается привязкой ФФ** (`_enrich_ff_links` в `routers/assembly.py`): `ff_request_number`/`ff_links` (несколько для migfull/«Натали») берутся одним индексированным запросом по `fulfillment_requests.assembly_request_id` — **БЕЗ гейта на активность ключа интеграции** (номер ФФ-заявки = историческая привязка; раньше гейт по `IntegrationKey.is_active` прятал его в локалке и после отключения интеграции). На «Лист логиста» (Активные: карточки+таблица+Excel) выводим эти номера строкой «Заявка ФФ» и подсвечиваем «висящие» заявки: бейдж «⏱ висит N дн» + рамка/фон (warning ≥2 дн, danger ≥4) для READY/VEHICLE_ASSIGNED от `actual_ready_date` — ПРИБЛИЖЕНИЕ аномалии `stuck_shipment` (порог 2 дн общий; точное время перехода в READY на списке недоступно → расхождение <1 сут допустимо).
- **Аналитика потока сборки (`GET /warehouse/assembly/flow-analytics`,** `services/assembly/analytics.py::get_assembly_flow_analytics`): summary / stages / transitions / by_warehouse / anomalies / thresholds (Pydantic-схемы зеркалят TS-блок «Анализ потока сборки» в `types/api.ts`). Период — по `created_at` (query `date_from`/`date_to`, дефолт 90 дней) применяется к stages/transitions/summary; **аномалии — всегда по текущему состоянию активных заявок** (IN_PROGRESS..SHIPPED, период не применяется). Длительности этапов — из `AssemblyStatusHistory` (время в статусе = вход → следующий переход); заявки из черновика исторически могли не иметь стартовой записи → fallback: вход в IN_PROGRESS = `created_at` (теперь `_create_one_request` пишет стартовую запись `None → IN_PROGRESS`, `changed_by="system"`). Категории аномалий (одна на заявку, по приоритету): `wb_accepted_not_shipped` (READY/VEHICLE_ASSIGNED при `WbFboSupply.wb_status == ACCEPTED` — «забыли отгрузить», без порога; **VEHICLE_ASSIGNED-часть авто-отгружается** на ближайшем FBO-синке — `_collect_assembly_ship_on_wb_accepted`/`_ship_assemblies_best_effort` в `fbo_supply/sync.py`, см. `DOMAIN_WAREHOUSE` «Авто-SHIP забыли отгрузить»; в аномалии оседают лишь READY без машины и заявки с дефицитом стока) → `ff_closed_not_shipped` (активная сборка до SHIPPED, у которой связанная `FulfillmentRequest` `is_completed`/`archived` и НЕ `local_archived` — ФФ собрал/отгрузил, а мы ещё нет; без порога; строка обогащена `ff_request_number`; статус НЕ меняется — отгрузка двигает сток вручную) → `stuck_shipment` (от `actual_ready_date`, порог `ship_threshold_days=2`) → `stuck_assembly` (от входа в IN_PROGRESS, порог `assembly_threshold_days=3`) → `shipped_not_accepted` (от `shipped_at`, порог `delivery_threshold_days=7`). Заметка: кэш `reports:assembly_flow` (300s) при синке ФФ напрямую не инвалидируется — `ff_closed_not_shipped` появляется в пределах TTL. Query-параметр `categories` (CSV, `Nomenclature.subject`; заявка попадает при ≥1 позиции категории, применяется к периодной и active-выборкам). Параметр `wb_warehouses` (CSV «городов сдачи»: coalesce(имя связанной поставки, `wb_warehouse_name_manual`)); значения фильтра — `GET /warehouse/assembly/flow-analytics/wb-warehouses` (НЕ /wb-warehouses — тот занят union-автокомплитом new/edit). Блок `stage_daily` (стек «товары по этапам»): снимок qty на конец дня по этапам IN_PROGRESS/READY/VEHICLE_ASSIGNED/SHIPPED; кандидаты — жившие в окне (≤365 дн), включая созданные до date_from; интервалы из `AssemblyStatusHistory`, открытый интервал по `req.status`, терминальные (DELIVERED/CANCELLED/CLOSED) этапов не занимают. Блок `daily` (график «динамика по дням»): `created_count`/`created_qty` по `date(created_at)`, `shipped_count`/`avg_cycle_days` по `date(shipped_at)` — SQL-агрегация по тем же фильтрам, без `_FLOW_LIMIT`. Строка аномалии обогащена `wb_supply_number` (номер WB-поставки `wb_fbo_supplies.wb_supply_id`) и `pallets_count` — колонки «ФБО-поставка»/«Паллет» и Excel-экспорт секций на фронте; там же кнопка «Отгрузить машины» (bulk `POST /assembly/ship-bulk` по VEHICLE_ASSIGNED-заявкам группы «забыли отгрузить»). Кэш `reports:assembly_flow` (300s) инвалидируется во всех переходах статусов (`services/assembly/status.py`) и при создании заявки (`crud.py`).
- **Связи и расхождения (`GET /warehouse/assembly/flow-analytics/link-anomalies`,** `services/assembly/link_anomalies.py::get_link_anomalies`, схема `LinkAnomaliesResponse`, кэш `reports:assembly_link_anomalies` 300s): вкладка «Связи и расхождения». Пять блоков, всё по зеркалу (без HTTP): (1) `ff_composition_mismatch` — активные сборки (IN_PROGRESS/READY/VEHICLE_ASSIGNED), чей состав расходится с привязанными заявками ФФ — поверх `fulfillment_service.get_assembly_ff_mismatch_map`/`_detail` (our_total/ff_total/diff/mode barcode|total); (2) `assemblies_without_ff` — наши сборки на ФФ-интегрированных складах (DISTINCT `FulfillmentRequest.warehouse_id`) без живой привязки; провайдер из `IntegrationKey.service ∈ FF_SERVICES`; (3) `ff_without_assembly` — `FulfillmentRequest` kind=assembly с `assembly_request_id IS NULL`, не archived/local_archived; (4) `fbo` — сводка аномалий FBO (без заявки / недоприёмка / излишек) реюзом `fbo_supply.service.get_fbo_summary`/`get_partial_acceptance_summary` (project-global, drill-through на `/warehouse/fbo-supplies`); (5) `stock_mismatch` — расхождение остатка «наш склад vs ФФ-зеркало» по интегрированным складам: `diff = ff_good − (our_quantity + our_defect)`, где `our_defect` берётся ТОЛЬКО для migfull (его `stock_actual`/ff_good включает брак — иначе расхождение раздувается ровно на наш брак, как было в `list_stocks` до фикса; прочие провайдеры — `ff_good − our_quantity`), короб→россыпь как в `list_stocks`, `diff==0` скрыт; агрегат по складу surplus_ff/our + net_diff, построчно cap `_STOCK_MISMATCH_SKU_CAP`. Query `warehouse_ids` (CSV) применяется к блокам 1–3, 5, не к FBO.
- **Распределение остатков (`GET /warehouse/assembly/flow-analytics/stock-distribution`,** `services/assembly/stock_distribution.py::get_stock_distribution`, схема `StockDistributionResponse`, кэш `reports:assembly_stock_distribution` 300s): вкладка «Распределение остатков» — «где сейчас товар» (100%). Бакеты (шт): `ff_stock` = Σ `max(qty_good - qty_reserve, 0) × units_per_box` по `FulfillmentStock` (резерв вычитаем — он = «в сборке», иначе двойной счёт; короб→россыпь по `base_barcode`/`units_per_box`); `in_assembly`=IN_PROGRESS, `ready`=READY+VEHICLE_ASSIGNED, `in_transit`=SHIPPED по `AssemblyRequestItem.quantity`. Разрезы `total` / `by_warehouse` / `by_status`. Статус товара — из `ProductStatusMap` (active/new/clearance) через `nomenclature_id → Nomenclature.article_wb → nm_id`, без статуса → `none` «Без статуса». Query `warehouse_ids` и `product_status` сужают `total`/`by_warehouse`; `by_status` всегда полный (без `product_status`-фильтра).
- **История распределения по дням (`GET /warehouse/assembly/flow-analytics/stock-distribution/history`,** `services/assembly/stock_distribution.py::get_stock_distribution_history`, схема `StockDistributionHistoryResponse` = `daily: [{date, ff_stock, in_assembly, ready, in_transit}]`): динамика 4 бакетов «где товар» по дням. `FulfillmentStock` истории не имеет (перезатир каждым синком) → склад ФФ нельзя восстановить задним числом — копим вперёд в таблице **`assembly_stock_distribution_daily`** (миграция `asm01_stock_distribution_daily`; одна строка на день × склад × статус товара, idempotent-перезапись дня). Пишет ежедневная scheduler-джоба `snapshot_all_projects_stock_distribution` (23:50 MSK, `scheduler/jobs/stock_distribution_snapshot.py`) поверх `snapshot_stock_distribution` (единый расчёт ячеек `_compute_distribution_cells`, общий с live-эндпоинтом). История без бэкфилла — пустая, пока джоба не накопит данные. Query `date_from`/`date_to`/`warehouse_ids`/`product_status` фильтруют выборку, агрегат — `SUM` по `snapshot_date`.
