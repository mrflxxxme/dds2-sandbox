# DOMAIN_FULFILLMENT — интеграция внешних фулфилментов (skladbot.ru, wmscelicom, migfull)

Generic-слой зеркалирования данных фулфилмент-провайдеров на странице склада: остатки (snapshot + расхождения), заявки на сборку и приёмки (зеркало + ручная связь с нашими документами). Фаза 1 — read-only pull. Фаза 2 (только skladbot) — PUSH: создание заявки «Доставка на склад МП» у ФФ из нашей `AssemblyRequest` (см. «Создание заявки ФФ из нашей сборки»).

## Провайдеры

Соседний wms2 «малое Брянцево» пуст целиком (Count=0).

## Бизнес-правила
- **Зеркало никогда не пишет в `WarehouseStock` / `StockMovement`** — наши остатки производны от документов; данные ФФ живут отдельно, вкладка показывает расхождения.
- **Возвраты migfull (`kind=return`, `GET /returns`) и пара «вскрытие коробов»**: Натали оформляет вскрытие коробов под FBS ПАРОЙ документов — «Возврат» (списание короб-SKU, кол-ва В КОРОБАХ) + «Поступление» (приход тех же товаров россыпью, В ШТУКАХ); пример PVB-0000069 ↔ PVB-0000133 (30.07.2026). Строки возврата встроены в список (`incoming_lines` в raw); строки приёмок складываются в raw enrich'ем (для матчера и офлайн-деталки). Матчер `_match_repack_pairs` (в транзакции синка): возврат — ВСЕ строки короб-SKU (override → зеркало → ITF14+«короб N шт.»), поступление — не связано с нашими документами, окно ±3 дня; ПАРА при точном равенстве мультимножеств штук россыпи (пересечение >80% без равенства — warning, не марк); успех → `repack_return_id` у поступления + `repack_matched_at` у обоих (идемпотентно). Помеченная пара — внутренняя переупаковка ФФ: **наш сток не двигается**, guard'ы исключают её из авто-ACCEPT приёмок, transfer-fact, резерва «В приёмке» (`_migfull_inbound_locked_by_barcode`) и привязок (`link_request`/`get_link_candidates`); kind=return не привязывается вовсе. Возврат без пары старше 3 дней → `repack_unpaired=True` в выдаче (возможно, РЕАЛЬНЫЙ возврат товара). Нумерация `PVB-…` возвратов коллизирует с приёмками/отгрузками — это разные нумерации, уникальность только по guid.
- **Разбивка резерва и «Расхождение» для migfull считаются на лету в `list_stocks`** (`stock_actual`/`stock_locked`/`stock_available` — единственные поля остатка migfull, отдельного брака в API НЕТ). Брак заблокирован ВНУТРИ `stock_locked` (qty_reserve). Резерв делим на **3 части**: **Собрано** (`ff_reserve_ready`, под активные отгрузки) + **В приёмке** (`ff_inbound_locked`, под свежий приход) + **Брак** (`ff_defect`, остаток). «Собрано» = `min(собранное под guid, qty_reserve)`, где собранное = Σ `planned_lines.quantity` отгрузок в статусах **`ready`+`uploaded`+`new`** (`_MIGFULL_ACTIVE_SHIPMENT_STAGES`) по `product_guid` (`_migfull_assembled_by_guid`; в коробах для короб-guid → ×`units_per_box`). «В приёмке» = `min(Σ expected_qty EXPECTED-приёмок по россыпь-ШК, остаток брака)` (`_migfull_inbound_locked_by_barcode`) — вынимается из предварительного брака. Кап нужен, т.к. заявка планирует больше, чем реально locked. А т.к. `stock_actual` (ff_good) включает весь резерв (в т.ч. брак), **diff** сверяет ИТОГИ: `ff_good − (our_quantity + our_defect)` (иначе расхождение раздувалось на величину брака). Инвариант: `Резерв = Собрано + В приёмке + Брак`.
  - **Почему все активные, а не только `ready`, + «В приёмке» (правка 2026-07-15):** старая логика (`ready`-only, без «В приёмке») РАЗДУВАЛА брак. Живьём (натали): резерв держат и `uploaded`/`new`-отгрузки (locked > собранного-ready), а свежий приход migfull лочит на время оприходования (Алмазная мозаика машины V-0032: резерв=весь остаток, отгрузок 0, наш брак 0, но есть EXPECTED-приёмка) — и то, и другое ошибочно падало в «Брак» (6016 на странице при реальном ≈3000). Теперь собрано = все активные отгрузки, приход-под-EXPECTED-приёмку — отдельный бакет. Расхождение (diff) при этом НЕ меняется (сравнивает ИТОГИ, а `ff_good` включает весь резерв целиком) — правка только про честность колонок Собрано/В приёмке/Брак.
  - **Прочие провайдеры** (skladbot/wmscelicom): `ff_defect` — из API (repair/нет), `ff_reserve_ready`=0, diff = `ff_good − our_quantity` (без изменений). Колонка «Собрано» на фронте — только при `provider==migfull`.
  - **⚠️ «Брак ФФ» у migfull — ВЫВЕДЕННАЯ величина, а не измерение, и доверять ей нельзя.** Живая сверка кабинета натали 27.07.2026: заблокировано 6821, активные отгрузки объясняют 2707, активные приёмки 862 — **3252 (48 %) не объясняет ничто из того, что отдаёт API migfull**, и всё это падает в «Брак». На SKU BZ-YY8820A/30x60 из 29 заблокированных коробов отгрузки объясняли 1, а остальные 28 в точности совпали с планом отгрузок, ЗАКРЫТЫХ за последнюю неделю → товар стоял НА СБОРКЕ. Отделить «уже уехало» от «лежит собранным» нечем: `is_processed`/`processed_at` пусты у всех 327 отгрузок, а окно по `shipment_date` не обобщается (на 7 днях по кабинету переатрибуция +16к). Поэтому на фронте у migfull колонка и KPI зовутся **«Блокировка проч.»**, а не «Брак ФФ»; реальный брак по такому складу — только наш `our_defect`. Разбивка Собрано/В приёмке остаётся полезной, ярлык остатка — нет.
  - **Две публичные точки под FBS, и их нельзя путать** (провайдер-специфика живёт только в них):
    - `ff_defect_by_nomenclature(db, project_id, warehouse_ids)` — **ИЗМЕРЕННЫЙ брак** (`{warehouse_id: {nomenclature_id: шт россыпи}}`): только `qty_defect` (skladbot `repair_amount`); у migfull и wmscelicom пусто, поля в API нет. Питает колонку «Брак» превью FBS (`_row_defect`), где пусто — показывается наш `defect_quantity`.
    - `ff_unavailable_by_nomenclature(...)` — **сколько нельзя отгрузить**: только migfull, `qty_good − qty_nominal`, то есть их СОБСТВЕННОЕ `stock_actual − stock_available`; у skladbot/wmscelicom — пусто (выборка вообще ограничена `provider == "migfull"`). Питает вычет из зеркала (`wb_fbs/stock_service._net_mirror`). ⚠️ **Брак skladbot тут НЕ вычитается** (прод-баг, найден 28.07.2026): `amount` (→`qty_good`) и `repair_amount` (→`qty_defect`) — ДИЗЪЮНКТНЫЕ корзины, годный уже без брака. Пруф данными: на складе Газпром у **64 строк из 115** брак БОЛЬШЕ годного — при вложенной корзине невозможно. Вычет был двойным: 491 штука годного срезана, **25 позиций схлопнуты в ноль** и при `min_of_both`/`ff_mirror` уехали бы к WB нулём при живом остатке (кейс 160х230_вишня, ШК 2044388467336: годного 8, брака 14 → зеркало 0, а карточка склада честно показывала 8). ⚠️ **Реконструировать блокировку из наших зеркал нельзя**: попытка вычитать «`stock_locked` минус собранное под наши активные отгрузки» стояла на допущении, что остаток снимет наш резерв `AssemblyRequest`, а это разные множества. Прод-кейс 120х170_серыйоднотон 27.07.2026: `actual 478 / locked 466 / available 12`, Натали выставила в WB **11**, реконструкция давала **443** — нашей заявки на сборку не существовало вовсе. Двойной вычет с `reserved` при этом не возникает: его снимает `_free_sides` (зеркало ниже наших книг ровно на то, что провайдер уже забрал).
    - `ff_boxed_by_nomenclature(...)` — **что лежит коробами** (`{wh: {nom: (штук, коробов)}}`, строки с `base_barcode`). В остаток FBS не входит: продать штуку из невскрытого короба нельзя, нужна поштучная приёмка. Питает поля `qty_ff_boxed`/`ff_box_count` и колонку «В коробах» — рабочий список «что перенести из коробов в россыпь».
- **Досчёт логистики к `ff_good` (skladbot, `ff_logistics`)**: skladbot списывает `stock_actual` (=ff_good зеркало) уже на стадии отгрузки **«Указание вида работ логистики»** (`stage_code ∈ LOGISTICS_WRITEOFF_STAGE_CODES = {"logistics_works"}`), хотя груз ещё физически на складе ФФ, а наша сборка не отгружена (`ship_request` списывает наш сток только по `is_completed`). Без поправки отчёт показывает ложную НЕДОСТАЧУ ровно на объём в этой стадии (подтверждено данными 2026-07-15, склад Газпром: `наш_годный − ff_good_зеркало == объём в logistics_works`; там же разовая сверка склада ADJUSTMENT-ами). `list_stocks` досчитывает состав таких сборок к `ff_good` (`_logistics_in_transit_by_barcode`: ФФ-заявка kind=assembly на стадии списания + `is_completed=false`, сборка в пред-отгрузочном статусе `_PRESHIP_ASSEMBLY_STATUSES` = PENDING/IN_PROGRESS/READY/VEHICLE_ASSIGNED). Отдельное поле строки/итога `ff_logistics` (сколько досчитано); `ff_good` уже включает его → `diff` корректен. После SHIPPED (наш сток списан) или `is_completed` (груз уехал) — не досчитываем (иначе ложный излишек). Только skladbot (стадия провайдер-специфична); migfull/wmscelicom — пустой досчёт. Блок `stock_mismatch` (вкладка «Связи и расхождения» → «Расхождение остатков с ФФ» в `link_anomalies.py`) применяет ТОТ ЖЕ досчёт через батч-хелпер `_logistics_in_transit_multi` (по всем ФФ-складам за один запрос) — иначе логистика в транзите даёт ложную недостачу «у нас больше» и Δ нетто расходится с вкладкой «Фулфилмент» склада (прод-кейс Газпром 2026-07-23: аналитика −5 598 vs склад +151, вся дельта = объём skladbot в logistics_works).
- **FBS-вычет из `ff_good` (`ff_fbs`, все провайдеры)** — зеркальный случай `ff_logistics`, только знак обратный: НИ ОДИН из трёх WMS-провайдеров не снимает свой остаток под FBS-продажи (сверка на проде 29.07.2026) — мы списали единицу из ledger'а (движение `reference_type='FBS_ORDER'`, см. `wb_fbs/orders_service.writeoff_completed_orders`), а ff_good зеркала не шелохнулся, и каждая FBS-продажа читалась как ложное «у ФФ больше». `list_stocks` вычитает из `ff_good` НЕТТО FBS-движений склада (`_fbs_shipped_by_barcode`: `-SUM(quantity)` по `FBS_ORDER` — OUTBOUND-списания и INBOUND-сторно отмен схлопываются сами; нетто ≤ 0 отбрасывается). База вычета — ff_good УЖЕ с досчётом `ff_logistics`; **кап по НАБЛЮДАЕМОМУ ПРОФИЦИТУ обязателен**: `surplus = ff_good − (our_quantity + our_defect для migfull; our_quantity для прочих)` — ровно та развилка, по которой рядом считается diff; `applied = min(нетто, max(surplus, 0))`. Кап по одному ff_good (lifetime-нетто) после первой же сверки ADJUSTMENT'ом — или если провайдер однажды спишет сам — давал ВЕЧНОЕ ложное «у нас больше»; кап по профициту самоизлечивается (выровняли остатки → вычет 0), а в штатном случае профицит и есть объём FBS — полезный эффект не теряется. Наблюдаемость: оба потребителя логируют раз на вызов суммарный clip (Σ нетто − Σ applied) и число промахов ключа (движение есть, строки зеркала/учёта нет) — сломавшаяся предпосылка «провайдер не списывает» обязана быть видна. Отдельное поле строки/итога `ff_fbs` — расшифровка; `diff` считается от поправленного ff_good и остаётся честным. `stock_mismatch` (`link_anomalies.compute_stock_mismatch_cells`) применяет ТОТ ЖЕ вычет батч-хелпером `_fbs_shipped_multi` — ячейка несёт ключ `ff_fbs`, строка склада — `ff_fbs_qty` (Σ по SKU, оставшимся с расхождением); суточный снимок (`stock_mismatch_snapshot`) собирает строки явными ключами — новый ключ его не трогает, а diff снимка автоматически неттирован. ⚠️ Ряд динамики расхождения несёт СТУПЕНЬКУ в день деплоя FBS-вычета: снимки до — с FBS-шумом, после — без; исторические строки не пересчитываются, колонка `ff_fbs` в daily-таблице — отложенная миграция (см. docstring `stock_mismatch_history`). Константа `_FBS_WRITEOFF_REF_TYPE` продублирована в `fulfillment_service` (импорт из wb_fbs дал бы цикл), равенство держит тест-связка в `tests/test_fulfillment_service.py`.
- Снапшот остатков перезаписывается целиком при каждом синке (delete + insert в одной транзакции); нулевые остатки тоже хранятся — нужны для диффа.
- Дубликаты barcode на стороне ФФ (версии товара под WB/OZON) агрегируются суммированием до записи.
- Заявки ФФ — UPSERT по `external_id`; связи `assembly_request_id`/`inbound_receipt_id`/`stock_transfer_id` при обновлении НЕ перетираются.
- Один наш документ ↔ максимум одна заявка ФФ (проверка при link) — **кроме migfull/«Натали» (N:1)**: одной нашей сборке И одной нашей приёмке могут соответствовать 2+ заявки WMS (кейс машины V-0035: InboundReceipt ↔ пара приёмок PVB штуками + коробами). Для migfull `link_request` разрешает мульти-привязку, кандидаты модалки «Связать» не исключают уже связанный документ (`linked_ff_count`), авто-READY сборки и авто-ACCEPT приёмки срабатывают только когда завершены ВСЕ активные привязанные заявки (`_other_linked_ff_all_ready` / `_other_linked_inbound_all_done` + гейт в `_collect_inbound_accept_candidates`; отменённые archived не блокируют), а `compute_doc_ff_mismatch` сверяет наш состав с Σ строк всех привязанных заявок (inbound migfull — из `incoming_lines`, короба сведены к россыпи через guid→ШК зеркала).
- **Слотов связи по-прежнему ТРИ** (`assembly_request_id` / `inbound_receipt_id` / `stock_transfer_id`), `link_request` требует ровно один. Но `stock_transfer_id` с 2026-07-31 обслуживает ОБЕ СТОРОНЫ переезда, а не только приёмную: товар от поставщика → `InboundReceipt`; переезд с нашего склада → `StockTransfer`, причём у ФФ-источника это `kind=assembly` (он СОБИРАЕТ переезд — отгрузочная сторона), а у ФФ-получателя `kind=inbound` (он ПРИНИМАЕТ). Направление валидируется по стороне: `assembly` — только к `from_warehouse_id` перемещения, `inbound` — только к `to_warehouse_id`. Конфликт 1:1 сужен ДО СВОЕЙ СТОРОНЫ (`_transfer_candidates` считает занятость по своему `kind`) — иначе отгрузочное зеркало источника прятало бы переезд от приёмочного зеркала получателя, и обе стороны одного переезда связать было бы физически нельзя. **Статусы кандидатов зеркальны:** для `kind=assembly` — `DRAFT`/`IN_TRANSIT` (ФФ собирает ДО отправки, поэтому черновик здесь законный кандидат, а `COMPLETED` — закрытая история); для `kind=inbound` — `IN_TRANSIT`/`COMPLETED` (черновик ещё не выехал, приходовать нечего). 🔴 `doc_id` уникален только внутри своего `doc_kind` (приёмка №7 и перемещение №7 сосуществуют), поэтому ключ строки и выбор слота — пара `(doc_kind, doc_id)`. Проведение перемещения при СВЯЗЫВАНИИ не автоматизируется, но при **ЗАВЕРШЕНИИ приёмки провайдером — да: авто-приём по факту** (канон 2026-07-28). Синк собирает `_collect_transfer_fact_candidates` (kind=inbound + `stock_transfer_id` + TR в IN_TRANSIT + `transfer_fact_applied_at IS NULL`; **и НЕ завершённые заявки тоже** — migfull кладёт товар на сток при stage «В обработке»), после commit тянет факт по баркодам (`_migfull_transfer_fact_by_barcode`: живые lines + guid→ШК с фолдом коробов; пока только migfull) и зовёт `receive_transfer_fact` (warehouse_outbound): порционный TRANSFER_IN по факту (годное+брак), каждый синк добирает ДЕЛЬТУ факта идемпотентно (по движениям), сверх плана не приходуем, transfer закрывается только когда факт покрыл весь план — недобор остаётся видимым транзитом (колонка «Перемещения» единых остатков). Финальный маркер `transfer_fact_applied_at` ставится атомарно с движениями и ТОЛЬКО при `is_completed` + полном резолве ШК — до закрытия заявка остаётся кандидатом. `compute_doc_ff_mismatch` знает только два типа документов, поэтому у связи с перемещением `linked_mismatch` остаётся `None` («не считали»), а `only_unlinked` требует пустыми ВСЕ слоты.

НЕ полностью атомарно: заказ у ФФ создаётся ДО записи зеркала — при сбое/гонке после POST заказ уже существует (текст ошибки поясняет; заявка появится после синка).
  - **Общие хелперы.** «Голова» `_load_assembly_composition` (загрузка сборки+позиций, guard'ы not_found/чужой-склад/отменена/already_linked/empty, агрегат `qty_by_barcode`) и «хвост» `_finalize_ff_push` (advisory-лок → `_apply_requests(provider)` → связь со сборкой + проверка гонки) — общие для skladbot и wmscelicom, single и bulk. Провайдер-ядра (`_push_assembly_to_ff` skladbot, `_push_assembly_to_wms`) возвращают результат-словарь со `status` (created/deficit/no_warehouse/already_linked/empty/error/not_found) — бизнес-причины и ошибки провайдера не бросаются; одиночная обёртка превращает не-created в 400.
  - **Массовый push** (`POST …/assembly/bulk-create-requests`, `bulk_create_ff_requests`, `FfBulkCreateRequestPayload`→`FfBulkCreateResult`): для выбранных сборок из блока «без связи», тоже по провайдеру. skladbot: склад МП подбирается по складу WB КАЖДОЙ сборки (`_match_wh_option`, нет совпадения → `no_warehouse`), `unloading_date` = её `WbFboSupply.planned_date`, form-data тянется один раз. wmscelicom: каждая сборка → отдельный add+send самовывозом. Каждая сборка независима (дефицит/ошибка не валит батч) → отчёт по статусам.
- **Создание приёмки ФФ из машины (PUSH, только skladbot 852)** (`push_ff_inbound` + `link_ff_inbound_mirror` в `fulfillment_service`, зовутся из `vehicle_delivery.update_vehicle_status` на переходе CUSTOMS→DISPATCHED): когда машина (`CostOrder`) переходит в «Отправлена» и выбран склад, создаём приёмку у ФФ (тип **852** «2.1 Приемка без согласования маркировки») и авто-связываем её зеркало с только что созданной `InboundReceipt` машины (`inbound_receipt_id`). Дальше существующий синк-путь авто-принимает нашу приёмку по `is_completed` (когда ФФ примет) и переводит машину DISPATCHED→DELIVERED — нового кода там нет. Контракт формы 852 (живая проба form-data 2026-07-14): единственное обязательное поле `product_arrival_date` (Y-m-d, берём `estimated_arrival_date` машины, иначе сегодня); полей склада/маркетплейса/дат забора НЕТ (приёмка в собственный склад ФФ). Резолв ШК под типом 852 отдаёт `product_data_id` **и при нулевом остатке** (приход, не расход) → дефицит НЕ проверяем, блокируем лишь нерезолвленные ШК (товар не заведён в карточках ФФ). **Блокирующе:** сбой skladbot (нерезолв/сеть/API) → ValueError → перевод в «Отправлена» отменяется (наша приёмка и статус не создаются; POST — единственный внешний сайд-эффект). Провайдеры без создания приёмки (wmscelicom/migfull) и склады без ключа → `push_ff_inbound` возвращает None, переход идёт как раньше (ручная связь). НЕ полностью атомарно: POST прошёл, но commit БД упал → приёмка у ФФ осиротела (как у сборочного PUSH). `INBOUND_REQUEST_TYPE_ID=852` в `skladbot_client`. Тесты — `tests/test_ff_inbound_push.py`.
- **Массовый локальный архив** (`POST …/requests/bulk-archive`, `bulk_archive_requests`, `FfBulkArchivePayload`): пометить/вернуть `local_archived` для списка заявок склада (идемпотентно, зеркальный archived не трогаем). Питает массовый «В архив»/«Вернуть» в таблице заявок ФФ.
- **Кол-во в штуках россыпи (migfull)** — `total_qty_units` в `FfRequestRow`: пересчёт коробов в штуки (`_migfull_units_by_request` в `list_requests`: из raw `planned_lines` + `_migfull_guid_barcodes`, одним запросом по всем guid, без HTTP/N+1). Только migfull-сборки с разрезолвленными guid; иначе None. Колонка «Кол-во (шт)» в таблице «Сборка» видна, когда у строк есть это число. NB: `FulfillmentRequest.total_qty` у migfull-отгрузки = число КОРОБОВ, не штук.
- **Расхождение наполнения сборки с ФФ** (`get_assembly_ff_mismatch_detail`): ФФ-итог считается в ШТУКАХ. `mode=barcode` — короб×штук из состава (`_mirror_ff_composition`); фолбэк `mode=total` (состав неполный) — `_ff_unit_total` (короба×штук по зеркалу, неразрезолвленный guid → ×1), НЕ `total_qty` (=коробá). Эндпоинт деталки зовёт с `live=True` → неразрезолвленные guid дотягиваются живой карточкой (`_try_migfull_client` + `_migfull_resolve_detail_barcodes`) → обычно `mode=barcode` по позициям; батч аномалий (`link_anomalies`) — `live=False` (без HTTP по каждой сборке).
- **Журнал синков** (`SyncLog`, `sync_type="fulfillment"`): каждый синк склада пишет строку в `sync_log` (`RUNNING` до, `OK`/`ERROR` после) — отдельно от `FulfillmentStatusEvent` (тот про переходы статусов заявок, этот — про сами прогоны). И ручной `POST …/fulfillment/sync` (через `sync_warehouse_logged`), и авто-синки шедулера пишут одну строку в той же сессии: `OK` → `rows_fetched`=остатки+заявки, `rows_inserted`=остатки; `ERROR` → `error_msg` (str(e), trunc 1000) и re-raise. Нет активного ключа → `ValueError` ДО лога. Чтение — `GET /warehouse/{warehouse_id}/fulfillment/sync-runs` → `list[FfSyncRun]` (`list_sync_runs`: JOIN `SyncLog`↔`IntegrationKey` по `integration_id`, фильтр по `project_id`+`warehouse_id`+`sync_type`, новые сверху, limit 100). `FfSyncRun`: `stocks_synced`=`rows_inserted`, `requests_synced`=`max(rows_fetched−rows_inserted,0)`, `duration_seconds`=`finished_at−started_at` сек или None. `SyncLog` без `project_id` — арендатор только через `integration_keys`. Питает вкладку «ФФ синхронизация».
- **История синхронизации** (`FulfillmentStatusEvent`, de03): зеркало хранит лишь ТЕКУЩЕЕ состояние заявки (перетирается синком) — журнал фиксирует переходы. `_apply_requests` сравнивает отслеживаемые поля заявки (`status`, `stage_code`, `stage_title`, `is_completed`, `archived`) со снимком в БД ДО перезаписи; при расхождении пишет строку `changed` (old_*→new_*), первое появление заявки → `created`. Обогащение (`total_qty`/`dest_warehouse`), даты и `raw` сменой статуса НЕ считаются — повторный синк без изменений событий не плодит. События создаются после `flush()` (у новых заявок появился id для FK), `changed_at` = единый `synced_at` синка (события одного синка группируются). Работает для ВСЕХ провайдеров (в т.ч. wmscelicom/migfull, у которых живой истории стадий нет). Чтение — `GET /requests` нет; `GET /warehouse/{id}/fulfillment/status-history?kind=&ff_request_id=` (новые сверху, limit 1000). Read-only журнал: без soft-delete, каскадно удаляется с заявкой.

## Сводная страница «Заявки ФФ»
`GET /warehouse/fulfillment/overview` (query: `kind=assembly|inbound|other`, `warehouse_id`, `only_unlinked`) — сводка по всем складам проекта с активной интеграцией: список складов с каунтами активных assembly-заявок (total / unlinked) + заявки зеркала (limit 500) с `suggestions` — топ-3 кандидата мэтчинга к нашим AssemblyRequest. Эвристика (`_load_match_suggestions`, без HTTP к провайдерам): date_score по |external_created_at − created_at| (0/1/2 дн → 70/55/40, дальше отсев) + пересечение ШК из raw (только wmscelicom: dispatchorders `items[]`; Jaccard × 30) + бонус 10 за суммарное qty в ±10%; cap 100, порог 30. Кандидаты — статусы IN_PROGRESS/READY/VEHICLE_ASSIGNED того же склада, ещё не связанные с ФФ-заявками. Роут со статическим префиксом объявлен раньше параметризованного `/{warehouse_id}/fulfillment/*` (отдельный sub-router в `routers/fulfillment.py`).

## Грабли
- **Деталка заявки skladbot — только недокументированный `GET /v1/requests/show/{id}`** (документированного `GET /v1/requests/{id}` нет — 404). Состав (`products[]`), динамические поля и история стадий доступны; роут не из официальных доков — при внезапных 404 проверить, не выпилил ли его провайдер. Деталка тянется живьём при открытии (не кэшируется): принятые количества меняются на стороне ФФ.
- **`/v1/products` отдаёт сырой Laravel-paginator**: `data` — dict с ключом system_product_id и списком barcode-уровневых item'ов внутри; `limit` в body работает (1000), пагинация `?page=N`.
- **`IntegrationKey` = SoftDeleteMixin + UniqueConstraint без is_deleted** — повторный connect обязан искать строку включая soft-deleted и делать `.restore()`, иначе IntegrityError.
- **Создание заявки у ФФ = реальный заказ** — POST /v1/requests только после явного подтверждения пользователя; локалка и тесты не ходят в живой API (в тестах клиент мокается).
- **Коды стадий skladbot ≠ названия** (тип 851, живые пробы 2026-06-11): `cargo_pickup`=«Забор груза» → `delivery_to_the_marketplace_warehouse`=«Указание обьема груза v2» (!) → «Указание виды работ логистики» (код неизвестен — живых примеров не было). Орфография провайдера гуляет («обьема»/«объема», «виды работ») — классификатор матчит и код, и title-маркеры.
- **migfull: строки приёмок содержат служебные грузоместа** («ФФ грузовое место — короб…», в т.ч. с пометкой «выявленный брак») вперемешку с товарами — фильтровать по name-маркеру при подсчётах. В строках заявок (`lines`) у `product` нет ШК — только guid (поле `product.gtin` приходит, но у «Натали» всегда `null` — ШК живёт лишь в `barcodes[]` карточки); резолв через зеркало остатков. Товар без остатка в зеркало не попал → в деталке приёмки **И отгрузки** строка висела бы «не опознанной»: `get_request_detail` дотягивает ШК живой карточкой (`_migfull_resolve_detail_barcodes`: для guid без ШК в зеркале — `GET /products/{guid}`, короб сводится к россыпи, cap `_ENRICH_DETAIL_CAP`, ошибки деталку не валят). Приёмка тянет клиента всегда (состав — живые lines); **отгрузка — best-effort** (состав из raw; клиент строится только если ключ есть, после disconnect деталка работает из зеркала+raw).

## FF billing — тарифы услуг, посуточное хранение, счета ФФ

**Механика** (зеркалит паттерн заявок на оплату логиста, но для услуг ФФ):
1. **Тарифы** (`WarehouseTariff`, ffb01): на каждом ФФ-складе — своя сетка тарифов 5 услуг (паллетирование ₽/паллета, обработка коробки ₽/короб, хранение ₽/паллета/день, выгрузка фуры ₽/машина, погрузка ₽/паллета или ₽/короб). unit только для LOADING; у прочих услуг фиксирован типом. История через valid_from/valid_to.
2. **Посуточное хранение** (`FfStorageDaily`, снимает штуки→короба→паллеты на момент среза):
   - Джоба `scheduler/jobs/ff_storage_snapshot.py` (23:40 MSK) пишет суточные начисления на ФФ-складе: qty штук/коробов/паллет + стоимость (тариф на дату × паллеты).
   - Источник штук: `FulfillmentStock` (интегрированные складские ФФ) либо fallback `WarehouseStock` для неинтегрированных (апл/хамза).
   - Конверсия qty→boxes→pallets через `box_multiplicity_service` (как в Листе логиста) и `pallet_boxes_by_size` (по ФО).
   - Кратность фиксируется НА МОМЕНТ среза, защита истории от последующих правок.
3. **Ожидаемая стоимость услуг по заявке** (`FfAssemblyExpectedCost`, вкладка заявки сборки):
   - Рассчёт компонент: отправка (паллетирование + обработка коробок + погрузка на основе `AssemblyRequest.ff_custom_warehouse`), приёмка (если есть bound-приёмка ФФ).
   - Если нет тарифа — компонент возвращается с `cost=NULL`, lista итого = сумма известных компонент.
   - Переопределение (`AssemblyRequest.ff_custom_cost` + `ff_custom_cost_comment`) — ручное override, забивает рассчёты.
4. **Счета ФФ** (`FfInvoice` + `FfInvoiceLine`, схемы `FfInvoiceCreatePayload`, эндпоинты `ff-invoices`):
   - Загрузка счёта от ФФ (multipart PDF/Excel): парс реквизитов, выяснение склада по ИНН юрлиц (NULL если неоднозначно — требует ручного выбора).
   - Сверка счёта = пересборка строк (`reconcile`) по якорям (заявка сборки / дни хранения / приёмка / забор): сравнение нашего расчёта vs счётные строки, статус NEW→RECONCILED|DISPUTED.
   - Созданиe заявки на оплату (`create-payment-request`) с category=FULFILLMENT.
   - Два способа матчинга с оплатой: (1) через заявку (`payment_request_id`, ручной/авто процесс заявок); (2) прямой линк дебета выписки (`matched_transaction_id`, авто-матчер счетов).
5. **Авто-матчер счетов** (`etl/sync_ff_invoices.py`, хук в `persist_df` ПОСЛЕ матчеров заявок/заборов):
   - На каждый дебет выписки: если ИНН = ИНН юрлица ФФ-склада проекта, сумма совпадает (±0.01) и в окне ±45 дн, И ровно ОДИН кандидат-счёт → авто-PAID.
   - Пропагация: счёт с payment_request_id, чья заявка PAID → счёт PAID (matched_at из PR).
   - Потреблённые дебеты не матчятся; счёт с активной заявкой идёт через заявочный поток.

## migfull-портал — создание заявки на отгрузку (write через браузер)
У migfull НЕТ write-API → создаём заявку как браузер на портале (Filament v5 / Livewire 3), отдельный `IntegrationKey(service="migfull_portal")` (логин/пароль; НЕ путать с read-only `service="migfull"` Bearer-API).
- **Поток:** на `warehouse/assembly/[id]` кнопка «Создать заявку в ФФ Натали» (виден при настроенном `migfull_portal`-ключе и совпадении склада) → модалка-превью (шапка + строки описи короб/россыпь) → `POST /migfull-portal/assembly/{id}/send` создаёт шапку (Livewire `create`) + грузит опись `.xlsx` (Livewire file-upload). migfull сам парсит опись в Планируемое/Контейнеры.
- **⚠ Создание НЕОБРАТИМО** — у клиента портала нет delete/cancel. Анти-дубль: `MigfullShipmentOrder.SENT` + `FulfillmentRequest(provider="migfull", assembly_request_id)`; без `force_resend` повторная отправка → 409. Audit-строка коммитится ПЕРВОЙ (до FF-link), исход пишется всегда (вкл. UNCERTAIN при guid+упавшей описи и при отмене запроса). create/upload — БЕЗ retry.
- **Сессия/логин:** Filament-логин портала троттлит ~5 попыток/мин (ловилось на батче: 6-я+ заявка падала «вход не подтверждён») → cookie-сессия кэшируется в памяти per (project, host, login) (`_portal_sessions`, TTL 45 мин) — батч логинится один раз; протухшая сессия = redirect на логин из НАЧАЛЬНОГО GET (до мутаций) → `MigfullPortalAuthError` → один перелогин и повтор (`_with_portal_session`).
- **Склад назначения:** наш WB-склад → numeric id формы портала резолвится по имени (`resolve_destination`, уникальный top-score). Индекс складов: зеркало БД (`_mirror_destinations` — `FulfillmentRequest.raw` отгрузок уже содержит destination_marketplace_id+имя, мгновенно и всегда тёпло) + read-API поверх (`_api_destinations`, кэш 1ч, таймаут 20с, негативный кэш 5 мин — раньше был единственным источником, и его таймаут давал «склад не распознан»). Нерезолв — не блокер: склад заполнит оператор.
- **Опись:** короб (есть в «Сопоставлении») → ШК короба ITF14 + число коробов; иначе россыпь EAN13 + штуки; не-кратное коробу → fallback россыпь + warning. Кол-во=коробов.
- **Файлы:** `integrations/migfull_portal_client.py` (Livewire: authenticate/create_shipment/upload_opis; SSRF-allowlist `*.migfull.app`, `follow_redirects=False`, `_redact`), `services/migfull_opis.py` (openpyxl-генератор), `services/migfull_portal_service.py` (config/build_draft/send_shipment, `classify_opis_lines` — чистое ядро), `routers/migfull_portal.py`, `models/migfull_portal.py` (`MigfullShipmentOrder` audit, миграция `mf01`), `schemas/migfull_portal.py`, `scripts/setup_migfull_portal_account.py`. Фронт: `assembly/[id]/MigfullModal.tsx`. Тесты: `tests/test_migfull_{opis,portal_client,portal_service}.py`.

### Поставка (приёмка) у Натали из DDS — обратное направление того же портала
Машина V-… едет НА склад «Натали» → раньше Натали заводила приёмку (PVB-…) у себя вручную, теперь заводим ИЗ DDS. Портал-ресурс — зеркальный `/app/submissions` (Filament генерит те же Livewire-паттерны: `CreateSubmission`/`EditSubmission`/FilesRelationManager; в read-API это `GET /submissions`, kind=inbound).
- **Поток:** на стр. склада, блок «Ожидаемые поставки», кнопка «Создать поставку у Натали» (виден при настроенном `migfull_portal`-ключе, склад = склад ключа, у машины есть приёмка `receipt_id`) → confirm-модалка `MigfullInboundModal` (состав-превью позиции/штуки/короба из `InboundReceiptItem.expected_qty` + «Сопоставление» короб→россыпь) → `POST /migfull-portal/inbound/{receipt_id}/send` (rate_limit_write): `create_submission` (шапка: number=V-…, submission_date, notes) + `upload_submission_opis` (.xlsx как у отгрузок). Write ТОЛЬКО по кнопке — никаких джобов.
- **Идемпотентность:** `MigfullShipmentOrder.inbound_receipt_id` (миграция `mfin01`) — SENT-строка блокирует повтор; плюс уже СВЯЗАННАЯ `FulfillmentRequest(kind=inbound, inbound_receipt_id)` (в т.ч. заведённая Натали и привязанная вручную) тоже считается дублем → 409 без `force_resend`.
- **Автосвязь:** guid созданной поставки сразу пишется в `FulfillmentRequest(provider=migfull, kind=inbound, inbound_receipt_id=…)` — read-синк заupsert'ит прилетевшую PVB в ту же строку по (project, provider, external_id), ручные связи синк не трогает.
- Сервис `services/migfull_portal_inbound.py` (build_inbound_draft/send_submission; общие с отгрузками креды/сессия/`compute_opis_lines_from_qty`). Тесты: `tests/test_migfull_portal_inbound.py`. ⚠ Контракт формы submissions выведен зеркалированием shipments (живой прогон на боевом портале не выполнялся — см. первую реальную отправку).
