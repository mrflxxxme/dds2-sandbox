# DOMAIN_FULFILLMENT — интеграция внешних фулфилментов (skladbot.ru, wmscelicom, migfull)

Generic-слой зеркалирования данных фулфилмент-провайдеров на странице склада: остатки (snapshot + расхождения), заявки на сборку и приёмки (зеркало + ручная связь с нашими документами). Фаза 1 — read-only pull. Фаза 2 (только skladbot) — PUSH: создание заявки «Доставка на склад МП» у ФФ из нашей `AssemblyRequest` (см. «Создание заявки ФФ из нашей сборки»).

## Провайдеры
| | skladbot.ru | wmscelicom («Целиком») | migfull.app («Натали») |
|---|---|---|---|
| База API | `api.skladbot.ru`, Bearer-токен | клиентский инстанс `{client}.wmscelicom.ru` (поле при подключении), **токен в URL-пути** `/api/{token}/…` — не логировать URL | `migfull.app/api/customer/{tenant_guid}` (GUID — поле при подключении, строго UUID), Bearer в заголовке; Laravel-конверт `{success,data,links,meta}` |
| Остатки | `POST /v1/products` (amount/reserve/repair/nominale) | `GET items/get/` — Count→good, CountVirtual→nominal, reserve/defect нет; `Barcodes[]` — берём первый | `GET /products` — stock_actual→good, stock_locked→reserve, stock_available→nominal; **ШК только в карточке** `GET /products/{guid}` |
| Сборка | `/v1/requests?type_id=851` | `dispatchorders/list/` (заявки на отгрузку, зОГ — РОДИТЕЛЬ отгрузки FBO): склад отгрузки=город МП (`warehouse`) + состав (`items[]`). Тянем активные статусы целиком + терминальные за окно `_WMS_DISPATCH_TERMINAL_DAYS`=90д (широкая выборка таймаутит). shipmentsfbo больше НЕ тянем (`shipped_target` там — лишь площадка, не город) | `GET /shipments` — planned/shipped_lines приходят в списке ЦЕЛИКОМ (сверено с *_lines_count живьём) |
| Приёмки | `/v1/requests?type_id=852,2644` | `unloadingorders/list/` (items в ответе списка) | `GET /submissions` (состава в списке нет) + `GET /submissions/{guid}/lines/incoming\|received` |
| Деталка | живой `GET /v1/requests/show/{id}` | **из raw зеркала** — by-id эндпоинта нет; актуальность = последний синк | сборки — из raw зеркала; приёмки — живые lines/incoming+received |
| Лимиты | 60/120 rpm | 150 rpm, max 30 элементов/страница | per_page 1..1000; явных rpm-лимитов нет (caps наши) |
| Токен | RS256 JWT (exp → token_expires_at) | hex-строка, без срока в самом токене | hex-строка, read-only API (POST только для `…/search`) |

Внутри сервиса провайдер-специфика заканчивается на нормализаторах `_normalize_*` (fulfillment_service.py); `_apply_stocks`/`_apply_requests` работают с нормализованными dict.

## Таблицы
| Модель | Назначение | Ключ / constraint |
|--------|------------|-------------------|
| `FulfillmentStock` | снапшот остатков ФФ (qty_good/reserve/defect/nominal) | `(project_id, warehouse_id, barcode)` |

## Бизнес-правила
- **Зеркало никогда не пишет в `WarehouseStock` / `StockMovement`** — наши остатки производны от документов; данные ФФ живут отдельно, вкладка показывает расхождения (diff = ff_good − our_quantity).
- Снапшот остатков перезаписывается целиком при каждом синке (delete + insert в одной транзакции); нулевые остатки тоже хранятся — нужны для диффа.
- Дубликаты barcode на стороне ФФ (версии товара под WB/OZON) агрегируются суммированием до записи.
- Заявки ФФ — UPSERT по `external_id`; связи `assembly_request_id`/`inbound_receipt_id` при обновлении НЕ перетираются.
- Один наш документ ↔ максимум одна заявка ФФ (проверка при link).
- `kind`: skladbot — по `type_id` (851 → `assembly`, 852/2644 → `inbound`); wmscelicom — по источнику (dispatchorders → `assembly`, unloadingorders → `inbound`); migfull — shipments → `assembly`, submissions → `inbound`. wmscelicom `external_id` сборки = `orderid` (стабилен весь цикл, не shipmentid); номера зОГ API не отдаёт (ярлык UI Целиком) → `number=None`. Первый синк после перехода на dispatchorders сносит несвязанные легаси-строки shipmentsfbo (`_purge_legacy_wms_shipments`: raw с `shipment_fbo_id` без нашей связи).
- Один склад — один активный провайдер (guard в `connect`); `IntegrationKey.config`: skladbot — customer_id/token_expires_at, wmscelicom — api_base_url (хост валидируется суффиксом `.wmscelicom.ru` — SSRF-guard), migfull — tenant_guid (строгая UUID-валидация = guard от инъекции пути; хост фиксированный).
- **Выбор кабинета skladbot при connect** (`customer_id` в payload): селлер-токен видит 1 клиента → `customer_id` авто (customers[0]). FF-operator токен видит весь tenant (сотни клиентов, `customers[0]` — произвольный!) → `customer_id` ОБЯЗАТЕЛЕН, иначе ValueError «укажите customer_id». Заданный `customer_id` валидируется через `SkladbotClient.find_customer` (листает `/v1/customers` — прямого lookup по id нет, `search` фильтрует по имени; cap `MAX_CUSTOMER_PAGES`), не найден → ValueError. Решает: число клиентов — `count_customers()` (meta.total). Без этого пиннинга PUSH-заявки/синк ушли бы не тому кабинету.
- wmscelicom-статусы: отгрузка завершена при «Отгружена»/«Вручена получателю»/«Принята в СЦ…», «Аннулирована» → archived; приёмка завершена при заполненном `unloading_close_date`.
- migfull-статусы (слаг → stage_code, человекочитаемый status_display → status/stage_title): отгрузки `uploaded → ready → closed` (+`canceled` → archived), приёмки `processing → send → closed` (+`canceled` → archived); `closed` → is_completed. Служебные позиции «ФФ грузовое место…» (учёт грузомест склада) фильтруются из остатков, тоталов и деталки.
- **Авто-READY связанных сборок**: при синке и при link связанная `AssemblyRequest` переводится `IN_PROGRESS → READY` (история `changed_by=ff_sync`, `actual_ready_date`, invalidate `reports:assembly_flow`), когда стадия ФФ говорит «груз собран» (`_assembly_ready_signal`): skladbot — стадия вне сборочных (`ASSEMBLY_WIP_STAGE_CODES` = cargo_pickup, delivery_to_the_marketplace_warehouse + title-маркеры «забор груза»/«объема груза» в обеих орфографиях) или `is_completed`; wmscelicom — `is_completed` либо статус ∈ `WMS_ASSEMBLY_READY_TITLES` («Собрана»/«Ожидает отгрузки»); migfull — `stage_code == "ready"` («Собран») или `is_completed`. Прочие статусы (VEHICLE_ASSIGNED+) не трогаются, обратных переходов нет; archived/expired не триггерят. Намеренно мимо `mark_ready` (его пред-условия FBO-supply/палеты не применимы к внешнему сигналу).
- **Обогащение зеркала заявок** (`total_qty` — заявлено всего, `dest_warehouse` — «Склад МП»): skladbot — живая деталка `show` при синке (активные сборки каждый синк, завершённые — разовый бэкфилл, cap 100/синк, 429 прекращает обогащение не валя синк); wmscelicom — из raw списка dispatchorders (`items[]` → total_qty / `warehouse` → dest_warehouse=город МП; пустой состав → None, не 0; PHP `false`-warehouse → None); migfull — сборки бесплатно из списка (`planned_quantity_total` / `destination_marketplace.name`), приёмки — `lines/incoming` (активные каждый синк, закрытые — разовый бэкфилл, отменённые НЕ бэкфиллятся — вечный NULL голодал бы cap; cap 100/синк). UPSERT не затирает обогащение `None`'ом.
- **migfull guid→barcode**: в списке `/products` ШК пустые у ВСЕХ товаров — резолв детальными карточками только для незакэшированных guid с остатком, cap 300/синк (хвост дотягивается следующими синками); персистентный кэш = прошлый снапшот `fulfillment_stocks` (`external_product_id` → `barcode`). Нерезолвленные строки в снапшот не попадают (пустой barcode).
- **migfull короб → россыпь** (`base_barcode`/`units_per_box`, ff05): «Натали» держит часть товара коробами (отдельная карточка с ШК короба ITF14, имя «… короб N шт.»), часть россыпью (EAN13); один товар бывает и тем, и другим. У нас учёт россыпью. При синке короб распознаётся (`_migfull_box_pack`): `base_barcode` россыпи выводится из ШК короба по GTIN-14 (`_itf14_to_ean13`: индикатор отброшен, чек EAN13 пересчитан), `units_per_box` — из «короб N шт.» в названии. Строка-короб хранится отдельно (ШК короба + число коробов), но матчится к номенклатуре по `base_barcode`. В `list_stocks` короб сводится к россыпи (`qty × units_per_box`) и складывается со строкой россыпи в ОДНУ строку на товар → `diff` сопоставим с нашим россыпным стоком; `ff_box_units`/`ff_box_count` показывают коробную долю. Авто-вывод проверен живьём (151/151 коробов → номенклатура, unmatched=0) и сошёлся с Excel «Плюс вайб»; отдельная таблица-маппинг НЕ нужна. Прочие провайдеры — `base_barcode=NULL`, `units_per_box=1` (поведение не меняется).
  - **Состав заявок**: `_migfull_guid_barcodes` отдаёт `{guid: (ШК россыпи, units_per_box)}` — короб в строках сборок/приёмок матчится к номенклатуре по россыпи и пересчитывается в штуки (`get_request_detail`, `_fetch_ff_composition` для скоринга); в деталке позиция показывает `box_qty × units_per_box`.
  - **Видимая таблица сопоставления**: `GET /warehouse/{id}/fulfillment/box-packs` (`list_box_packs`) → коробá склада (ITF14 или с base_barcode) с `source` (auto/manual/unmapped); вкладка «Сопоставление» (только migfull).
  - **Ручной override** (`fulfillment_box_overrides`, ff06): когда авто-вывод промахнулся (нестандартное имя/ШК), пользователь привязывает короб к существующей номенклатуре + штук в коробе. `PUT/DELETE …/box-packs/{box_barcode}/override` (`set_box_override`/`delete_box_override`), поиск товара `GET …/box-packs/nomenclature-search?q=`. Override побеждает авто-вывод при синке (`_load_box_overrides` → `_normalize_migfull_stock`) и применяется сразу к текущему остатку; delete возвращает к авто. Привязка только к номенклатуре с ШК (россыпь).
- Токен write-only: наружу только `key_preview` (***последние 4); шифрование `backend/utils/crypto.py`; `config` хранит customer_id и token_expires_at (exp из JWT, ~180 дней — следить за истечением).
- **Локальный архив** (`local_archived`/`local_archived_at`, ff03): пометка пользователя в DDS, НЕ зеркало провайдера (`archived` затирается каждым синком — local_* синк не трогает). `POST|DELETE /requests/{id}/archive`; списки/overview/suggestions/авто-READY исключают архивные; `GET /requests?show_archived=true` — вид «Архив».
- **Кандидаты связывания** (`GET /requests/{id}/link-candidates`): документы склада (assembly → AssemblyRequest кроме CANCELLED + ФБО-поставка/склад WB; inbound → InboundReceipt), не связанные с другими ФФ-заявками, со скорингом «подходит под наполнение»: Jaccard ШК × 60 + кол-во ±10% (+20) + дата 0/±1/±2 дн (+20/15/10), порог 40; состав ФФ — wmscelicom из raw (`items[]`), skladbot живой деталкой (недоступна → фолбэк по датам, порог 30). Каждый кандидат помечен `warehouse_match` (склад сдачи документа совпал со складом сдачи ФФ-заявки, нормализованно через `_norm_wh_name`; для inbound всегда true); ответ несёт `ff_dest_warehouse`. Питает модал «Связать» (поиск + секция «Похожие»); модал по умолчанию показывает только совпавшие по складу + чекбокс «Показать все склады». Реверс-модал (ASM→ФФ) фильтрует так же, клиентски (`whNamesMatch`).
- **Создание сборки из ФФ-заявки** (`POST /requests/{id}/create-assembly`): наша AssemblyRequest из состава ФФ-заявки (kind=assembly, ещё не связанной) через `create_assembly_request` (номер ASM-N, IN_PROGRESS, валидация доступного стока) + автосвязь; ШК без номенклатуры пропускаются и возвращаются в `skipped_barcodes`.
- **Создание заявки ФФ из нашей сборки (PUSH, фаза 2)** (`POST /warehouse/{wid}/fulfillment/assembly/{aid}/create-request`, `create_ff_request_from_assembly`): из позиций нашей `AssemblyRequest` создаёт РЕАЛЬНЫЙ заказ у ФФ и связывает зеркало со сборкой. **Диспетчеризация по провайдеру** (`key.service`): **skladbot** и **wmscelicom** поддержаны, migfull → 400 («не поддерживается для провайдера»). Ниже — детали skladbot (851); wmscelicom-контракт — отдельным пунктом.
  - **skladbot (851 «Доставка на склад МП»):** состав агрегируется по ШК → резолв в `product_data_id` живым `GET /v1/requests/products` (только товары с доступным остатком под тип заявки; нерезолвленные → `skipped_barcodes`), затем `POST /v1/requests` (`SkladbotClient.create_request` — БЕЗ retry: повторный POST = дубль-заказ). Динамические поля 851 (не хранятся в `AssemblyRequest`, задаются в диалоге, предзаполняются из заявки): `marketplace` (Wildberries), `marketplace_delivery_type` (straight/cross_dock), `marketplace_warehouse` (город сдачи WB = `effective_wb_warehouse`), `collection_date`, `unloading_date` (Y-m-d). **Блок по дефициту:** доступного у ФФ (`counts` из resolve) меньше, чем нужно (по любому ШК; нерезолвленный = 0) → 400 со списком дефицита (`_compute_ff_deficit`/`_format_deficit_message`). `unloading_date` по умолчанию = `WbFboSupply.planned_date`, `collection_date` ставит пользователь (кнопка «+3 дня»). Требует write-токен ФФ-оператора у skladbot.
  - **wmscelicom («Целиком»):** `_push_assembly_to_wms` → `POST dispatchorders/add/` (`delivery=2` самовывоз + `fbo=1` + состав `[{barcode, count}]` агрегирован по ШК; БЕЗ retry) → `POST dispatchorders/send/` (авто-подтверждение: перевод в сборку, создаётся Shipment). Склад WB в payload НЕ задаётся — определяется привязкой к WB-поставке на стороне «Целиком» (UI/контракт курьерский, без выбора склада МП); **дефицит заранее не проверяем** (нет stock-резолва, «Целиком» резервирует на add). `external_id` = orderId из ответа add. Если add прошёл, а send упал — заявка уже создана («Новая»): зеркалим и связываем со сборкой (идемпотентность), но возвращаем 400 «подтвердите в ЛК Целиком». UI: диалог без склада/дат (только комментарий), `FfCreateRequestPayload`-поля склада/дат опциональны. Контракт выведён из реальных зОГ silkroad.wmscelicom.ru (склад 2): `externalid` пуст ⇒ не курьер, а самовывоз; склад WB из `addit_info`/привязки.
  - Идемпотентность (оба): сборка уже связана с ФФ-заявкой → 400. Зеркало — через `_apply_requests` (UPSERT + событие `created`) под advisory-локом синка. НЕ полностью атомарно: заказ у ФФ создаётся ДО записи зеркала — при сбое/гонке после POST заказ уже существует (текст ошибки поясняет; заявка появится после синка).
  - **Общие хелперы.** «Голова» `_load_assembly_composition` (загрузка сборки+позиций, guard'ы not_found/чужой-склад/отменена/already_linked/empty, агрегат `qty_by_barcode`) и «хвост» `_finalize_ff_push` (advisory-лок → `_apply_requests(provider)` → связь со сборкой + проверка гонки) — общие для skladbot и wmscelicom, single и bulk. Провайдер-ядра (`_push_assembly_to_ff` skladbot, `_push_assembly_to_wms`) возвращают результат-словарь со `status` (created/deficit/no_warehouse/already_linked/empty/error/not_found) — бизнес-причины и ошибки провайдера не бросаются; одиночная обёртка превращает не-created в 400.
  - **Массовый push** (`POST …/assembly/bulk-create-requests`, `bulk_create_ff_requests`, `FfBulkCreateRequestPayload`→`FfBulkCreateResult`): для выбранных сборок из блока «без связи», тоже по провайдеру. skladbot: склад МП подбирается по складу WB КАЖДОЙ сборки (`_match_wh_option`, нет совпадения → `no_warehouse`), `unloading_date` = её `WbFboSupply.planned_date`, form-data тянется один раз. wmscelicom: каждая сборка → отдельный add+send самовывозом. Каждая сборка независима (дефицит/ошибка не валит батч) → отчёт по статусам.
- **Массовый локальный архив** (`POST …/requests/bulk-archive`, `bulk_archive_requests`, `FfBulkArchivePayload`): пометить/вернуть `local_archived` для списка заявок склада (идемпотентно, зеркальный archived не трогаем). Питает массовый «В архив»/«Вернуть» в таблице заявок ФФ.
- **Кол-во в штуках россыпи (migfull)** — `total_qty_units` в `FfRequestRow`: пересчёт коробов в штуки (`_migfull_units_by_request` в `list_requests`: из raw `planned_lines` + `_migfull_guid_barcodes`, одним запросом по всем guid, без HTTP/N+1). Только migfull-сборки с разрезолвленными guid; иначе None. Колонка «Кол-во (шт)» в таблице «Сборка» видна, когда у строк есть это число.
- **Журнал синков** (`SyncLog`, `sync_type="fulfillment"`): каждый синк склада пишет строку в `sync_log` (`RUNNING` до, `OK`/`ERROR` после) — отдельно от `FulfillmentStatusEvent` (тот про переходы статусов заявок, этот — про сами прогоны). И ручной `POST …/fulfillment/sync` (через `sync_warehouse_logged`), и авто-синки шедулера пишут одну строку в той же сессии: `OK` → `rows_fetched`=остатки+заявки, `rows_inserted`=остатки; `ERROR` → `error_msg` (str(e), trunc 1000) и re-raise. Нет активного ключа → `ValueError` ДО лога. Чтение — `GET /warehouse/{warehouse_id}/fulfillment/sync-runs` → `list[FfSyncRun]` (`list_sync_runs`: JOIN `SyncLog`↔`IntegrationKey` по `integration_id`, фильтр по `project_id`+`warehouse_id`+`sync_type`, новые сверху, limit 100). `FfSyncRun`: `stocks_synced`=`rows_inserted`, `requests_synced`=`max(rows_fetched−rows_inserted,0)`, `duration_seconds`=`finished_at−started_at` сек или None. `SyncLog` без `project_id` — арендатор только через `integration_keys`. Питает вкладку «ФФ синхронизация».
- **История синхронизации** (`FulfillmentStatusEvent`, de03): зеркало хранит лишь ТЕКУЩЕЕ состояние заявки (перетирается синком) — журнал фиксирует переходы. `_apply_requests` сравнивает отслеживаемые поля заявки (`status`, `stage_code`, `stage_title`, `is_completed`, `archived`) со снимком в БД ДО перезаписи; при расхождении пишет строку `changed` (old_*→new_*), первое появление заявки → `created`. Обогащение (`total_qty`/`dest_warehouse`), даты и `raw` сменой статуса НЕ считаются — повторный синк без изменений событий не плодит. События создаются после `flush()` (у новых заявок появился id для FK), `changed_at` = единый `synced_at` синка (события одного синка группируются). Работает для ВСЕХ провайдеров (в т.ч. wmscelicom/migfull, у которых живой истории стадий нет). Чтение — `GET /requests` нет; `GET /warehouse/{id}/fulfillment/status-history?kind=&ff_request_id=` (новые сверху, limit 1000). Read-only журнал: без soft-delete, каскадно удаляется с заявкой.

## Сводная страница «Заявки ФФ»
`GET /warehouse/fulfillment/overview` (query: `kind=assembly|inbound|other`, `warehouse_id`, `only_unlinked`) — сводка по всем складам проекта с активной интеграцией: список складов с каунтами активных assembly-заявок (total / unlinked) + заявки зеркала (limit 500) с `suggestions` — топ-3 кандидата мэтчинга к нашим AssemblyRequest. Эвристика (`_load_match_suggestions`, без HTTP к провайдерам): date_score по |external_created_at − created_at| (0/1/2 дн → 70/55/40, дальше отсев) + пересечение ШК из raw (только wmscelicom: dispatchorders `items[]`; Jaccard × 30) + бонус 10 за суммарное qty в ±10%; cap 100, порог 30. Кандидаты — статусы IN_PROGRESS/READY/VEHICLE_ASSIGNED того же склада, ещё не связанные с ФФ-заявками. Роут со статическим префиксом объявлен раньше параметризованного `/{warehouse_id}/fulfillment/*` (отдельный sub-router в `routers/fulfillment.py`).

## Зависимости
- `DOMAIN_WAREHOUSE` — Warehouse, WarehouseStock (для диффа), InboundReceipt (связь приёмок).
- `DOMAIN_ASSEMBLY` — AssemblyRequest (связь заявок на сборку).

- skladbot.ru API — детали в memory `project-skladbot-api` (лимиты 60/120 rpm, формы ответов, типы заявок).
- migfull.app API — детали в memory `project-natali-fulfilment-api` и `~/Desktop/Натали_фулфилмент_API_документация.md`.

## Грабли
- **Деталка заявки skladbot — только недокументированный `GET /v1/requests/show/{id}`** (документированного `GET /v1/requests/{id}` нет — 404). Состав (`products[]`), динамические поля и история стадий доступны; роут не из официальных доков — при внезапных 404 проверить, не выпилил ли его провайдер. Деталка тянется живьём при открытии (не кэшируется): принятые количества меняются на стороне ФФ.
- **`/v1/products` отдаёт сырой Laravel-paginator**: `data` — dict с ключом system_product_id и списком barcode-уровневых item'ов внутри; `limit` в body работает (1000), пагинация `?page=N`.
- **`IntegrationKey` = SoftDeleteMixin + UniqueConstraint без is_deleted** — повторный connect обязан искать строку включая soft-deleted и делать `.restore()`, иначе IntegrityError.
- **Создание заявки у ФФ = реальный заказ** — POST /v1/requests только после явного подтверждения пользователя; локалка и тесты не ходят в живой API (в тестах клиент мокается).
- **Коды стадий skladbot ≠ названия** (тип 851, живые пробы 2026-06-11): `cargo_pickup`=«Забор груза» → `delivery_to_the_marketplace_warehouse`=«Указание обьема груза v2» (!) → «Указание виды работ логистики» (код неизвестен — живых примеров не было). Орфография провайдера гуляет («обьема»/«объема», «виды работ») — классификатор матчит и код, и title-маркеры.
- **migfull: строки приёмок содержат служебные грузоместа** («ФФ грузовое место — короб…», в т.ч. с пометкой «выявленный брак») вперемешку с товарами — фильтровать по name-маркеру при подсчётах. В строках заявок (`lines`) у `product` нет ШК — только guid; резолв через зеркало остатков.

- `backend/scheduler/jobs/fulfillment_sync.py` — периодический синк (worker). Интервал — `settings.FULFILLMENT_SYNC_INTERVAL_MINUTES` (дефолт 60). **Тиринг расписания (прод):** FAST 10 мин для складов 5 и 1, SLOW 30 мин для склада 2, DEFAULT 60 мин для остальных — задаётся `FULFILLMENT_SYNC_*` env на сервисе `worker` в **`docker-compose.app.yml`** (это файл, который реально деплоит прод: `cd-production.yml` запускает `docker compose -f docker-compose.app.yml up -d`). Раньше переменные жили только в `docker-compose.prod.yml` (деплой его НЕ использует), поэтому авто-синк гонял всё по DEFAULT 60 мин вместо 10 мин у приоритетных складов. **Меняя интервалы/списки складов — правь `docker-compose.app.yml`.** Локально основной scheduler выключен (`SCHEDULER_ENABLED=false`); опционально поднимается **fulfillment-only scheduler** (`FULFILLMENT_SYNC_ENABLED=true`, см. `start_scheduler`/`_start_fulfillment_only_scheduler`) в два контура: быстрый (`FULFILLMENT_SYNC_WAREHOUSE_IDS` @ `FULFILLMENT_SYNC_INTERVAL_MINUTES`) и медленный (`FULFILLMENT_SYNC_SLOW_WAREHOUSE_IDS` @ `FULFILLMENT_SYNC_SLOW_INTERVAL_MINUTES`, пересечение с быстрым исключается). Сужение по складам обязательно — иначе синк всех ~2k замаскированных FF-ключей прод-копии = шторм ошибок.
- `frontend-react/src/app/(main)/p/[slug]/warehouse/[id]/page.tsx` — вкладки «ФФ остатки / ФФ сборка / ФФ приёмки / ФФ история / ФФ синхронизация» (последняя, `ff-sync`, журнал прогонов из `sync-runs`) + блок подключения в «Реквизитах». Хелперы истории (`ffEventSummary`/`ffEventBadge`) — в `ff-shared.tsx`; деталка заявки показывает её срез истории.
