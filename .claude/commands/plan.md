# /plan — план реализации

Создаёт план ПЕРЕД написанием кода. Без явного «ок» / «proceed» код не пишется.

## Когда
Новая фича, архитектурное изменение, сложный рефакторинг, cross-domain задача. Для багов и мелочей план не нужен — действуй сразу.

## Процесс
1. **Анализ требований** — что строим, зачем, что вне scope.
2. **Чтение контекста** — `DOMAIN_*.md` затронутых доменов, существующий код.
3. **Пошаговый план** в порядке: Model → Migration → Schema → Service → Router → Test → Frontend.
4. **Риски** — блокеры, breaking changes, миграции на больших таблицах.
5. **ЖДЁТ подтверждения.**

## Крупная фича (>5 файлов, новый домен)
Перед планом зафиксируй формальную спеку:
- **Requirements** — user stories, измеримые success criteria, out of scope.
- **Design** — модель данных, API-контракт (эндпоинты + схемы + коды ошибок), слой сервисов, кэш.
- **Tasks** — задачи по фазам, каждая ≤1 файл, понятно кому (lead / backend / frontend).

Спека утверждается до плана.

## После подтверждения
Реализация по плану → `/build-fix` при ошибках сборки → субагент `code-reviewer` → `/verify`.
