Инвариант «строка ФОТ (начислено) = сумма подстрок «Менеджеры» + по должностям»
держится ТОЧНО только до ОПиУ; после pro-rata он приблизительный.

**Точно (Decimal, `payroll_service.get_month_accrual`):**
`total = Σ_emp accrued_total`, где `accrued_total = _money(percent_total + fixed)`.
Все слагаемые уже 2-знаковые (`_money` на `SheetTeamAccrual.amount`, `per_member`,
`fixed_accrual`), поэтому `total == managers + Σ by_position` — бит-в-бит, без
хвостов. Неактивные сотрудники не ломают: команда начисляет только
`active_members`, фикс неактивному = 0, а сотрудник с нулём выпадает из ведомости.

**Приблизительно (float, `opiu_service`):** pro-rata неполного месяца множит
КАЖДУЮ компоненту на `factor` отдельно, а `opiu_helpers.build_row` округляет
каждую строку своим `round(x, 2)`. Σ округлённых детей ≠ округлённый родитель.
Репро: `factor=10/31`, total=100000, managers=30000, «Бухгалтер»=70000 →
родитель 32258.06, дети 9677.42 + 22580.65 = 32258.07 (Δ −0.01 ₽).
Полный месяц (`factor=1.0`) безопасен. EBITDA/налоги считаются от родителя, так
что деньги отчёта не едут — расходится только «раскрытая» сумма на экране.

**Why:** канон юзера 2026-07-28 — «Менеджеры» = ВЕСЬ процент команд (должность не
важна), фикс-оклады группируются по `position` (пустая → «Без должности»).
Комментарии в `opiu_service` (блок 7d и блок ФОТ в `_build_pnl_result`)
утверждают инвариант безусловно — это верно про Decimal-слой, но не про
float-слой после pro-rata.

**How to apply:** при ревью изменений в подстроках ОПиУ (не только ФОТ) —
проверять, не масштабируется ли каждая компонента отдельно перед независимым
округлением; лечится largest-remainder (остаток крупнейшему ребёнку) или
пересчётом родителя как суммы уже округлённых детей. Тест на pro-rata с ОДНИМ
ребёнком расхождение не поймает — нужен ≥2.

Смежное: [[cost-valuation-auto-opening-invariants]] — тот же класс «что доказуемо
инвариантно, а что плывёт после переоценки».
